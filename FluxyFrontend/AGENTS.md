# AGENTS.md

Single-package Vite + React 19 SPA (antd 6, react-router-dom 7, react-i18next). Everything under `src/` is TypeScript — strict, checked by `tsc --noEmit`, with Vitest for the pure logic (the suite under `tests/`), the `npm run probe*` scripts for everything that needs a render or a backend, and no runtime type checking.

## Commands

```bash
npm run dev           # vite on https://localhost:5173, auto-opens the browser
npm run build         # tsc --noEmit, then vite build -> dist/
npm run typecheck     # tsc --noEmit only (build runs it first, so this is the fast loop)
npm run preview       # serve dist/
npm run lint          # eslint . — both blocks: **/*.{js,jsx} and **/*.{ts,tsx}, plus jsx-a11y over the JSX; scripts/*.mjs matches neither block
npm test              # vitest run — unit tests for tests/**/*.test.ts (no backend, no browser)
npm run test:watch    # the same suite in watch mode (the edit loop)
npm run favicon       # regenerate public/favicon.ico + favicon.svg from public/logo.svg
npm run probe         # exercise src/utils/* against a running backend (needs the backend)
npm run probe:session # sign in / refresh / sign out against a running backend (needs FLUXY_ADMIN_PASSWORD)
npm run probe:groups # exercise the user-group API and its permission gate (needs FLUXY_ADMIN_PASSWORD)
npm run probe:render  # render every page and assert on the HTML (no backend needed)
npm run probe:i18n   # every literal t('...') key in src/, checked against both bundles
npm run probe:paths  # every API prefix in src/ vs backendPaths in vite.config.js
```

`npm run dev` opens a browser by default; for automation/debugging use `npm run dev -- --no-open` (matches the `dev (debug)` VS Code task, which the `launch.json` Chrome/Edge configs depend on).

Node 22.12 or newer (`.nvmrc` = 22; `engines` states the floor Vitest 5 and Vite 7 share). CI lives at the repository root — `.github/workflows/frontend.yml`, the only place GitHub reads a workflow from — and runs on pushes to `master` and on pull requests touching `FluxyFrontend/`: `npm ci`, typecheck, lint, test, build, `probe:render`, `probe:i18n`, `probe:paths`. The three backend-dependent probes stay local.

Verify changes with `npm run typecheck`, `npm run lint`, `npm test` and `npm run build`, then `npm run probe:render`, `npm run probe:i18n` and `npm run probe:paths` (see "Verifying: Vitest for pure logic, probes for the rest" — typecheck, lint and build all pass on markup that renders nothing, and on a locale key that exists nowhere).

## Structure

- `src/main.tsx` -> `src/App.tsx` -> `src/router/index.ts` (the history) and `src/router/routes.tsx` (the table)
- `src/App.tsx` owns the antd `ConfigProvider` (locale + dark algorithm). Components must be rendered under `<AntApp>` to use `App.useApp()`; `AuthForm` and `RegisterPage` rely on that.
- The tree is layered by what a module knows, not only by file kind. `src/layouts/` is the signed-in shell (`AccountLayout`, `AccountHeader`, `AccountSidebar`); `src/components/` holds UI that knows no domain, with `src/components/table/` for the generic server-table frame the five tables share; `src/features/<domain>/` holds what is bound to one domain — the seven domains `auth`, `profile`, `sessions`, `users`, `user-groups`, `content-categories`, `video-streams`. Each feature is laid out by kind: `api.ts` for its endpoints and request shapes, `types/` for the response contracts those endpoints return (with an `index.ts` re-exporting them as types — the one barrel a feature has), `components/` for its domain-bound UI, `hooks/` for its `queries.ts` and `mutations.ts`, and its own rules as modules at the root beside `api.ts` (`features/auth/policy.ts`, `features/user-groups/permissions.ts`); a folder exists only when it has files, so `sessions`, `user-groups` and `content-categories` carry no `components/` today. `src/pages/` holds the routed screens, grouped by who may open them: `auth/` for the five guest screens, `account/` for the four every signed-in role shares (`DashboardPage`, `ProfilePage`, `SessionsPage`, `ActiveSessionsPage`), and `admin/` for the admin-only screens; `NotFoundPage` and `SectionPage` sit at the root because more than one area reaches them. Pages reach a feature's `api.ts`, `types/`, `components/` and `hooks/` directly (there is no public API yet), the signed-in shell's `AccountHeader` reaches `features/auth/hooks/mutations` for the sign-out hook, features import from the shared `components/`, `hooks/` and `utils/`, and a feature imports neither another feature nor a page — the one deliberate exception is `features/auth/components/RequireAuth.tsx` drawing `pages/NotFoundPage` for a role mismatch, because the guard owns the refusal whose catch-all draws the same page. Nothing under `features/` gets a runtime `index.ts` public API; the one barrel a feature has is its `types/index.ts`, and it re-exports types only, so importing it erases to nothing. The tree's barrels are `src/types/index.ts` for the shared vocabulary, those seven `types/index.ts` files, and the table's two — `components/table/index.ts` for the frame and `hooks/table/index.ts` for the four hooks it runs on (see the bullet on the table frame); every other import stays direct (see the Gotcha on `CODE_STANDARDS.md`).
- **The signed-in shell is responsive, and its breakpoints are decisions rather than antd defaults.** `src/hooks/useIsCompact.ts` answers `(max-width: 991px)` through `useSyncExternalStore`, with `false` as the server snapshot so `probe:render` still measures the desktop shell. At 992px and above `AccountLayout` draws the `Sider` exactly as before. At 991px and below it draws no rail at all: the same `AccountSidebar` renders inside a left `Drawer` whose width is `min(84vw, 320px)`, titled with the area's own heading. The drawer is a layer over the page, so its open state is `AccountLayout`'s own and deliberately not persisted (the desktop rail's remains `fluxy-sidebar-collapsed`); it closes on any route change, on choosing the already-open page through `AccountSidebar`'s optional `onNavigate`, and when a resize crosses back to desktop. The header's leading button follows the mode: `MenuOutlined` with `header.openMenu` and `aria-expanded` in compact mode, the fold/unfold icons with `header.collapseMenu`/`header.expandMenu` on desktop. The account dropdown is hover-opened on desktop (a click opens it too, which is how a focused trigger answers Enter) and click-opened in compact mode, because a finger cannot hover. The logo's width lives in `src/index.css` (132px, 96px at ≤768px, hidden at ≤480px via `rootClassName`); the area title and username disappear at ≤768px; header padding is 8px and content padding 16px at ≤991px; and both the shell and the auth page carry `100dvh` behind `100vh`, so a phone measures its visible viewport rather than the one under its browser chrome.
- **Every card that owns a page toolbar carries `className="page-card"`, and the compact rules key on it.** The seven are `SessionsPage`, `ActiveSessionsPage`, `UsersPage`, `UserGroupsPage`, `VideoStreamsPage`, `ContentCategoriesPage` and `AdminSessionsPage`; the class is what keeps the rules from reaching a card with no toolbar, such as the profile cards or the session cards inside `ActiveSessionsPage`. At ≤1200px `.ant-card-head-wrapper` becomes a column, so the heading takes a row of its own and the toolbar moves under it — measured at 800/992/1024px, the title was width 0 while every control stayed visible, and the title row is the fix. At ≤768px each `.ant-space` in `extra` becomes a column, every control is full width (including the `span` that `hinted` wraps around a disabled button), the heading may wrap (the desktop pages pin `whiteSpace: nowrap` inline, which is why that one rule needs `!important`), and card head/body padding is 16px. Desktop stays one row above 1200px. `probe:render` asserts the class on all seven cards and checks that both stylesheet halves exist; a page added later without the class silently keeps the broken desktop header on a phone.
- `src/features/auth/components/AuthCard.tsx` is the shared frame (language switcher, logo, card, `Form`). Both forms render through it, so a second form looks like the first without copying the layout. It **must** render its `footer` prop — it is the last child inside the `<Form>`, and that is where the cross-link between the two flows has always lived. Dropping it is invisible to `typecheck`, `lint` and `build`, which is how it went missing once.
- `src/features/auth/components/AuthForm.tsx` is the shared credentials form, generic in the values its page collects (see Gotchas). The three login pages in `src/pages/auth/` are thin wrappers that pass `action` + `onSubmit`; add behavior there, not by copying the form.
- `src/features/auth/components/ConfirmCodeForm.tsx` is the second step of registration. It is separate from `AuthForm` because the two share no fields but differ in endpoint, captcha action and rate limit.
- `src/features/auth/components/GuestOnly.tsx` wraps the five guest routes (three sign-ins, registration, password reset) where they are declared in `src/router/routes.tsx`. A visitor who already holds a session is sent to their own area instead of being shown a form that would stack a second session over a first that nothing can end anymore. It renders its children while `GET /auth/me` is in flight — a login form must not sit behind a round trip — and the destination comes from `homeForRole` in `src/utils/session.ts`.
- `src/config/index.ts` holds all route paths, the reCAPTCHA key and `API_BASE_URL`, read from `import.meta.env`. Never hardcode route strings in pages — use `config.X_ROUTE` and `routePath()`.
- `src/utils/http.ts` is the transport: `apiFetch`, the `ApiError` shape, the code→text lookup in both directions (`textForCode` for a refusal, `successTextFor` for a success — the latter unifying the fourteen `textForCode(...) ?? result.message` repeats), `fieldErrors`, and the shared `CallOptions` every endpoint call carries. Each feature's `api.ts` is the endpoint list for that domain, and the auth feature's `api.ts` exports the value shapes (`SignInValues`, `RegistrationValues`) its forms name at their call sites. `src/features/auth/policy.ts` mirrors the server's `RegistrationPolicy` (and `features/profile/loginGuardPolicy.ts` the guard's `LoginGuardPolicy`). `src/utils/session.ts` holds `homeForRole`, the frontend's copy of the server's landing rule (`LandingPathOf`), used by the guest guard, and `areaForRole`, the prefix that landing path sits inside and that every section address is built from. `src/utils/url.ts` holds `apiUrl` — see the circular-import note in Gotchas before moving it. Two display helpers live there as well and are the only ones `probe:render` calls as functions rather than as markup: `src/utils/countryName.ts` turns an ISO alpha-2 code into the country's own name in the page's language through `Intl.DisplayNames` (upper-cases first, because a lower-case `de` is answered with `de` rather than with `Germany`; refuses anything that is not two letters, because `X1` is a `RangeError`; an unknown code comes back as itself), and `src/utils/userAgent.ts` turns a user agent into `Chrome 140 (Windows 10, x64)` or into `null`, which means "show it exactly as it is".
- `src/types/` is the **cross-domain vocabulary**: **one exported type per file**, with `index.ts` re-exporting the shared set so a consumer writes `import type { Session } from '../types'`. What remains there is what more than one feature or `src/utils` names — the role and status enums, the permission catalog, the session and its context value, the bulk and message responses, the login guard settings and the CSRF answer. A domain's own response contracts live in `features/<domain>/types/`, one type per file beside the `api.ts` that returns them, with a type-only `index.ts` re-exporting them so a consumer names the folder (`features/<domain>/types`) rather than a file. Only types live in either place — importing a value from a types folder is a sign the type belongs next to the code that uses it.
- `src/pages/account/SessionsPage.tsx` is the visit history: a read-only antd `Table` on `getSessionHistory` (`src/features/sessions/api.ts`), reached from `nav.items.sessions`, which sits in the `account` group of **all three** roles so `/client|reseller|admin/sessions` all exist. Its types are `src/features/sessions/types/SessionVisit.ts` and `SessionHistoryResponse.ts`. Three things it owns rather than inherits: it reads `getProfile()` once on mount to print `visitedAt` in the **account's** time zone (the profile page promises "Dates and times are shown in this zone", and a history page answering in the browser's zone would be the one place that promise visibly failed); it renders `—` rather than an error for a `null` geo field, because a loopback address or a missing `.mmdb` is unknown, not broken; and it puts the heading, the search and the table in **one** `Card`, because the two cards and the sentence between them were a box around a single subject — the search replaced the sentence. It also owns the column widths (resizable, remembered — see below) and the two display helpers it wires into its cells through `tableCells`, while the table body around them — the resizer cells, the scroll box and the pager — is `src/components/table/ServerTable.tsx`, the same one the other four server-paged tables draw. `npm run probe:render` renders it with an explicit `sectionKey` — the shared `render` helper passes no props and would measure `t(undefined)` — and every render of it lands in the state *before* the first answer arrives, which is why the two helpers it calls are asserted as functions below.
- **Its paging, search and sort are all server side, and that is forced by `total`.** `getSessionHistory` sends `page`, `pageSize`, `search`, `sortBy` and `sortOrder` as query parameters (built with `URLSearchParams`, so a `+` or an `&` in a user agent is searched for rather than reinterpreted). Filtering or ordering in the browser would apply to the page on screen while the pager still counted everything, which is the same lie at both ends. Consequences the page has to keep: any change to the five resets to page 1 (`handleTableChange` distinguishes `extra.action === 'paginate'` from a sort), the page size picker offers 10/20/50/100 — the server's ceiling is 100 and asking for 500 comes back `validation_failed` — and the two sortable headers are **controlled** (`orderOf`) rather than left to antd, because the server always applies an order and a header showing no arrow over rows arriving newest-first would describe a table that does not exist. Only "When" and "IP address" are sortable: those are the two stored columns, and `SessionSortField` on the backend records why the geo fields are not offered.
- **Every column has a width and the table is `table-layout: fixed`, which is the whole answer to a long provider name.** A column with no width of its own grows to fit its widest cell, so an organisation name — whatever the registry called the company, sixty characters and no end — would widen the table and push everything after it sideways. The widths are 300/170/150/240/280 and they are `DEFAULT_COLUMN_WIDTHS`, a *starting point* rather than the answer (see below); the network and user-agent cells truncate through `ellipsis: { showTitle: false }` and hand the uncut value to an antd `Tooltip`, and `overflow-x: auto` lives on `.ant-table-content` so any overflow scrolls inside the card instead of moving the page. antd 6's tooltip takes `styles.container`, not `styles.body`. `npm run probe:render` asserts the `<colgroup>` widths, the fixed layout, the scroll box and the search box — none of which typecheck, lint or the build would notice missing.
- **The visitor may move those widths, and `scroll.x` follows them.** `tableWidth` is the sum of whatever the five currently are, not a constant; the widths live in `useState`, are read from and written to `localStorage` under `fluxy.sessions.columnWidths`, and every path back to `DEFAULT_COLUMN_WIDTHS` (the width-reset control in the card's `extra`, double-click on a handle, `Home` on a focused handle) removes the key so a future default change still applies. Reading it is one `try` and not a `typeof` guard: the probes render this under Node, where `localStorage` is not declared at all and reaching for it is a `ReferenceError`, and the compiler would be entitled to call the `typeof` unnecessary. The floor of 90 is a handle width rather than a taste — a column narrowed to nothing takes its own resize handle off the edge of the screen with it. It is the same 90 the *squeezed* column stops at, for a different reason: a column the screen made narrower has to keep the name of the column in it (see the fit in `ServerTable`). Dragging writes from the width the drag *began* at (an accumulator compounds the delta and the column runs away), listeners live on `window` rather than on the handle (a drag outlives the ten pixels it started on) and are torn down through a ref so that leaving the page mid-drag still ends it; text selection and the resize cursor are held by a class on `body` rather than by `preventDefault()` on `pointerdown`, because whether cancelling that suppresses the compatibility `mousedown` — and with it the `click`, the double-click and the focus — is left to the implementation rather than promised. Keyboard: `ArrowLeft`/`ArrowRight` by 16, `shift` for 64.
- **`ResizableHeaderCell` and the antd sorter both want the same header cell, and `useSorter` wins.** The handle has to be a *sibling* of the header's own content rather than a child of it, because antd wraps a sortable title in a `<button>` and a focusable span inside a button that sorts would sort as well as resize — so the only way to place it is `components={{ header: { cell: ResizableHeaderCell } }}` — set once now, in `ServerTable` — with the per-column data (key, width, label, handlers) handed over by `onHeaderCell`. What is handed over is then **dismantled, not forwarded**: `antd/es/table/hooks/useSorter.js` does not add to what `onHeaderCell` returned, it overwrites it — `aria-label` becomes the column title (line 184), `tabIndex` becomes 0 (line 186), `className` and `title` merge, `onClick` is replaced by the sorter and `onKeyDown` is wrapped so that **Enter sorts before the original handler is called at all**. Getting this wrong is silent: the first version took the cell's `tabIndex` and `aria-label` for its handle, which made the header unfocusable and keyboard sorting impossible while the markup stayed perfectly well formed, and named two of its five handles "When" and "IP address" instead of "Resize the … column". So the cell keeps its `tabIndex`, `aria-label`, click and key handler; the handle gets the separator's `role`, orientation and bounds, a hardcoded `tabIndex={0}`, its own `resizeLabel` channel, and **no `Enter`** — antd has already wrapped that handler and would turn the sort arrow at the same time as the width. A click on the handle is stopped by the *cell*, in the capture phase, before it reaches either the handle or the sorter — a sortable header sorts on any click that bubbles to it, and stopping it on the way down also keeps the handle free of a click listener that a linter (or a reader) would parse as an interaction no keyboard can perform. Both halves are asserted by `probe:render`, which is the only thing that can see them: typecheck is satisfied either way. The component is defined at module scope deliberately — a component type created inside the page would be a new type on every repaint, React would unmount the handle mid-drag and the pointer would go with it.
- **The two display columns are built from helpers, not from the raw server fields.** The country cell shows a *name* (`Germany`, `Германия`) rather than the code GeoIP produces, looked up by `countryName` in the page's own language and drawn as `—` for a null, because a loopback address or a missing `.mmdb` is unknown and not broken; the country column is 150 rather than the 110 a two-letter code needed for exactly that reason. The user-agent cell shows `Chrome 140 (Windows 10, x64)` from `describeUserAgent` and keeps the untouched string in the tooltip, so twenty rows are one scannable line each and the whole client is still one hover away. `null` from `describeUserAgent` means "show it as it is", which is what `curl`, a bot and a browser this build has never heard of get. Two limits it does not pretend to fix: Chrome froze the UA at `Windows NT 10.0`, so **Windows 11 reads as Windows 10** to every parser in existence, and the Mac UA is frozen at `Intel Mac OS X`, so an Apple Silicon Mac gets no architecture rather than a wrong one. The parser is **`ua-parser-js@^1.0.41`, MIT — the 2.x line is AGPL-3.0-or-later and must not be pulled in**, which is why the caret cannot cross a major; `bowser` (no CPU architecture) and `device-detector-js` (LGPL) were the alternatives and are worse fits. It costs ~20 kB minified, and its answers are memoised per string along with the `Intl.DateTimeFormat`s and `Intl.DisplayNames` instances, because the table repaints on every step of a drag and a hundred fresh formatters is 8.6 ms of a 16 ms frame.
- **Dates follow the account's time zone and the *page's* language.** The zone is read once from `getProfile()` because the profile page promises "Dates and times are shown in this zone"; the language is `i18n.resolvedLanguage ?? i18n.language` (not `language`, which still reports a language nobody is being shown once its bundle is missing) because this application has a language switcher and a date in one language beside a country name in another is that switcher visibly failing halfway down a row — the same reason the country column uses it.
- `src/pages/account/ActiveSessionsPage.tsx` is the active sessions page: **one card per sign-in that is still running**, each with the way to end it — the opposite question to the history above, and the opposite shape: no table, no paging, a grid of cards that keeps the way to stop a session inside the session it describes. It is framed by a single `Card` whose `title` is `t(sectionKey)` (so it says what the sidebar says, like the history — there is no `activeSessions.title` key to drift from `nav.items.activeSessions`) and whose `extra` holds the "end all but this one" button — the same single-frame reasoning the history's card gives: a heading floating beside a box of content is a second box around one subject. Reached from `nav.items.activeSessions` (`LaptopOutlined`), which sits in the `account` group of **all three** roles, so `/client|reseller|admin/sessions/active` all exist. Types are `src/features/sessions/types/ActiveSession.ts` and `ActiveSessionList.ts`; the endpoints are `getActiveSessions` / `revokeActiveSession` / `revokeOtherActiveSessions` in `src/features/sessions/api.ts`, and `src/utils/http.ts` grew a `DELETE` branch for them (`RawOptions.method` is `'GET' | 'POST' | 'DELETE'`). Three rules come from the server rather than duplicating it: the grouping into one card per session is the server's (the page draws exactly what the endpoint returns, and `isCurrent` marks the card the page is being read with); the current card's button is disabled because the API would answer `cannot_revoke_current` for that id anyway, so the disabled button is the UI telling the truth the API would tell; and the bulk button is disabled while there is nothing to end. The two revokes are not the same update: a **single** revoke takes its card out of the `['sessions', 'active']` cache with `setQueryData` — a session is exactly one card here, so nothing else on any page is outdated by knowing it — while the **bulk** revoke re-reads with `refetch()`, because the endpoint reports a count and rebuilding the cards from a number would mean deciding in the browser which card is which when the server already knows. Its four API codes (`session_revoked`, `other_sessions_revoked`, `cannot_revoke_current`, `session_not_found`) are translated in `messages.api` of both locales like every other. `npm run probe:render` renders it with an explicit `sectionKey="nav.items.activeSessions"` — the shared `render` helper passes no props, the same reason the history needs its own — and asserts that the heading, the bulk action and the spinner are drawn **before any cards arrive**, because every render in the probe lands in the state before the first answer, which is exactly where a card row must not appear yet.
- `src/pages/admin/UsersPage.tsx` is the admin's account table — heading, toolbar and table in one `Card` (the same single-frame reasoning as the history), reached from `nav.items.usersManage` in the admin-only `users` group, **headed by `users.listTitle` rather than by `sectionKey`**: the page must not repeat in its own card what the menu already says beside it, so the item `Управление`/`Manage users` names how the visitor got there while the card says `Пользователи`/`Users`. The prop is accepted and deliberately unread the same way `UserFormPage`'s is (the comment above `users.listTitle` says why), and the group keeps its own `Пользователи` name on the owner's call — sharing a word with its category is accepted, echoing the clicked item is not. **Paging, search, filtering and sorting are server side, for the reason the history's are: `total`.** A filter or order applied in the browser would narrow the page on screen while the pager still counted everything, so every change goes back to `GET /admin/users`, any change that is not a page turn resets to page 1, and the six sortable headers are controlled. The column keys *are* the server's sort fields (`username`, `email`, `group`, `status`, `lastSeenAt`, `ip` — hence the `lastSeenAt` locale key, so a header click hands its own key to `getUsers` with no mapping table to get wrong); `id` and `actions` never produce a sorter event. `DEFAULT_COLUMN_WIDTHS` is 100/180/160/150/150/180/130/140 = **1190px**, and the selection column takes it to the same **1230** on purpose: that total is what must fit beside the sidebar on one Full HD screen so the action buttons at the far right stay inside the viewport, and the three content columns are narrow *because* their cells truncate through `TruncatedCell` into tooltips — the id shows eight characters with the full GUID on hover, widening one costs visible table room. The actions column is the exception to "a number in the list": it is exactly as wide as the four buttons a row draws (`actionsColumnWidth`), and the room that frees goes to the username — the column this table is read by. It shares `ResizableHeaderCell` / `TruncatedCell` / `useColumnWidths` / `hinted` with the history and with the group table (storage key `fluxy.users.columnWidths`), and the rest of the table frame (`tableResults` / `tableCells` / `TableSearch` / `LoadErrorAlert` / `useRowAction` / `useBulkAction` / `ServerTable` / `RowActions` — see below) with every other table. **The two filters live in the address, not in the page's state**: `?groupId=` and `?status=` are read with `useSearchParams`, narrowed by `enumParam` where they name an enum, and written back by their `Select`s through `withFilter` with `replace: true`. The group one has to be there because the groups table's "show accounts" button sends a visitor here with a filter already chosen, and a filter kept in `useState` would be gone by the time this page mounted — the button would land on the unfiltered list looking like it had done nothing; the status follows it for every reason the five `useServerTable` parameters do. One source rather than two also makes the address shareable and a reload keep the filter, with no effect anywhere keeping the two in step; `replace` rather than push because changing a filter is a change to what is being looked at, not a step worth a history entry; and `withFilter` drops `page` in the same write, so a filter change is one navigation and one request rather than a filter followed by the pager starting over. The role filter was **replaced** by the group filter when the group arrived: a row no longer has a role of its own, the group is what the server joins to answer one, and a filter over a field that is no longer in the query would be a control the endpoint silently ignores. The group options are fetched in a **separate query** from the accounts list (`useAllUserGroups`), because they need `viewUserGroups` while the accounts need `viewUsers` — sharing one call would fail the whole page with `403 permission_denied` for an administrator who may read accounts but not groups, while as it is that visitor's filter simply offers nothing to pick, which is the truth. Status draws as a `Tag` from `STATUS_COLOR` — three descriptions, not a ramp (`UserStatus` is not an ordered scale) — over the **effective** status the server reports, the more restrictive of the account's own and its group's (`combineStatus` in `src/features/users/userStatus.ts`); last visit and address come from the endpoint's `lastSeenAt`/`lastIp` (its freshest refresh token), printed by `formatTimestamp` in the reading account's time zone, with `—` for an account that has never signed in. Only deletion asks first (`modal.confirm` — the one irreversible move); every other action is a request and a **re-read**, because a transition changes what the server considers the row to be and the page draws what it is told. Block and delete are disabled on the signed-in account's own row with the `selfProtected` tooltip — the same "the UI tells the truth the API would tell" rule the active sessions page follows — and an account blocked only by its group answers a block attempt with `user_blocked_by_group`. `npm run probe:render` renders it with an explicit `sectionKey` and asserts the heading (the page's own title, with the menu item's name absent), the toolbar/table before any row, the eight widths *in order*, eight named handles, a sortable header keeping its own access, the group filter and the table's own state (search, status, order) arriving from the address, and both menu items loading the real pages.
- `src/pages/admin/UserFormPage.tsx` is the add **and** edit form — one component behind `users/add` (a menu item) and `users/:id` (an `extra` route with no menu item, reached only by choosing a row; a second `lazy()` over the same module makes a move between the two remount rather than carry a half-filled form across). The heading comes from whether there is an `id` (`users.addTitle`/`users.editTitle`), not from `sectionKey` — the prop is accepted and deliberately unread, and the comment above `addTitle` in the locales says why. Every write is one navigation and one request — a filter change and the page reset it implies are a single address (see `withFilter`), rather than a filter followed by the pager starting over — and a value that says only what its absence says (`page=1`, the default order, an empty search) is removed rather than written, so `/admin/users` and `/admin/users?page=1` are one address with one meaning. `sortFields` is what an incoming `?sortBy=` is judged against (the endpoint's own union, including fields no header offers — `createdAt`, `sortOrder`), so a hand-edited link draws the default order rather than a `validation_failed`. The kit itself lives in `src/components/table/` and is consumed through its `index.ts` — one of the tree's barrels: seven files, nine consumers outside them, and the three-to-five file paths each of the nine used to carry replaced by one specifier; inside the folder files import each other directly (`ServerTable` reaches `./LoadErrorAlert`), because a barrel that one of its own members imported back would be a cycle. `src/utils/tableResults.ts` turns a page's query into the three values it draws from — the rows, `loadError` (the query's own `error` through `messageForError`, so the reason arrives translated) and `loading` (`isFetching`, not `isPending`: a page turn re-reads with the previous rows still on the table under the spinner). `src/utils/tableCells.tsx` holds the shared column renderers — `idCell` (eight characters and an ellipsis, the whole value on hover), `textCell`, `dashedCell`, `ipCell` (code-set), `agentCell` (`describeUserAgent`'s one line, the raw string in the tooltip), `countryCell` (the name in the page's language), `networkCell` (organisation · AS number) — and the dash rule under them: a value the server could not determine is unknown, not broken. - **The table fits the box it is drawn in, and keeps a width of its own when the box is too small for that.** `ServerTable` measures its own box with a `ResizeObserver` — the box is the card's body, and its width is a fact about the window, the zoom and the sidebar (164 pixels of difference on its own), so a table that assumes a width overflows on somebody's screen and not on the one it was written on, and the column that disappears is the one at the far right: the actions. The room is then divided between the columns by `distributeWidths` (`src/utils/tableWidths.ts`), in the proportions the visitor arranged them in: **a column that truncates — one with `ellipsis` — may be narrower, and a column that holds something fixed — a logo, a tag, a row's buttons — keeps its width**, because its content has no smaller form. The actions column is the one this matters for: squeezing it would put the buttons outside their own cell, which is the very thing `actionsColumnWidth` measured. The division is done here rather than left to the browser because a browser stretches a fixed-layout table that is narrower than its box, and it stretches every column in proportion — which would hand the actions column back the very dead space the measurement was taken to remove. **The table has a floor**: a squeezed column stops at `MIN_COLUMN_WIDTH` (90 — the number the visitor cannot drag a column past either, for a different reason: a dragged column's floor is about the resize handle staying reachable, a squeezed one about the column keeping its name), and the table keeps the sum of those floors when the box is narrower still — it then scrolls inside the card, which is what a table on a phone is supposed to do. The room a floored column does not need goes to the columns that can still take it (without that the sum of the shares is *larger* than the room, and a table wider than its box is the one thing the whole exercise exists to prevent), and the shares are rounded by their remainders so the sum is the room exactly — a table a pixel narrower than the box is stretched by the browser, and the column that grows in that stretch is the actions one. The headings of a squeezed column **wrap** rather than being cut: antd's `ellipsis` reaches the heading as well as the cells, and a column showing a letter where a heading should be is a column with no name (`src/index.css`, whose selector is longer than it looks — antd's own rule is three classes and a shorter one loses the cascade). The visitor's own widths are untouched by all of it: the fitting is a fact about the screen, not about the arrangement.
- `src/utils/tableWidths.ts` holds the width rules the tables share, and they are in `utils` rather than beside the frame because they are numbers and a sum rather than a component: `MIN_COLUMN_WIDTH` / `MAX_COLUMN_WIDTH` (the floor and the ceiling of a dragged column, read by the hook that drags it and by the frame that squeezes it), `actionsColumnWidth` (the width an actions column needs for the buttons it holds — `count * 24 + (count - 1) * 4 + 32`, from antd's own small icon button, the gap `RowActions` puts between two of them and the cell's padding), and `distributeWidths` (the room divided between the columns, with the floor). The last two are unit-tested in `tests/utils/tableWidths.test.ts`; the first is read from three places at once, which is why it lives in one.
- `src/locales/en.ts` and `ru.ts` are plain nested objects used as i18next resources. `en.ts` exports `type Translation = typeof en` and `ru.ts` annotates itself with it, which is what makes a key present in one file and missing from the other a compile error.
- `tests/**/*.test.ts` are the unit tests (`npm test`, `vitest.config.js`): pure functions only — no render, no fetch, no DOM — mirroring `src/` under a tree of their own (`tests/utils/`, `tests/features/<domain>/`) rather than sitting beside the modules they cover, with `tsconfig.json` including `tests` so `tsc` checks them too. They are for the halves of `src/` that a probe can only reach sideways (the policy mirrors, `combineStatus`, `permissionsForRole`, the URL rules, the display helpers, `tableResults`); anything that needs markup, a router or an endpoint stays with `probe:render` and the backend probes.

## Registration is two steps on one page

`RegisterPage` holds `step` and the address carried between the steps. `AuthForm` calls `onSuccess(result, values)` once the server answers 2xx, which is what advances to `ConfirmCodeForm`. There is **no `/register/confirm` route** — the visitor stays on `/register` and the page swaps the form underneath them.

The address is mirrored into `sessionStorage` (`src/features/auth/pendingRegistration.ts`) so a reload between the steps resumes instead of throwing the visitor back to the first form. It is a convenience, never a source of truth: the server keys confirmation by address alone, so a stale value costs a re-typed email. Cleared on `registration_confirmed` and on `code_expired` — the latter also drops back to step one, because an expired code cannot be revived by typing a better one.

`captchaAction` is a prop of `AuthForm` separate from `action`. The server fixes one captcha action per endpoint, so the confirm form passes `ConfirmCaptchaAction` from `src/features/auth/api.ts`, while the login pages still let `action` serve both purposes.

## The server code is the branch, not the text

Every response is `{ code, message, errors }`. The client branches on `code` and shows `messages.api.<code>` from the locale files; `message` is used only when a code has no translation yet. `network_error` and `server_error` are the two codes the client invents for failures that never reached the server.

Adding a code to `RegistrationResponses.cs` on the backend without adding it to `messages.api` in both locales breaks nothing — it degrades to the server's English sentence. It should still be added, because the point of the code is to be translated.

`errors` is keyed by the camelCase JSON property name (`username`, `email`, `password`), which is deliberately identical to the antd `Form.Item` names, so `fieldErrors()` feeds `form.setFields` with no translation step.

## The API shares an origin with the page, and that is load-bearing

Nothing here is about convenience. The antiforgery cookies the backend sets are `SameSite=Lax` (`AntiforgeryExtensions.cs` for the framework cookie, `AuthController.GetCsrfToken` for the readable `XSRF-TOKEN`), and a *site* in the SameSite sense is scheme **plus** registrable domain. So an `http://localhost:5173` page calling `https://localhost:7221` is a **cross-site** request even though both hosts read as "localhost". A browser withholds Lax cookies from cross-site subresource requests — `credentials: 'include'` does not change that — and hides them from `document.cookie`, so `getCsrfToken` finds no cookie and returns no token either. Both halves of the pair are lost and every submit comes back `csrf_invalid`.

Switching the base URL to `https://localhost:7221` does not rescue it: the scheme still differs. It only looks like it helps because the `https` launch profile answers the http port with a **307**, and a `fetch` cannot follow that without `Access-Control-Allow-Origin` on the redirect, so the http URL fails differently and worse.

So there are three ways to serve the API in development, and only one of them keeps `SameSite=Lax`:

| Setup | SameSite | Verdict |
| --- | --- | --- |
| Vite proxy over https, `VITE_API_BASE_URL` empty | first-party, irrelevant | **What this repo does** |
| Page on `https://localhost:5173`, API on `https://localhost:7221` | same scheme, so same site | Works, but needs a Node-trusted cert |
| Page on `http`, API on `https` (or the reverse) | cross-**site** | Never works while the cookies are Lax |

Making it work without the proxy would mean either weakening the backend to `SameSite=None; Secure` — which degrades CSRF protection for production, where it is unnecessary, and leaves the app on an insecure origin — or giving the SPA its own trusted certificate. The proxy avoids both and matches the production topology, which is one origin behind a reverse proxy.

### The dev server speaks https, via `@vitejs/plugin-basic-ssl`

`server.https` is on, so the page is `https://localhost:5173` — the same scheme the API is served under in production. The plugin generates a self-signed certificate on first run and caches it at `node_modules/.vite/basic-ssl/_cert.pem`; nothing goes into the machine's trust store. Expect **one** browser warning about the certificate until you accept it, after which Chrome remembers it per host.

This is not cosmetic. With the page on `http` and the backend on `https` — which is exactly what Visual Studio's `https` launch profile produces — the two are different schemes, which is the class of mismatch that produced the `307` → cross-origin → refused chain described under the middleware notes in `AGENTS.md` of the backend. Both halves being https removes the whole category rather than papering over its current instance. It also means the local dev loop is no longer a special case that behaves differently from a deployment.

The proxy target stays the backend's **http** port (`VITE_API_PROXY_TARGET`, default `http://localhost:5159`). The hop from the proxy to the backend is server-to-server on loopback and invisible to the browser, so its scheme has no bearing on SameSite; the browser only ever sees `https://localhost:5173`.

**`npm run probe` goes through `scripts/run-probe.mjs`, not straight to `node`.** Node's `fetch` does not trust a self-signed certificate, so every request through the https dev server failed with `DEPTH_ZERO_SELF_SIGNED_CERT` — and the symptom was badly misleading: `getCsrfToken` treats a network error as "no token" and returns `null`, so the probe reported a failing check *about the CSRF URL* when nothing was wrong with it. The runner spawns the bundle with `NODE_EXTRA_CA_CERTS` pointing at the generated certificate, which is read once at process start and therefore cannot be set from inside the probe. Do not "simplify" this to `NODE_TLS_REJECT_UNAUTHORIZED=0`: that turns off verification for every host the process talks to and hides a genuinely wrong certificate, which is the one thing worth seeing. With the runner in place the probe is 11/11 over `https://localhost:5173` and 11/11 over a plain `http://localhost:5159`; the http path involves no certificate at all, which is a useful control that the fix did not break the no-TLS case.

One more consequence worth remembering: `npm run probe` runs in Node, which has no cookie or SameSite semantics at all — the script has to fake a cookie jar. It can therefore verify the proxy forwards correctly and the whole flow completes, and it did (11/11 through `https://localhost:5173`, and 11/11 over plain `http://localhost:5159`), but it **cannot** detect this class of bug. Only a real browser can, and every check here was made without one.

That gap has a sharp edge worth naming: a Node-only failure can *masquerade* as an application bug. When the dev server turned to https, every probe request failed with `DEPTH_ZERO_SELF_SIGNED_CERT`, `getCsrfToken` converted that to `null`, and the check that reported it was the one asserting `getCsrfToken` uses the API base — pointing at a module that had not changed and was not wrong. A check that fails for a transport reason while describing a logic property is the most expensive kind of failure to read, so check the transport before believing the assertion.

## Verifying: Vitest for pure logic, probes for the rest

`typecheck`, `lint` and `build` are not enough on their own, and this repo has the receipts: `AuthCard` accepted a `footer` prop that four pages passed and it silently rendered nothing. Lint passed, the build succeeded, and the link existed nowhere in the DOM. Reading the code did not catch it. Rendering it did.

Verification therefore has two layers. `npm test` (Vitest, `vitest.config.js`) covers the **pure logic** in the suite under `tests/` — the policy and status mirrors, the permission table, the URL rules, the display helpers — the half that needs neither a browser nor a backend and that a probe can only reach sideways or not at all. Nothing in it renders; a component, a router or a `fetch` in a test would be a second implementation of what the probes already exercise for real.

Everything else stays with the probes, which bundle the **real** `src/` modules with esbuild and print PASS/FAIL per check rather than stopping at the first failure. Every esbuild line in `package.json` carries `--jsx=automatic`, because the sources include `.tsx`: esbuild's own default emits `React.createElement`, which in a Node bundle is a bare reference to a `React` nothing there defines. The automatic runtime instead emits an import esbuild can resolve and bundle. `probe:paths` is the one exception to the bundling: it reads files from disk and is plain Node.

### `npm run probe` — against a running backend

`scripts/probe-registration.mjs` exercises the transport, the code→text lookup and the real endpoints.

```bash
# through the dev server (https, the certificate is trusted by scripts/run-probe.mjs)
set FLUXY_API=https://localhost:5173

# or straight at the backend - only with the `http` profile, since :5159 answers a
# 307 to :7221 under the `https` profile and Node does not trust that certificate
set FLUXY_API=http://localhost:5159

# the backend needs SMTP configured, otherwise step 1 answers 503
# and the confirmation step is never reachable
set FLUXY_MAIL_DIR=<dir an SMTP sink writes .eml into>   # optional; skips the full flow
npm run probe
```

`FLUXY_MAIL_DIR` is what lets it read the confirmation code out of a caught message and confirm for real; without it every error path still runs.

Two things about how it is written, both learned the hard way:

- **It drives the app's own `getCsrfToken`, not a hand-rolled fetch of `/auth/csrf`.** The earlier version fetched the token itself, which meant the request the probe made was correct while the request the browser made was not — `csrf.ts` was reaching for a relative path and every probe still passed. A probe that re-implements the code under test verifies the probe.
- **It emulates a cookie jar.** Node has none, so the script wraps `globalThis.fetch` to keep and replay cookies. That is not decoration — the antiforgery check needs both the cookie and the header token, and without it every POST comes back `csrf_invalid`. It also shims `document.cookie`, which `getCsrfToken` reads, left empty so the cookie short-circuit cannot answer and the real fetch is exercised.

The rate limits make repeated runs awkward, so the script reports a full window as a **SKIP** with the `redis-cli DEL` command to clear it, rather than as a failure. A 429 is the server working correctly and says nothing about the client; failing on it made the probe useless in an ordinary edit loop. Cleared windows: `fluxy:throttle:register:::1` and `fluxy:throttle:confirm:::1` (`::1` is the loopback client, and the colons belong to the IPv6 address).

An enforced reCAPTCHA is skipped for the same reason. A v3 token is minted by Google's JavaScript in a page, so the script cannot produce one: with `RECAPTCHA_SECRET_KEY` set in the backend `.env`, both `POST /auth/registrations` and `POST /auth/registrations/confirm` answer `captcha_invalid` before doing anything measurable. That is the server working correctly, so it is a SKIP with the hint to leave the key empty, not a FAIL. Without this the probe is permanently red on any machine that has the key set, which is exactly the machine where someone would stop trusting it.

### `npm run probe:session` — sign in, refresh, sign out

`scripts/probe-session.mjs` drives the real session flow with the seeded administrator through the app's own `submitAuth`, `signOut`, `currentSession` and `getCsrfToken`: sign-in and `GET /auth/me`, the sign-out the placeholder page performs (with and without an explicit token — and with no session at all, which the endpoint refuses with `auth_required`, since logout is for signed-in visitors only), refresh rotation with reuse detection — a replayed refresh token kills the whole family, current token included — the identical `invalid_credentials` refusal for a wrong password and an unknown account, and the translation of the session codes.

It needs credentials, because the seeded password is random and printed once:

```bash
set FLUXY_ADMIN_PASSWORD=<the "Password: ..." line from the backend log>
# optional: FLUXY_ADMIN_USER (default admin), FLUXY_TEST_LOGIN_LIMIT=1 (spends the whole
# 15-minute login window, so it runs last), FLUXY_PROBE_DEBUG=1
npm run probe:session
```

It also covers the guest pages' landing rule: `homeForRole` must name the same path the sign-in was answered with in `redirect`, and must fall back to a non-guest route for a role it does not know (see the Gotcha on the guard).

Two checks exist for the sign-out bug this probe was written after: a token minted before sign-in is refused once signed in (the antiforgery claims binding — the server log names the reason), and sign-in and sign-out both drop the readable `XSRF-TOKEN` copy so nothing can read that refused token back. The third is the fix: `signOut()` mints at click time, under the session it is about to end. `FLUXY_PROBE_DEBUG=1` prints the cookies each request sent and each response set, which is how the `csrf_invalid` was traced to a specific response instead of inferred — the Node jar has no SameSite semantics, so, as with `probe`, a browser is still the only thing that can check those.

### `npm run probe:groups` — the user-group API and its permission gate

`scripts/probe-groups.mjs` exercises `GET/POST/PATCH/DELETE /admin/user-groups` and the accounts list's `groupId` filter through the app's own `getUserGroups` / `getUserGroup` / `createUserGroup` / `updateUserGroup` / `deleteUserGroup` / `getUsers`. It exists because groups are the first thing in this application behind **two independent gates at once** — a role and a permission — and a single-account probe cannot see a permission gate at all: everything it tries is allowed.

So it needs **two** accounts, and the difference between them is the point:

| Account | Group | Grants | Must |
| --- | --- | --- | --- |
| `historyadmin` | `Admins` (base) | all four | succeed at everything |
| `admintest` | `Limited admins` | `viewUsers`, `editUsers` only | read accounts, be refused every group endpoint with `permission_denied` |

The second account is the check the whole probe is built around. Both take the same password, set directly on the two rows (`bcrypthash` via `dotnet fsi`, cost 11 — the same library the application verifies with). The login window is shared by role and address, so the two sign-ins spend two of the same five permits; a full window is reported as a **SKIP** with the `redis-cli DEL` command, not a failure.

```bash
set FLUXY_ADMIN_PASSWORD=<the password of both accounts>
# optional: FLUXY_GROUP_ADMIN_USER (default historyadmin), FLUXY_GROUP_LIMITED_USER (default admintest)
npm run probe:groups
```

What it asserts, all against a running backend:

- **The base groups.** All three present and only those marked `isBase`; the Admin one grants four, the Client one grants **zero** — drawn as `0`, not as a gap.
- **The asymmetry in the permission catalog.** A permission name that does not exist (`viewEverything`) is **refused** with `validation_failed`; a *valid* one the chosen role does not own (`viewUsers` on a Client group) is **dropped**, and the probe re-reads the row to prove it stored nothing.
- **A base group may be renamed and nothing else.** Role change and permission stripping each answer `409 user_group_immutable`; deletion of one answers the same.
- **`409 user_group_in_use`** on a group that still has a member, and `404 user_group_not_found` on an identifier nobody answers to.
- **`400 csrf_invalid`** on a write with no antiforgery token — checked before the rules above, so it must not come back as a 409 wearing a different hat.
- **`GET /admin/users?groupId=`** returns only that group's accounts, with `groupId` matching on every row.
- **The limited account**: signs in, still reads 10 accounts, and is refused the list, the detail, create, patch and delete — each `403 permission_denied`.
- **Every code it asserted by name is translated in both locale bundles**, by importing `en.ts` and `ru.ts` and looking each one up — a code that reaches the untranslated fallback is an English sentence on a Russian page.

**It cleans up both groups it creates** (including the wrong-role fixture, whose identifier is kept for that purpose). That is a correctness rule and not tidiness: a leftover `Probe client` would make the *next* run's "a second group with the same name is refused" check pass for the wrong reason, having caused its own 409.

### `npm run probe:i18n` — every literal `t()` key, in both bundles

`scripts/i18n-audit.mjs` walks every `.ts`/`.tsx` under `src/`, collects each literal
`t('a.b.c')` key, and resolves it against `en.ts` **and** `ru.ts`.

It exists because the `Translation` type cannot see the bug it was written for. `ru.ts`
declares itself `: Translation` where `Translation = typeof en`, so a key present in one file
and missing from the other is `TS2353` — but a key missing from **both** is absent from the
type itself, and a type cannot report what it does not contain. `t()` keys are deliberately
untyped on the call side (see Gotchas), so `tsc` has nothing to check there either; `lint`
does not, the build does not, and `probe:render` only walks the keys the shell renders.
`videoStreamsForm.namePlaceholder` shipped exactly that way and the form drew the raw key
into its input — in both languages, so it was invisible on the machine it was written on.

A key missing from both bundles is therefore invisible to **every** checker in this repo
except this one, which is the reason it is a probe of its own rather than a note.

No backend, no render, no credentials. It imports the two bundles directly (esbuild compiles
the `.ts`) and reads `src/` from disk, so it is the cheapest of the probes.

Two limits, both deliberate:

- **Only literal keys are collected.** `t(\`videoStreams.statuses.${value}\`)` is a real call
  whose key is built at runtime; the audit skips it rather than guessing an enum's members.
  Those keys are covered by `probe:render`, which renders the pages that build them.
- **The locale files themselves are skipped as sources.** They call no `t()`, and reading them
  would only re-report their own keys.

`probe:render` also asserts the *shape* of the failure over one render — the stream add form
must draw translated text rather than `videoStreamsForm.…` — so a key dropped from both
bundles still fails the probe most likely to be run.

### `npm run probe:paths` — API prefixes vs the dev-server proxy

`scripts/api-paths-audit.mjs` reads every feature's `api.ts`, plus `src/utils/csrf.ts` and `src/utils/http.ts`,
takes the first segment of every path a request is made with (`/auth`, `/admin`), and
compares that set with `backendPaths` in `vite.config.js` — in **both** directions: a prefix
a request uses but the proxy does not know, and a prefix the proxy knows but nothing
requests.

It exists because the failure it catches is silent twice over. An endpoint outside every
proxied prefix is answered by Vite's HTML fallback with a **200**, so `res.ok` is true and
the JSON parse fails; and the one time this class of mismatch actually happened, it surfaced
much later as `csrf_invalid`, because `getCsrfToken` treats any failure as "no token".
Nothing in either symptom names the prefix — see the Gotcha about `apiUrl`.

No backend, no render, no credentials, and no esbuild step: it reads files from disk and
fails loudly when it finds no sources or no `backendPaths`, rather than passing over an
empty set (the same guard `probe:i18n` keeps).

### `npm run probe:render` — no backend needed

`scripts/probe-render.jsx` renders each page with `renderToStaticMarkup` and asserts on the HTML: that the footer cross-link is present where one is meant to be, absent where it is not, that `ConfirmCodeForm` is not dead code, and that the guest guard still shows the form while its session check is in flight. Needs neither a backend nor a mail server, so run it first. Every page render is wrapped in `withQuery` — a **fresh** `QueryClientProvider` per render (`createQueryClient` from `src/utils/queryClient.ts`) — because the pages now read through `useQuery` and would render nothing at all without a client, and a shared one would let one render's cache paint the loaded state the next render is asserted not to show. It also calls two functions directly — `countryName` and `describeUserAgent` — and renders `RowActions` directly, because every render in it lands before the first answer arrives: no row is ever drawn, so neither helper nor the row-action cluster would otherwise be reachable from a probe. The visit history section is where both live, and where the resize handles and the sortable header's own keyboard access are asserted; the accounts table is where the address-borne table state is asserted — a render opened at `?search=…&status=…&sortBy=…` must draw the box, the filter and the header arrow it was opened with, since every one of those falls back to its default silently if the read is dropped.

Two things it had to get right, both of which produced a false failure before being fixed:

- **React escapes `'` as `&#x27;`** even in text content, so "Don't" reaches the DOM escaped. Comparing rendered HTML against the source string fails on a correct page; the script decodes entities before matching.
- **The script is `.jsx`, not `.mjs`,** because `eslint.config.js` enables `jsx` for `**/*.{js,jsx}` only and `npm run lint` would otherwise reject its own JSX.

And one that produced a false **hang**: `main()` ends with an explicit `process.exit(failed === 0 ? 0 : 1)`, and that is load-bearing rather than tidy. Every query the pages create keeps its garbage-collection timer alive — TanStack Query's default `gcTime` is five minutes — and `renderToStaticMarkup` never unmounts anything, so nothing ever cancels those timers. Without the exit the probe prints its full verdict and then sits through the whole five minutes before the process dies, which reads as a hang (and did: the probe "hung" for a day before this was traced with `process.getActiveResourcesInfo()` to a lone `Timeout`).

All five guest pages have a footer, and what each one carries is a fact about the app rather than an oversight. `ClientLoginPage` and `RegisterPage` carry the cross-link between registration and sign-in; `ResellerLoginPage` and `AdminLoginPage` were extended to offer the password-reset link (they had no footer at all before that, which is what an earlier version of this note recorded); `ForgotPasswordPage` carries "back to sign in" in all three of its states. `probe-render.jsx` asserts `hasFooter: true` for all five, so a `footer` prop that silently renders nothing fails there — that is the check, and asserting a footer *absent* on any of them would now be the wrong expectation.

## Gotchas

- **`CODE_STANDARDS.md` is a generic template; where the two disagree, this file wins.** It prescribes Tailwind, Vitest/RTL/Playwright/jest-axe, Storybook, `src/features/[feature]/` and **named exports only**. This repository deliberately has almost none of those: styling is antd 6 plus `src/index.css`, verification is Vitest for the pure logic (the suite under `tests/`) plus the `npm run probe*` scripts (no RTL, no browser test runner, no jest-axe), structure is `src/layouts|components|features|pages|utils|config|types|locales|hooks|router` (its `src/features/[feature]/` idea is adopted only in the light form the Structure section describes: domain components under `src/features/<domain>`, no feature `index.ts` public API, pages not folded in yet), and **`export default` is the convention here** — every page and component uses it and `react-refresh` is fine with it. Read its sections on React hooks, TypeScript safety, accessibility and performance as applicable; read its Tailwind and named-export rules as inapplicable, its feature-structure rule only as far as the light `src/features/<domain>` reading goes (no runtime feature barrel — the only barrel a feature has is its type-only `types/index.ts`; besides those the tree's barrels are the table's two `index.ts` files, the kit's and `hooks/table`'s, see Structure — and direct imports everywhere else), and its testing rules only as far as the `tests/` unit tests go. Do not "fix" default exports to named exports: that is a repo-wide diff with no benefit, and the standard is what needs the correction, not the code.
- **The tree is TypeScript, and `tsc` runs before every build.** `npm run build` is `typecheck && vite build`; `tsconfig.json` is `strict` with `noUncheckedIndexedAccess` and `isolatedModules`, `include: ["src"]` and `allowJs: false`. Nothing under `src/` may be `.js`/`.jsx` again — a half-checked JavaScript file sitting in an included tree is the exact state the flag exists to prevent. `npm run typecheck` is the fast loop: it is what fails on a bad import or a forgotten prop long before the bundle does, and it is not a substitute for `npm run probe:render`, which is the only thing that notices markup rendering nothing.
- **The i18n keys are deliberately untyped; the locale files are not.** `t('profile.typo')` compiles and falls back at runtime, which is accepted because the keys are written twice and the two copies must agree: `en.ts` exports `type Translation = typeof en` and `ru.ts` declares itself `: Translation`, so a key present in one file and missing from the other is `TS2353` on the line it happened. Adding a translation means both files, and that type is what makes it an error rather than a missing string.
- **`AuthForm` and `ConfirmCodeForm` are generic in the values their page collects, and neither has a default.** A page that writes `<AuthForm>` alone infers `unknown`, and its first field read fails to compile — that is the design: the alternative is a `values` typed as whatever the component guessed, which compiles happily and is `undefined` at the first submit. Name the shape at the call site: `SignInValues` or `RegistrationValues` from the auth feature's `api.ts` for `AuthForm`, and `RegistrationConfirmValues` or `ResetConfirmValues` from the component for `ConfirmCodeForm`. The token half of the contract is fixed the same way: neither form mints an antiforgery token — it passes only the captcha token it minted for its action, beside the values — so the endpoint call a page wires in is always its feature's `mutations.ts` hook's `mutateAsync`, never the endpoint function itself.
- **`useSession()` answers `SessionContextValue | null` and never throws without a provider.** `npm run probe:render` renders `ProfilePage` with no provider at all, so a hook that threw would take the probe down instead of describing the page. Consumers narrow instead: `AccountHeader` and `AccountSidebar` write `if (!session) return null` — only `RequireAuth` renders them, so `null` there means the guard was bypassed rather than that nobody is signed in, and the comment above each says so — while everything else reaches through `session?.`.
- **`src/config/index.ts` reads `import.meta.env ?? {}`.** The probes bundle `src/` for Node, where `import.meta.env` does not exist at all: the fallback is what keeps those bundles running, and typing it as `Record<string, unknown>` behind two narrow helpers (`pick`, `raw`) is what keeps `tsc` honest about a value that genuinely is not always there. Vite inlines the real values at build time, so the type is a description of a build step rather than of the object at hand.
- **The route table is annotated `RouteObject[]`, not inferred.** `index: true` widens to `boolean` the moment nothing says otherwise, and an entry carrying both a `path` and an `index` is a contradiction the union only reports once a union is being asked for — which, unannotated, would be the first consumer of the table rather than the line the entry sits on. Every top-level entry is built through `withFallback`, which attaches the shared `ErrorFallback`: the crash screen used to be nine repeated lines, and a route added later would have been the one to drop it.
- **Every request to the API must go through `apiUrl`.** There are exactly two `fetch` calls in the app — one in `csrf.ts`, one in `http.ts` — and both build the URL with `apiUrl(path)`. Nothing may fetch a bare `/auth/...`.
  This is not a style rule. A relative path resolves against whatever serves the page, which in development is the Vite server; it answers an unknown path with the SPA shell and a **200**, so `res.ok` is true, the JSON parse fails, and the token silently comes back `null`. Every later POST is then refused with `csrf_invalid` and the UI shows no cause. It happened once already.
- **`apiUrl` lives in `src/utils/url.ts` and must stay there.** `http.ts` imports `csrfHeader` from `csrf.ts`, and `csrf.ts` needs `apiUrl` too — so defining `apiUrl` in either of them closes an import cycle. A cycle does not necessarily throw here; it can resolve in an order that yields a stale binding, which surfaces as a wrong URL rather than a crash. The module exists to break that, and it imports nothing but `config`.
- **`VITE_API_BASE_URL` must stay empty in development.** `vite.config.js` proxies `/auth` to the backend (`VITE_API_PROXY_TARGET`, default `http://localhost:5159`), and `preview` proxies it too, so the page and the API share one origin. That is not a convenience — see the SameSite note below. `credentials: 'include'` is still set on both fetches; it is a no-op same-origin and load-bearing if a deployment ever splits the origins.
- **Either launch profile works, and that is deliberate — do not "fix" it back to one.** The proxy sets `X-Forwarded-Proto: https`, which is how the backend recognises a proxied request and skips `UseHttpsRedirection` for it (the branch is Development-only; outside it the header is attacker-controlled). Without that header the `https` launch profile answers the http port with a **307** to `https://localhost:7221`, and the proxy relays the redirect verbatim. The browser follows it to a different **scheme**, the call becomes cross-origin, needs a preflight, and the antiforgery cookies come back `secure` over a plain http connection and get discarded — which reads as `csrf_invalid` with nothing wrong in the response body. Measured on the `https` profile: proxied `/auth/csrf` was `307`, then after this change `200` with `XSRF-TOKEN` and **no** `secure` flag, and the POST advanced to `captcha_invalid`, which is the point past CSRF. Visual Studio launches the `https` profile by default, so a rule that only works under the `http` profile would be a rule that breaks again on the next F5.
  The header value must state the scheme the **browser** used, not the one the proxy used to reach the backend. The backend reads it only as a marker that a terminator already decided, so `http` there would be a marker stating the wrong scheme — worse than no header at all, because it would suppress the redirect while misreporting what happened.
- **`strictPort: true` is set on `server` and `preview` on purpose.** Vite's default is to take the next free port, and a silent move from 5173 to 5174 changes the page origin — hence a different CORS decision and a different rate-limit bucket — while the console still prints "ready". This is not hypothetical: a stray second dev server on 5173 pushed the real one to 5174, and that port drift was half of what made the CORS failure above look like an unfixable mystery. The port has to be a fact, not a suggestion.
- **API paths carry no `api/` segment.** The backend serves nothing but the API, so the prefix was dropped there (`[Route("auth")]` in `FluxyBackend/Fluxy.API/Controllers/Auth/AuthenticationController.cs`, and the same route on `RegistrationController.cs` beside it). Both halves hardcode their own copy — `/auth/${action}` in `src/features/auth/api.ts` and `TOKEN_URL` in `src/utils/csrf.ts` — so a rename has to be made in two repositories at once or registration silently 404s. `npm run probe:paths` checks the local half of that drift: every prefix a request is made with must be one the dev proxy knows.
- **The three login endpoints exist and are per-role.** `submitAuth` posts to `/auth/client-login`, `/auth/reseller-login` and `/auth/admin-login`; each refuses an account of a different role with the same `invalid_credentials` a wrong password gets, and each entrance has its own window (5 attempts per 15 minutes per IP and role, keyed without the username). An earlier version of this note said all three 404 — they were filled in when the JWT + refresh-token session was built, and `npm run probe:session` exercises them against a live backend.
- **The profile page has a login guard card next to the time zone card.** `LoginGuardCard` edits the two switches and the three allow lists (`changeLoginGuard` sends them as the `loginGuard` field of the single `PATCH /auth/profile`, `lookupGeo` reads `/auth/geo/lookup` for the "use my current network" button) and joins the same confirmation step as the other changes — a `profile_change_submitted` answer swaps the page to `ConfirmCodeForm` with `kind: 'guard'`, no rename afterwards. The form item names are the server's camelCase field names (`allowedIps`, `allowedCountry`, `allowedAutonomousSystemNumber`), so `fieldErrors()` lands rejections under their inputs with no translation step. Limits mirror the server (`LOGIN_GUARD_MAX_IPS` in `src/features/profile/loginGuardPolicy.ts`); the server stays the authority.
- **The guest pages are guarded in the router, not inside the pages.** `GuestOnly` asks `/auth/me` once per navigation and leaves through `homeForRole(session.role)` — by role, never by entrance: an admin at `/login` belongs on the admin area, a client at `/admin/login` on the client one, because that is where signing that account in would land it. Two properties are easy to break without anything failing loudly. The fallback for an unknown role must be a **non-guest** route — a session that demonstrably exists sent back to login would pass through the guard that just asked and come straight back, which is a loop and not a fallback. And the destination must come from this app's own route table rather than a path the server sent, so a path the two sides disagreed about cannot bounce a signed-in visitor between the catch-all and the guard. The two copies of the landing rule agreeing is asserted by `npm run probe:session`: `homeForRole(role)` must equal the `redirect` the sign-in itself was answered with.
- **`homeForRole` and `areaForRole` answer different questions, and building a section URL from the wrong one is how `/admin/dashboard/profile` happened.** The landing path the server names is a *page* — `admin/dashboard` — while the area every section hangs from is only its prefix — `admin`. So the router's area path, the sidebar's menu keys and the header's profile shortcut all take `areaForRole`; `homeForRole` is where a sign-in opens and nothing else. Both are cut from the same `config.*_HOME_ROUTE` by `areaOf` / `insideArea` in `src/config/index.ts`, so neither can move without the other, and neither the server's `Auth:LandingPath*` nor the landing paths themselves changed when the nesting did. `npm run probe:render` asserts the result twice: every menu key must match a declared child route, and `matchRoutes` must resolve each of them to that role's own area rather than to the catch-all — a nested path still resolves, just to the 404, so string comparison alone would have passed it.
- **Page `action` is the reCAPTCHA action and comes from a `*CaptchaAction` constant; the submit path is kebab-case.** `ClientLoginPage` passes `action={ClientLoginCaptchaAction}` (`'client_login'`, the string the server expects to find in the token) and submits to `action: 'client-login'`. The two spellings still have to agree when a flow is added — the captcha half is now a constant in `src/features/auth/api.ts` rather than a literal copied into five pages, but the endpoint is still written where it is used.
- **reCAPTCHA is disabled in dev** (`getCaptchaToken` returns `null` when `import.meta.env.DEV`) and skipped entirely when the site key is empty. Captures in prod only.
- **`getCsrfToken` always mints a fresh token — never a cached one, never the cookie read back.** It is best-effort only in the failure direction: it silently returns `null` when the backend is absent, and that silence is load-bearing for the login pages. It is also what hid the wrong-URL bug above, which is why the probe asserts the URL `getCsrfToken` actually requests. **The callers are exactly four modules** — `http.ts` for its refresh retry, `features/auth/api.ts` for `signOut` (which must mint under the session it is about to end), `hooks/useWrite.ts` for every write built on it and `features/sessions/hooks/mutations.ts` for the one write with no argument of its own — and a page or a component naming it directly is a sign the write belongs in its feature's `hooks/mutations.ts`.
  The freshness is a correctness rule, not a preference. The antiforgery service binds a token to the identity that was current when it was minted: a token obtained on the sign-in page is refused after sign-in, with `csrf_invalid` and `"The provided antiforgery token was meant for a different claims-based user than the current user"` in the server log. That is exactly what killed the placeholder's sign-out button — it read the `XSRF-TOKEN` cookie written before the session existed, the POST came back 400, and `handleSignOut` had no `catch`, so nothing appeared to happen at all. Two fixes close it from both sides: every submit now mints immediately before sending, and the backend drops the readable `XSRF-TOKEN` copy whenever the session changes (`AuthCookies.Write`/`Clear`), so a cookie cannot outlive the identity it was minted under either. Both halves — and the refusal of the stale token, which is the rule itself — are asserted by `npm run probe:session`.
- **The header logo is sized through `rootClassName`, not `className`, because antd's `Image` puts those two on different elements.** In antd 6 `className` lands on the `<img>` itself and `rootClassName` on the `.ant-image` wrapper; the wrapper is the flex item whose width is the logo's width. Giving the class to the `<img>` looks right in the markup and loses the cascade twice over: antd's `.ant-image .ant-image-img { width: 100% }` is two classes to the logo's one, and the wrapper is left shrink-to-fit, so at 1440px the image measured 914×291 inside a 64px header and pushed the page's scroll width past the viewport. `AccountHeader` therefore carries `rootClassName="layout-shell__logo"`, `index.css` sets the width on that wrapper, and `.layout-shell__logo .ant-image-img` lets the image fill it. The width is CSS rather than the `width` prop so the 96px and hidden breakpoints can change it without an inline style winning.
- **The app renders two assets: `public/logo.jpg` (both `AuthCard` and `AccountHeader`) and `public/logo.svg` (the favicon generator).** All of `public/` is tracked, so a fresh clone renders both. Two files sit in the *repository root* — `logo.jpg` and `reflux_logo.png` — and nothing in `src/` or `scripts/` references them; `public/logo.png` is likewise referenced by nothing. Do not "wire up" any of the three, and do not assume a root `logo.jpg` is what `/logo.jpg` serves.
- `index.html` carries a static `lang="en"` for the moment before the bundle runs; from then on `src/i18n.ts` keeps `document.documentElement.lang` in step — on init and on every `languageChanged` — from `i18n.resolvedLanguage ?? i18n.language`. The language itself comes from i18next (`localStorage` key `fluxy-lang`, then `navigator.language`, default `en`).
- `.env` is gitignored; `.env.example` is the committed template (it documents `VITE_API_BASE_URL`, the route vars and the reCAPTCHA key). Env vars are inlined at build time, so changing them requires a rebuild, not just a dev-server restart.
