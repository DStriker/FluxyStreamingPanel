# AGENTS.md - FluxyFrontend

Single-package Vite + React 19 SPA (antd 6, react-router-dom 7, react-i18next). Everything under `src/` is TypeScript — strict, checked by `tsc --noEmit`, with Vitest for the pure logic (the suite under `tests/`), the `npm run probe*` scripts for everything that needs a render or a backend, and no runtime type checking. Backend-facing work: read `..\FluxyBackend\AGENTS.md` first. Topic detail lives in `docs\` — see the pointer table at the bottom.

## Commands

```bash
npm run dev           # vite on https://localhost:5173, auto-opens the browser
npm run build         # tsc --noEmit, then vite build -> dist/
npm run typecheck     # tsc --noEmit only (build runs it first, so this is the fast loop)
npm run preview       # serve dist/
npm run lint          # eslint . — both blocks: **/*.{js,jsx} and **/*.{ts,tsx}, plus jsx-a11y over the JSX; scripts/*.mjs matches neither block
npm test              # vitest run — unit tests for tests/**/*.test.ts (no backend, no browser)
npm run test:watch    # the same suite in watch mode (the edit loop)
npm run favicon       # regenerate public/favicon.ico + favicon.svg from public/logo.svg
npm run probe         # exercise src/utils/* against a running backend (needs the backend)
npm run probe:session # sign in / refresh / sign out against a running backend (needs FLUXY_ADMIN_PASSWORD)
npm run probe:groups # exercise the user-group API and its permission gate (needs FLUXY_ADMIN_PASSWORD)
npm run probe:render  # render every page and assert on the HTML (no backend needed)
npm run probe:i18n   # every literal t('...') key in src/, checked against both bundles
npm run probe:paths  # every API prefix in src/ vs backendPaths in vite.config.js
```

- `npm run dev` opens a browser by default; for automation/debugging use `npm run dev -- --no-open` (matches the `dev (debug)` VS Code task the `launch.json` Chrome/Edge configs depend on).
- Node 22.12 or newer (`.nvmrc` = 22; `engines` states the floor Vitest 5 and Vite 7 share).
- CI lives at the repository root — `.github/workflows/frontend.yml`, the only place GitHub reads a workflow from — and runs on pushes to `master` and PRs touching `FluxyFrontend/`: `npm ci`, typecheck, lint, test, build, `probe:render`, `probe:i18n`, `probe:paths`. The three backend-dependent probes stay local.

## Structure (core)

Full tree, shells, tables and per-page rules: the topic files below. These twelve are the frame every task sits in.

- `src/main.tsx` -> `src/App.tsx` -> `src/router/index.ts` (the history) and `src/router/routes.tsx` (the table)
- `src/App.tsx` owns the antd `ConfigProvider` (locale + dark algorithm). Components must be rendered under `<AntApp>` to use `App.useApp()`; `AuthForm` and `RegisterPage` rely on that.
- The tree is layered by what a module knows, not only by file kind. `src/layouts/` is the signed-in shell (`AccountLayout`, `AccountHeader`, `AccountSidebar`); `src/components/` holds UI that knows no domain, with `src/components/table/` for the generic server-table frame the twenty tables share; `src/features/<domain>/` holds what is bound to one domain — the twenty-one domains `auth`, `profile`, `sessions`, `users`, `user-groups`, `blacklists`, `content-categories`, `video-streams`, `audio-streams`, `video-on-demand`, `series`, `epg`, `bouquets`, `tariff-plans`, `subscriptions`, `connection-logs`, `credit-logs`, `user-logs`, `api-request-failures`, `stream-problems` and `mag-events`. Each feature is laid out by kind: `api.ts` for its endpoints and request shapes, `types/` for the response contracts those endpoints return (with an `index.ts` re-exporting them as types — the one barrel a feature has), `components/` for its domain-bound UI, `hooks/` for its `queries.ts` and `mutations.ts`, and its own rules as modules at the root beside `api.ts` (`features/auth/policy.ts`, `features/user-groups/permissions.ts`); a folder exists only when it has files, so `content-categories`, `credit-logs`, `epg`, `series`, `sessions`, `tariff-plans`, `user-groups`, `user-logs`, `video-on-demand`, `api-request-failures` and `stream-problems` carry no `components/` today. `src/pages/` holds the routed screens, grouped by who may open them: `auth/` for the five guest screens, `account/` for the four every signed-in role shares (`DashboardPage`, `ProfilePage`, `SessionsPage`, `ActiveSessionsPage`), and `admin/` for the admin-only screens; `NotFoundPage` and `SectionPage` sit at the root because more than one area reaches them. Pages reach a feature's `api.ts`, `types/`, `components/` and `hooks/` directly (there is no public API yet), the signed-in shell's `AccountHeader` reaches `features/auth/hooks/mutations` for the sign-out hook, features import from the shared `components/`, `hooks/` and `utils/`, and a feature imports neither another feature nor a page — the one deliberate exception is `features/auth/components/RequireAuth.tsx` drawing `pages/NotFoundPage` for a role mismatch, because the guard owns the refusal whose catch-all draws the same page. Nothing under `features/` gets a runtime `index.ts` public API; the one barrel a feature has is its `types/index.ts`, and it re-exports types only, so importing it erases to nothing. The tree's barrels are `src/types/index.ts` for the shared vocabulary, those twenty-one `types/index.ts` files, and the table's two — `components/table/index.ts` for the frame and `hooks/table/index.ts` for the four hooks it runs on (see [docs/tables.md](docs/tables.md)); every other import stays direct (see the `CODE_STANDARDS.md` bullet under Gotchas).
- `src/config/index.ts` holds all route paths, the reCAPTCHA key and `API_BASE_URL`, read from `import.meta.env`. Never hardcode route strings in pages — use `config.X_ROUTE` and `routePath()`.
- `src/utils/http.ts` is the transport: `apiFetch`, the `ApiError` shape, the code→text lookup in both directions (`textForCode` for a refusal, `successTextFor` for a success — the latter unifying the fourteen `textForCode(...) ?? result.message` repeats), `fieldErrors`, and the shared `CallOptions` every endpoint call carries. Each feature's `api.ts` is the endpoint list for that domain, and the auth feature's `api.ts` exports the value shapes (`SignInValues`, `RegistrationValues`) its forms name at their call sites. `src/features/auth/policy.ts` mirrors the server's `RegistrationPolicy` (and `features/profile/loginGuardPolicy.ts` the guard's `LoginGuardPolicy`). `src/utils/session.ts` holds `homeForRole`, the frontend's copy of the server's landing rule (`LandingPathOf`), used by the guest guard, and `areaForRole`, the prefix that landing path sits inside and that every section address is built from. `src/utils/url.ts` holds `apiUrl` — see the circular-import note in [docs/gotchas.md](docs/gotchas.md) before moving it. Two display helpers live there as well and are the only ones `probe:render` calls as functions rather than as markup: `src/utils/countryName.ts` turns an ISO alpha-2 code into the country's own name in the page's language through `Intl.DisplayNames` (upper-cases first, because a lower-case `de` is answered with `de` rather than with `Germany`; refuses anything that is not two letters, because `X1` is a `RangeError`; an unknown code comes back as itself), and `src/utils/userAgent.ts` turns a user agent into `Chrome 140 (Windows 10, x64)` or into `null`, which means "show it exactly as it is".
- `src/types/` is the **cross-domain vocabulary**: **one exported type per file**, with `index.ts` re-exporting the shared set so a consumer writes `import type { Session } from '../types'`. What remains there is what more than one feature or `src/utils` names — the role and status enums, the permission catalog, the session and its context value, the bulk and message responses, the login guard settings and the CSRF answer. A domain's own response contracts live in `features/<domain>/types/`, one type per file beside the `api.ts` that returns them, with a type-only `index.ts` re-exporting them so a consumer names the folder (`features/<domain>/types`) rather than a file. Only types live in either place — importing a value from a types folder is a sign the type belongs next to the code that uses it.
- `src/utils/hinted.tsx` holds `hinted` — the span that wraps a disabled button so a tooltip still opens over it. A native `<button disabled>` swallows the pointer events a tooltip listens for, and two buttons on each of these tables are disabled *on purpose*, so without the wrapper the reason a button is greyed out is the one thing the visitor cannot read. Extracted out of `UsersPage` when the group table needed the same helper — the precedent is `loginGuardForm.ts`, and `react-refresh/only-export-components` is what forces a component's file to export only its component.
- `src/utils/queryClient.ts` builds the one TanStack Query client (`createQueryClient`, used by `src/App.tsx`), and its defaults are the decision, not boilerplate: **`staleTime: 0`, `retry: false`, no focus/reconnect refetch** — the library is not here for its cache (a cached account list is a stale one, which is exactly why the pages used to re-read in every effect); it is here for request **deduplication** across mounted pages, a real `AbortSignal` instead of a `cancelled` flag, and `refetch()`/`invalidateQueries` instead of the fifteen `setAttempt(v => v + 1)` counters that used to exist. New queries inherit this; do not raise the cache settings per page.
- Each feature's `hooks/queries.ts` holds **that domain's reads of the API** — one `useQuery`-wrapping hook per endpoint, the query key in the same file as its hook (`['users', params]` in `features/users/hooks/queries.ts`, `['sessions', 'active']` in `features/sessions/hooks/queries.ts`). The rule is unchanged: a page never fetches in a `useEffect`; it names the hook and its parameters, the key *is* the parameters so a filter change is a new query rather than an effect that had to notice one, and mutations call `refetch()` instead of bumping a counter. Each `queryFn` passes React Query's `AbortSignal` through to `apiGet` (`src/utils/http.ts` and every feature's `api.ts` take an optional `signal`; `probe-groups`-style scripts keep working because it is optional everywhere). Session fetching is **deliberately not** in any of them — `RequireAuth`/`GuestOnly` ask `/auth/me` on every navigation because a cached session is a stale session. A read another domain needs is imported across — `useProfile` for the account's zone, `useAllUserGroups` for the accounts filter — because pages may import several features; nothing inside a feature reaches across.
- Each feature's `hooks/mutations.ts` holds **that domain's writes** — one `useMutation`-wrapping hook per write endpoint, the counterpart of its `hooks/queries.ts`, built on the shared `useWrite` in `src/hooks/useWrite.ts`. That helper carries the token rule the rest of the app depends on: `mutateAsync` takes the endpoint's own arguments **without the antiforgery token**, which `useWrite` mints at call time inside the hook — the rule `getCsrfToken`'s comment states (a token is bound to the identity that was current when it was minted, so one carried across a session change is refused as `csrf_invalid`) is structural here rather than remembered at each call site. The captcha token is the exception and stays with the caller: it is minted for an action the endpoint fixes and the form knows. `signOut` (in `features/auth/hooks/mutations.ts`) and `revokeOtherActiveSessions` (in `features/sessions/hooks/mutations.ts`) are the two special cases — the first mints its own token because it must (see its note in `src/features/auth/api.ts`), the second takes no arguments at all and mints its own token on the spot. Nothing there reports, refetches or navigates: that stays with the page, and the shapes the screens share live where they already did. The guest forms follow the same boundary from the other side — `AuthForm`'s `SubmitArgs` hands over `{ values, captchaToken }`, and `ConfirmCodeForm` and `LoginGuardCard` state the same shape for their own callbacks — and every in-flight flag on a page is its mutation's own `isPending` (a form's `submitting` derives from whichever half is running, a row's spinner from `variables`), rather than a state someone has to remember to clear. After this, `getCsrfToken` is called by exactly four modules: `http.ts` (the transport), `features/auth/api.ts` (`signOut`), `hooks/useWrite.ts` (every write built on it) and `features/sessions/hooks/mutations.ts` (the one write with no argument of its own).
- `src/locales/en.ts` and `ru.ts` are plain nested objects used as i18next resources. `en.ts` exports `type Translation = typeof en` and `ru.ts` annotates itself with it, which is what makes a key present in one file and missing from the other a compile error.
- `tests/**/*.test.ts` are the unit tests (`npm test`, `vitest.config.js`): pure functions only — no render, no fetch, no DOM — mirroring `src/` under a tree of their own (`tests/utils/`, `tests/features/<domain>/`) rather than sitting beside the modules they cover, with `tsconfig.json` including `tests` so `tsc` checks them too. They are for the halves of `src/` that a probe can only reach sideways (the policy mirrors, `combineStatus`, `permissionsForRole`, the URL rules, the display helpers, `tableResults`); anything that needs markup, a router or an endpoint stays with `probe:render` and the backend probes.

## Verifying: Vitest for pure logic, probes for the rest

`typecheck`, `lint` and `build` all pass on markup that renders nothing, and on a locale key that exists nowhere — so pick by what you touched. Verify changes with `npm run typecheck`, `npm run lint`, `npm test` and `npm run build`, then `npm run probe:render`, `npm run probe:i18n` and `npm run probe:paths` — the three probes CI runs.

| Command | Verifies | Run when |
| --- | --- | --- |
| `npm run typecheck` | `tsc --noEmit` over `src/` and `tests/` | always — the fast loop |
| `npm run lint` | eslint over the JS/TS blocks plus jsx-a11y | always |
| `npm test` | Vitest pure-logic suite (`vitest.config.js`) | any logic change |
| `npm run build` | typecheck, then `vite build` into `dist/` | before handing off |
| `npm run probe:render` | renders every page, asserts the HTML | any page, component or route change — no backend |
| `npm run probe:i18n` | every literal `t()` key against both bundles | any locale or `t()` change — no backend |
| `npm run probe:paths` | API prefixes in `src/` vs `backendPaths` | any new endpoint or proxy change — no backend |
| `npm run probe` | transport, code→text lookup, real endpoints | backend running, transport/CSRF touched |
| `npm run probe:session` | sign-in, refresh, sign-out, CSRF freshness | auth/session touched, backend running |
| `npm run probe:groups` | user-group API and its permission gate | groups/permissions touched, backend running |

Env vars, run order, caveats and what each probe has caught: [docs/probes.md](docs/probes.md). Vitest never renders; probes bundle the real `src/` with esbuild and print PASS/FAIL per check.

## UI rules that govern every page

The full text, with the reasoning: [docs/ui-rules.md](docs/ui-rules.md). The five rules, in short:

- **The page title is always visible in the page card.** Every routed page's `Card` carries a `title` — in loading, failed-read and empty states too — and it must stay readable, not merely present: the `page-card` class and the pinned `styles={{ title: { whiteSpace: 'nowrap' } }}` are what stop antd from shrinking it to zero width beside a wide toolbar. The menu names how the visitor arrived; the card names what they are looking at, and the two may differ.
- **A long filter control gets its own row above the table, outside the card head.** `DatePicker.RangePicker` (and a long multi-select or month picker) is rendered in the card **body**, one control per row, left-aligned, above the tag row and the table — never in the card's `extra`/head, where it pushes the title aside or wraps the toolbar. The card still frames the page; only the head is reserved for the title and the toolbar. Its value still lives in the address. `ConnectionLogsPage`'s activity start-time range is the reference placement.
- **A form says each thing once, one field per row.** No `Row`/`Col` pairing; no placeholder that repeats its label; no `extra` sentence for an obvious field; no `Divider`/section for name, category or title. A placeholder adds a format, an `extra` states a rule the visitor cannot infer ("leave empty to keep the current password"), and a section is only for a genuinely separate concern (the login-guard block).
- **Every new page or UI element is checked in a browser with a screenshot.** Playwright against the running dev server, capture under `.tmp-runtime/`, and read the image for layout defects — in addition to `probe:render`, never instead of it. `@playwright/test` is not a dependency here and is not to be added without the owner's approval; `docs/probes.md` has the recipe.
- **A check that needs a sign-in uses a throwaway PostgreSQL account, never a password hunt.** Create the account in the base group of the narrowest role that can open the screen, run the check, delete the account on success and on failure alike. Identifiers, the BCrypt hash command and the SQL are in `docs/probes.md`; the seeded administrator's password is not to be searched for.

## Gotchas that govern every task

Two apply everywhere; the rest are per area in [docs/gotchas.md](docs/gotchas.md).

- **`CODE_STANDARDS.md` is a generic template; where the two disagree, this file wins.** It prescribes Tailwind, Vitest/RTL/Playwright/jest-axe, Storybook, `src/features/[feature]/` and **named exports only**. This repository deliberately has almost none of those: styling is antd 6 plus `src/index.css`, verification is Vitest for the pure logic (the suite under `tests/`) plus the `npm run probe*` scripts (no RTL, no browser test runner, no jest-axe), structure is `src/layouts|components|features|pages|utils|config|types|locales|hooks|router` (its `src/features/[feature]/` idea is adopted only in the light form the Structure (core) section describes: domain components under `src/features/<domain>`, no feature `index.ts` public API, pages not folded in yet), and **`export default` is the convention here** — every page and component uses it and `react-refresh` is fine with it. Read its sections on React hooks, TypeScript safety, accessibility and performance as applicable; read its Tailwind and named-export rules as inapplicable, its feature-structure rule only as far as the light `src/features/<domain>` reading goes (no runtime feature barrel — the only barrel a feature has is its type-only `types/index.ts`; besides those the tree's barrels are the table's two `index.ts` files, the kit's and `hooks/table`'s, see Structure (core) — and direct imports everywhere else), and its testing rules only as far as the `tests/` unit tests go. Do not "fix" default exports to named exports: that is a repo-wide diff with no benefit, and the standard is what needs the correction, not the code.
- **The tree is TypeScript, and `tsc` runs before every build.** `npm run build` is `typecheck && vite build`; `tsconfig.json` is `strict` with `noUncheckedIndexedAccess` and `isolatedModules`, `include: ["src"]` and `allowJs: false`. Nothing under `src/` may be `.js`/`.jsx` again — a half-checked JavaScript file sitting in an included tree is the exact state the flag exists to prevent. `npm run typecheck` is the fast loop: it is what fails on a bad import or a forgotten prop long before the bundle does, and it is not a substitute for `npm run probe:render`, which is the only thing that notices markup rendering nothing.
