## Structure

> Moved from AGENTS.md — the core bullets stay in the index.

- `src/utils/tableParams.ts` holds the pure functions that write the address a table's state lives in: `withFilter` — the filter set or removed, and `page` dropped in the same write, because a different list is a different pager and a second write for the reset would be a second request — `withFilterList` — the same rule for the repeated-parameter filters (`?userIds=a&userIds=b`), replacing the whole key and removing it when the list is empty — `listParam` — the read-back half, which keeps only the elements the caller recognises (a fixed whitelist or a uuid test) so a hand-edited address narrows the table rather than answering the endpoint's 400 — and `enumParam` — one of a fixed set, or `null`, so an absent, empty or hand-edited value draws the unfiltered table rather than a `validation_failed`. All run inside event handlers, which is why the unit tests in `tests/utils/tableParams.test.ts` are the only checker that reaches them: every `probe:render` lands before either happens.
- `src/hooks/table/useServerTable.ts` holds the five parameters every server-paged table is read with — `page`, `pageSize`, the applied `search` and the two sort values — **in the address, not in the hook's state**: they are read back with `useSearchParams` on every render and written by the pager, the search box and the sortable headers with `replace: true`, so a reload keeps the view, the address is shareable, and there is no second copy for either to drift away from. Every write is one navigation and one request — a filter change and the page reset it implies are a single address (see `withFilter`), rather than a filter followed by the pager starting over — and a value that says only what its absence says (`page=1`, the default order, an empty search) is removed rather than written, so `/admin/users` and `/admin/users?page=1` are one address with one meaning. `sortFields` is what an incoming `?sortBy=` is judged against (the endpoint's own union, including fields no header offers — `createdAt`, `sortOrder`), so a hand-edited link draws the default order rather than a `validation_failed`. The typed search is the hook's only own state, seeded from the applied one so a reload draws a box showing the search the table is filtered by; `applySearch` compares the *trimmed* value against what the server was last asked, so typing into a box whose text was already sent asks for nothing new, and it is called from the box's own events, which is what makes an emptied box empty the list the moment it *is* empty; `handleTableChange` reads the pager and the sortable headers together because antd reports both through one handler and they behave differently — a new page keeps the order, a new order starts the pages over, and a different page size starts both over; `orderOf` drives the controlled header arrows, because the server always applies an order and a header showing no arrow over rows arriving newest-first would describe a table that does not exist; and `page`/`setPage` are returned for the one non-control case, the step back off a page a delete emptied. What the pages keep is everything that differs: the page-level filters themselves (in the address too, through `withFilter`), bulk selection, busy ids, auto-refresh, column widths and the wording of `showTotal`, which the page hands to `ServerTable` where it is spread in beside the returned `pagination`.
- The rest of the table frame is shared the same way, and each piece exists because six copies of one decision are six places for it to drift. The kit itself lives in `src/components/table/` and is consumed through its `index.ts` — one of the tree's barrels: seven files, eleven consumers outside them, and the three-to-five file paths each of the nine used to carry replaced by one specifier; inside the folder files import each other directly (`ServerTable` reaches `./LoadErrorAlert`), because a barrel that one of its own members imported back would be a cycle. `src/utils/tableResults.ts` turns a page's query into the three values it draws from — the rows, `loadError` (the query's own `error` through `messageForError`, so the reason arrives translated) and `loading` (`isFetching`, not `isPending`: a page turn re-reads with the previous rows still on the table under the spinner). `src/utils/tableCells.tsx` holds the shared column renderers — `idCell` (eight characters and an ellipsis, the whole value on hover), `textCell`, `dashedCell`, `ipCell` (still code-set, used by the accounts table's "IP address" column), `agentCell` (delegates to `UserAgentCell`: `describeUserAgent`'s one line, the raw string in the tooltip) — and the dash rule under them: a value the server could not determine is unknown, not broken. It no longer carries `countryCell` or `networkCell`: those three facts became one two-line cell, and that cell is a component (`features/connection-logs/components/ConnectionNetworkCell.tsx`) because it holds state of its own (the flag that failed to load) and the visit histories draw it too. They are functions rather than components because a column's `render` wants a function, the same reasoning as `hinted`. `src/components/table/LoadErrorAlert.tsx` is the failed read and its retry, which carries the table's own `loading`; `src/components/table/TableSearch.tsx` states the emptied-box rule once for all six (the `allowClear` icon arrives as the same event, so one branch covers both); `src/components/table/ResetColumnWidths.tsx` is the icon-only width reset those six draw in their card header — a `text` button carrying `ColumnWidthOutlined`, its label in the accessible name and in `hinted`'s tooltip (so it stays readable while disabled), with the page passing the already-translated label rather than a key so `probe:i18n` still sees every literal `t('...resetWidths')`. `src/components/table/ServerTable.tsx` is the body those six tables draw: the failed read **in place of** the table (a table sitting under an error banner would be an empty table pretending to be an answer), the resizable header cells, the scroll box (the page's own widths plus the checkbox column when there is one), **the fit** (see [shell-and-layout.md](shell-and-layout.md)), and the pager (the hook's `page`/`pageSize`/`pageSizeOptions`, the endpoint's `total` and the page's own `showTotal`) — so a page hands over its columns, its page of rows and the three values `tableResults` returned, and keeps the columns themselves, the widths, the query, the filters, the toolbar and the selection state. `src/components/table/RowActions.tsx` is a row's action cluster: one icon-only `text` button of the small size per action, each wrapped in `hinted` — an icon has no text of its own, so the tooltip is the button's whole accessible name, and `hinted` is what lets that tooltip open over a disabled button — four pixels apart in one `Space`; the page keeps which actions a row has, in what order, what each says and whether this row may press it. The four hooks the frame runs on live together in `src/hooks/table/` and are consumed through its `index.ts`, the other half of that pair, so a page names them once. `src/hooks/table/useRowAction.ts` is the one row action the administrator tables share — one id in flight, so the acting row's buttons spin while its neighbours stay clickable; the write handed in as a zero-argument closure (the endpoints disagree about what travels beside the id — a group's block is a `patch`, a stream's start is nothing at all — and the caller is the only one that knows which), so the token and the request itself belong to the feature's `hooks/mutations.ts`; the success text resolved from the answer's code; and a **re-read** afterwards, because a transition changes what the server considers the row to be. It is constructed with the page's own facts — `refetch`, plus `rows`/`page`/`setPage` where there is a pager — because deletion needs them: `confirmDelete(row, question)` owns the one question that is asked first (a `RowDeleteQuestion` carrying this page's own three keys and the write), and on success it steps back a page when the deleted row was the last of a later page rather than re-reading a page the server would answer empty. `src/hooks/table/useBulkAction.ts` is the selection the eight bulk tables act on and the one run that acts on it: the ids the **current page** has marked, pruned on every answer to the rows still drawn (returning the same array when nothing moved is the termination condition that keeps a re-read after every action from becoming a loop); one run in flight; the answer read out loud — a toast only when every row landed **and nothing was cleared**, and a dialog when at least one row was refused or a successful row carried a warning, because a green toast over a change that cost a setting would be the one place that fact never appeared. The dialog's title distinguishes a refusal from a warning (`partialTitleKey`, with an optional `warningsTitleKey`), its lines are grouped by code with a count because thirty rows refused for one reason are one sentence, and they are drawn by `src/utils/bulkResultList.tsx` — a function rather than a component for the same reason `tableCells` is one, because its only call site is a `.ts` hook's `content`, which wants a node. That list draws refusals and warnings under separate headings, and only when both exist; warnings never count as failures. The run itself re-reads rather than patches and clears the selection because the run is over, not because the rows are gone — only deletion guarantees that. The page keeps what differs: which endpoint an action names, the menu that chooses it, the dialogs that ask first, and the "may this operator change anything here" question, which is a fact about the page rather than about the selection. Its optional second argument closes a dialog the run came out of: the move dialog closes on any answer, because once the answer has arrived there is nothing left to ask. None of the cells is reachable from `probe:render`, which lands in the state before the first answer; `tableResults` is covered by its own unit test and the two display helpers behind the cells stay asserted as functions.
- `src/utils/tableWidths.ts` holds the width rules the tables share, and they are in `utils` rather than beside the frame because they are numbers and a sum rather than a component: `MIN_COLUMN_WIDTH` / `MAX_COLUMN_WIDTH` (the floor and the ceiling of a dragged column, read by the hook that drags it and by the frame that squeezes it), `actionsColumnWidth` (the width an actions column needs for the buttons it holds — `count * 24 + (count - 1) * 4 + 32`, from antd's own small icon button, the gap `RowActions` puts between two of them and the cell's padding), and `distributeWidths` (the room divided between the columns, with the floor). The last two are unit-tested in `tests/utils/tableWidths.test.ts`; the first is read from three places at once, which is why it lives in one.
