## Structure

> Moved from AGENTS.md — the core bullets stay in the index.

- `src/pages/account/SessionsPage.tsx` is the visit history: a read-only antd `Table` on `getSessionHistory` (`src/features/sessions/api.ts`), reached from `nav.items.sessions`, which sits in the `account` group of **all three** roles so `/client|reseller|admin/sessions` all exist. Its types are `src/features/sessions/types/SessionVisit.ts` and `SessionHistoryResponse.ts`. Three things it owns rather than inherits: it reads `getProfile()` once on mount to print `visitedAt` in the **account's** time zone (the profile page promises "Dates and times are shown in this zone", and a history page answering in the browser's zone would be the one place that promise visibly failed); it renders `—` rather than an error for a `null` geo field, because a loopback address or a missing `.mmdb` is unknown, not broken; and it puts the heading, the search and the table in **one** `Card`, because the two cards and the sentence between them were a box around a single subject — the search replaced the sentence. It also owns the column widths (resizable, remembered — see [tables.md](tables.md)) and draws its two content columns through the shared `ConnectionNetworkCell` and `agentCell`, while the table body around them — the resizer cells, the scroll box and the pager — is `src/components/table/ServerTable.tsx`, the same one the other five server-paged tables draw. `npm run probe:render` renders it with an explicit `sectionKey` — the shared `render` helper passes no props and would measure `t(undefined)` — and every render of it lands in the state *before* the first answer arrives, which is why the two helpers it calls (`countryName`, `describeUserAgent`) are asserted as functions below.
- **Its paging, search and sort are all server side, and that is forced by `total`.** `getSessionHistory` sends `page`, `pageSize`, `search`, `sortBy` and `sortOrder` as query parameters (built with `URLSearchParams`, so a `+` or an `&` in a user agent is searched for rather than reinterpreted). Filtering or ordering in the browser would apply to the page on screen while the pager still counted everything, which is the same lie at both ends. Consequences the page has to keep: any change to the five resets to page 1 (`handleTableChange` distinguishes `extra.action === 'paginate'` from a sort), the page size picker offers 10/20/50/100/500/1000 — every server-paged list accepts up to 1000 and `1001` comes back `validation_failed` — and the two sortable headers are **controlled** (`orderOf`) rather than left to antd, because the server always applies an order and a header showing no arrow over rows arriving newest-first would describe a table that does not exist. Only "When" and "Network" are sortable, and "Network" sorts by `ip`: those are the two stored facts (`visitedAt` and `client_address`), the geo fields beside the address are resolved while a page is built, and `SessionSortField` on the backend records why they are not offered.
- **Every column has a width and the table is `table-layout: fixed`, which is the whole answer to a long provider name.** A column with no width of its own grows to fit its widest cell, so an organisation name — whatever the registry called the company, sixty characters and no end — would widen the table and push everything after it sideways. The widths are 300/440/400 and they are `DEFAULT_COLUMN_WIDTHS`, a *starting point* rather than the answer (see the `useColumnWidths` paragraphs below); that is **1140**, and it is this table's own invariant rather than the 1190 the administration's tables reach, because this page has no selection column and no actions column. The network and user-agent cells truncate through `ellipsis: { showTitle: false }` and hand the uncut value to an antd `Tooltip`, and `overflow-x: auto` lives on `.ant-table-content` so any overflow scrolls inside the card instead of moving the page. antd 6's tooltip takes `styles.container`, not `styles.body`. `npm run probe:render` asserts the `<colgroup>` widths, the fixed layout, the scroll box and the search box — none of which typecheck, lint or the build would notice missing.
- **The visitor may move those widths, and `scroll.x` follows them.** `tableWidth` is the sum of whatever the three currently are, not a constant; the widths live in `useState`, are read from and written to `localStorage` under `fluxy.sessions.columnWidths.v2` (the `.v2` is the round-3 merged-column set), and every path back to `DEFAULT_COLUMN_WIDTHS` (the width-reset control in the card's `extra`, double-click on a handle, `Home` on a focused handle) removes the key so a future default change still applies. **The hook is also told which table it is serving.** Its state is kept as `{ storageKey, widths }` rather than `widths` alone, and a changed `storageKey` re-reads the stored arrangement *during render* (React's documented prop-change adjustment) instead of in an effect: the connection log's two modes are two routes into one component, so React keeps the instance and only changes its props, and a `useState` initializer runs once. Without the pairing the second table was handed the first one's numbers - five stored widths read into a seven-column table, then persisted under the new key, which is why the activity table kept the wrong look after a reload. Reading it is one `try` and not a `typeof` guard: the probes render this under Node, where `localStorage` is not declared at all and reaching for it is a `ReferenceError`, and the compiler would be entitled to call the `typeof` unnecessary. The floor of 90 is a handle width rather than a taste — a column narrowed to nothing takes its own resize handle off the edge of the screen with it. It is the same 90 the *squeezed* column stops at, for a different reason: a column the screen made narrower has to keep the name of the column in it (see the fit in `ServerTable`). Dragging writes from the width the drag *began* at (an accumulator compounds the delta and the column runs away), listeners live on `window` rather than on the handle (a drag outlives the ten pixels it started on) and are torn down through a ref so that leaving the page mid-drag still ends it; text selection and the resize cursor are held by a class on `body` rather than by `preventDefault()` on `pointerdown`, because whether cancelling that suppresses the compatibility `mousedown` — and with it the `click`, the double-click and the focus — is left to the implementation rather than promised. Keyboard: `ArrowLeft`/`ArrowRight` by 16, `shift` for 64.
- **`ResizableHeaderCell` and the antd sorter both want the same header cell, and `useSorter` wins.** The handle has to be a *sibling* of the header's own content rather than a child of it, because antd wraps a sortable title in a `<button>` and a focusable span inside a button that sorts would sort as well as resize — so the only way to place it is `components={{ header: { cell: ResizableHeaderCell } }}` — set once now, in `ServerTable` — with the per-column data (key, width, label, handlers) handed over by `onHeaderCell`. What is handed over is then **dismantled, not forwarded**: `antd/es/table/hooks/useSorter.js` does not add to what `onHeaderCell` returned, it overwrites it — `aria-label` becomes the column title (line 184), `tabIndex` becomes 0 (line 186), `className` and `title` merge, `onClick` is replaced by the sorter and `onKeyDown` is wrapped so that **Enter sorts before the original handler is called at all**. Getting this wrong is silent: the first version took the cell's `tabIndex` and `aria-label` for its handle, which made the header unfocusable and keyboard sorting impossible while the markup stayed perfectly well formed, and named two of its five handles "When" and "IP address" instead of "Resize the … column". So the cell keeps its `tabIndex`, `aria-label`, click and key handler; the handle gets the separator's `role`, orientation and bounds, a hardcoded `tabIndex={0}`, its own `resizeLabel` channel, and **no `Enter`** — antd has already wrapped that handler and would turn the sort arrow at the same time as the width. A click on the handle is stopped by the *cell*, in the capture phase, before it reaches either the handle or the sorter — a sortable header sorts on any click that bubbles to it, and stopping it on the way down also keeps the handle free of a click listener that a linter (or a reader) would parse as an interaction no keyboard can perform. Both halves are asserted by `probe:render`, which is the only thing that can see them: typecheck is satisfied either way. The component is defined at module scope deliberately — a component type created inside the page would be a new type on every repaint, React would unmount the handle mid-drag and the pointer would go with it.
- **The two display columns are built from helpers and one shared cell, not from the raw server fields.** The network column is now **one cell** (`features/connection-logs/components/ConnectionNetworkCell.tsx`) holding what were three columns — the country's flag and the address on its first line, the provider on its second — drawn by the same component the connection logs use, on the owner's round-3 correction. It carries **no filter callbacks here**: this endpoint resolves its geo fields while a page is built and takes no `ip`/`country`/`isp` parameter, so a clickable cell would be a control that writes nothing. The user-agent cell shows `Chrome 140 (Windows 10, x64)` from `describeUserAgent` and keeps the untouched string in the tooltip, so twenty rows are one scannable line each and the whole client is still one hover away. `null` from `describeUserAgent` means "show it as it is", which is what `curl`, a bot and a browser this build has never heard of get. Two limits it does not pretend to fix: Chrome froze the UA at `Windows NT 10.0`, so **Windows 11 reads as Windows 10** to every parser in existence, and the Mac UA is frozen at `Intel Mac OS X`, so an Apple Silicon Mac gets no architecture rather than a wrong one. The parser is **`ua-parser-js@^1.0.41`, MIT — the 2.x line is AGPL-3.0-or-later and must not be pulled in**, which is why the caret cannot cross a major; `bowser` (no CPU architecture) and `device-detector-js` (LGPL) were the alternatives and are worse fits. It costs ~20 kB minified, and its answers are memoised per string along with the `Intl.DateTimeFormat`s and `Intl.DisplayNames` instances, because the table repaints on every step of a drag and a hundred fresh formatters is 8.6 ms of a 16 ms frame.
- **Dates follow the account's time zone and the *page's* language.** The zone is read once from `getProfile()` because the profile page promises "Dates and times are shown in this zone"; the language is `i18n.resolvedLanguage ?? i18n.language` (not `language`, which still reports a language nobody is being shown once its bundle is missing) because this application has a language switcher and a date in one language beside a country name in another is that switcher visibly failing halfway down a row — the same reason the country column uses it.
- `src/pages/account/ActiveSessionsPage.tsx` is the active sessions page: **one card per sign-in that is still running**, each with the way to end it — the opposite question to the history above, and the opposite shape: no table, no paging, a grid of cards that keeps the way to stop a session inside the session it describes. It is framed by a single `Card` whose `title` is `t(sectionKey)` (so it says what the sidebar says, like the history — there is no `activeSessions.title` key to drift from `nav.items.activeSessions`) and whose `extra` holds the "end all but this one" button — the same single-frame reasoning the history's card gives: a heading floating beside a box of content is a second box around one subject. Reached from `nav.items.activeSessions` (`LaptopOutlined`), which sits in the `account` group of **all three** roles, so `/client|reseller|admin/sessions/active` all exist. Types are `src/features/sessions/types/ActiveSession.ts` and `ActiveSessionList.ts`; the endpoints are `getActiveSessions` / `revokeActiveSession` / `revokeOtherActiveSessions` in `src/features/sessions/api.ts`, and `src/utils/http.ts` grew a `DELETE` branch for them (`RawOptions.method` is `'GET' | 'POST' | 'DELETE'`). Three rules come from the server rather than duplicating it: the grouping into one card per session is the server's (the page draws exactly what the endpoint returns, and `isCurrent` marks the card the page is being read with); the current card's button is disabled because the API would answer `cannot_revoke_current` for that id anyway, so the disabled button is the UI telling the truth the API would tell; and the bulk button is disabled while there is nothing to end. The two revokes are not the same update: a **single** revoke takes its card out of the `['sessions', 'active']` cache with `setQueryData` — a session is exactly one card here, so nothing else on any page is outdated by knowing it — while the **bulk** revoke re-reads with `refetch()`, because the endpoint reports a count and rebuilding the cards from a number would mean deciding in the browser which card is which when the server already knows. Its four API codes (`session_revoked`, `other_sessions_revoked`, `cannot_revoke_current`, `session_not_found`) are translated in `messages.api` of both locales like every other. `npm run probe:render` renders it with an explicit `sectionKey="nav.items.activeSessions"` — the shared `render` helper passes no props, the same reason the history needs its own — and asserts that the heading, the bulk action and the spinner are drawn **before any cards arrive**, because every render in the probe lands in the state before the first answer, which is exactly where a card row must not appear yet.
- `src/pages/admin/AdminSessionsPage.tsx` is the installation's visit history, reached from `nav.items.adminSessions` at `user-sessions` in the admin-only `users` group. It is the account's own history answered over every account the operator may read, so it keeps that page's server-side paging, search, filtering and sorting — a filter applied in the browser would narrow one page while `total` still counted everything — and adds an account column and one action. **Its own five columns are `user`, `when`, `network`, `agent`, `actions`; the widths are 170/250/340/350/120 = 1230**, which is this table's own total: unlike the account and group tables beside it in the same rail, it has no selection column, so the five are the whole 1230 the sidebar leaves room for and the action cell is still exactly as wide as its one button. Since the owner's round-3 correction the address, country and provider are **one** network cell (the same `ConnectionNetworkCell` the connection log draws), which is why the column count is five rather than seven; the page passes **no filter callbacks**, because `GET /admin/sessions` resolves its geo fields while a page is built and takes no `ip`/`country`/`isp` parameter, so a clickable cell would write nothing. The network header keeps the sorter and sorts by `ip` (the one geo field the endpoint can order by) through `sortFieldOf`, rather than losing the feature with the merged column. Ending a session is an act on a chain, not on a row — several rows of one sign-in share a `sessionId` and the DELETE takes that — so the table re-reads after every revoke instead of dropping the clicked row, and the button is drawn disabled with its reason for a row whose session has ended and for the rows of the session the page is being read with (`cannot_revoke_current`). `?userId=` is the account filter and lives in the address, because the accounts table's last-visit cell is what sends a visitor here; a filter kept in `useState` would be gone by the time the page mounted. Storage key `fluxy.adminSessions.columnWidths.v2`; `probe:render` pins the five widths in order, the five handles, the sortable network header, and the arriving `userId` drawn in the filter.
- `src/pages/admin/UsersPage.tsx` is the admin's account table - heading, toolbar and table in one `Card` (the same single-frame reasoning as the history), reached from `nav.items.usersManage` in the admin-only `users` group, **headed by `users.listTitle` rather than by `sectionKey`**: the page must not repeat in its own card what the menu already says beside it, so the item `Управление`/`Manage users` names how the visitor got there while the card says `Пользователи`/`Users`. The prop is accepted and deliberately unread the same way `UserFormPage`'s is (the comment above `users.listTitle` says why), and the group keeps its own `Пользователи` name on the owner's call — sharing a word with its category is accepted, echoing the clicked item is not. **Paging, search, filtering and sorting are server side, for the reason the history's are: `total`.** A filter or order applied in the browser would narrow the page on screen while the pager still counted everything, so every change goes back to `GET /admin/users`, any change that is not a page turn resets to page 1, and the six sortable headers are controlled. The column keys *are* the server's sort fields (`username`, `email`, `group`, `status`, `lastSeenAt`, `ip` — hence the `lastSeenAt` locale key, so a header click hands its own key to `getUsers` with no mapping table to get wrong); `id` and `actions` never produce a sorter event. `DEFAULT_COLUMN_WIDTHS` is 100/180/160/150/150/180/130/140 = **1190px**, and the selection column takes it to the same **1230** on purpose: that total is what must fit beside the sidebar on one Full HD screen so the action buttons at the far right stay inside the viewport, and the three content columns are narrow *because* their cells truncate through `TruncatedCell` into tooltips — the id shows eight characters with the full GUID on hover, widening one costs visible table room. The actions column is the exception to "a number in the list": it is exactly as wide as the four buttons a row draws (`actionsColumnWidth`), and the room that frees goes to the username — the column this table is read by. It shares `ResizableHeaderCell` / `TruncatedCell` / `useColumnWidths` / `hinted` with the history and with the group table (storage key `fluxy.users.columnWidths`), and the rest of the table frame (`tableResults` / `tableCells` / `TableSearch` / `LoadErrorAlert` / `useRowAction` / `useBulkAction` / `ServerTable` / `RowActions` — see [tables.md](tables.md)) with every other table. **The two filters live in the address, not in the page's state**: `?groupId=` and `?status=` are read with `useSearchParams`, narrowed by `enumParam` where they name an enum, and written back by their `Select`s through `withFilter` with `replace: true`. The group one has to be there because the groups table's "show accounts" button sends a visitor here with a filter already chosen, and a filter kept in `useState` would be gone by the time this page mounted — the button would land on the unfiltered list looking like it had done nothing; the status follows it for every reason the five `useServerTable` parameters do. One source rather than two also makes the address shareable and a reload keep the filter, with no effect anywhere keeping the two in step; `replace` rather than push because changing a filter is a change to what is being looked at, not a step worth a history entry; and `withFilter` drops `page` in the same write, so a filter change is one navigation and one request rather than a filter followed by the pager starting over. The role filter was **replaced** by the group filter when the group arrived: a row no longer has a role of its own, the group is what the server joins to answer one, and a filter over a field that is no longer in the query would be a control the endpoint silently ignores. The group options are fetched in a **separate query** from the accounts list (`useAllUserGroups`), because they need `viewUserGroups` while the account rows need the per-role `view*` grants - sharing one call would fail the whole page with `403 permission_denied` for an administrator who may read accounts but not groups, while as it is that visitor's filter simply offers nothing to pick, which is the truth. Status draws as a `Tag` from `STATUS_COLOR` — three descriptions, not a ramp (`UserStatus` is not an ordered scale) — over the **effective** status the server reports, the more restrictive of the account's own and its group's (`combineStatus` in `src/features/users/userStatus.ts`); last visit and address come from the endpoint's `lastSeenAt`/`lastIp` (its freshest refresh token), printed by `formatTimestamp` in the reading account's time zone, with `—` for an account that has never signed in. Only deletion asks first (`modal.confirm` — the one irreversible move); every other action is a request and a **re-read**, because a transition changes what the server considers the row to be and the page draws what it is told. Block and delete are disabled on the signed-in account's own row with the `selfProtected` tooltip — the same "the UI tells the truth the API would tell" rule the active sessions page follows — and an account blocked only by its group answers a block attempt with `user_blocked_by_group`. `npm run probe:render` renders it with an explicit `sectionKey` and asserts the heading (the page's own title, with the menu item's name absent), the toolbar/table before any row, the eight widths *in order*, eight named handles, a sortable header keeping its own access, the group filter and the table's own state (search, status, order) arriving from the address, and both menu items loading the real pages.
- `src/pages/admin/UserFormPage.tsx` is the add **and** edit form — one component behind `users/add` (a menu item) and `users/:id` (an `extra` route with no menu item, reached only by choosing a row; a second `lazy()` over the same module makes a move between the two remount rather than carry a half-filled form across). The heading comes from whether there is an `id` (`users.addTitle`/`users.editTitle`), not from `sectionKey` — the prop is accepted and deliberately unread, and the comment above `addTitle` in the locales says why. Three rules on the page are the server's: the **id is static text** — a `Form.Item` with no `name`, so layout only rather than a field, `copyable`, and never in the body because the path carries it; a **blank password means "keep the current one"** — required only on add, sent as `null` on PATCH, with one validator that short-circuits blank before judging length and complexity (an `async-validator` `min` on an empty string is not a behaviour to bet "keep" against); `timeZone` travels as `''` to clear on PATCH (`null` there would mean "keep") and as `null` on create for "follow the browser", with `AutoTimeZone` as the sentinel the `Select` holds. Edit mode **fetches by URL and draws a spinner until the answer arrives** — `probe:render` lands in exactly that state and asserts it, because a form painted from whatever the previous screen happened to hold would edit the wrong row after a reload. The guard comes from the shared `LoginGuardFields` with **no `fillCurrent`** (the caller's network is the wrong network for an account that is not theirs) and with `protectionEnabled` passed down as the floor beneath `Form.useWatch`'s undefined-first answer. Success navigates to `${area}/users` — `area` from `areaForRole(session.role)`, since `navigate('..')` from a child of the area pops to `/admin`, not to the list. Two attributes of this form exist for the browser's password generator and were found by rendering, not by reading: the `<Form>` carries `autoComplete="on"` (antd 6 renders no attribute at all without it, and `AuthCard` passes exactly this to every guest form — this page renders its own `Form` and had none), and the password input carries `new-password`; together they are the pair the registration form states, which is the form that demonstrably triggers the "generate a strong password" offer, while the two identity fields keep their own `off` so the administrator's saved username is never offered into somebody else's account. One falsehood survives here and cannot be removed from this side: rc-select hardcodes `new-password` on every hidden combobox input (`autoComplete || 'new-password'` in `@rc-component/select` `SelectInput/Input.js`, and no prop reaches that input — the `Select`'s own `autoComplete` lands on the wrapper div), so role, status, time zone and the two guard selects each draw an input claiming "new password"; they are `type="text"` combobox inputs, never password-type fields, which is not what a password manager counts when it classifies a form, and `probe:render` pins that fact rather than trusting it. The profile page's change-password form carries the same `on` for the same reason. An explicit generate button sits under the field in both modes: `generatePassword` in `src/features/auth/policy.ts` — `GENERATED_PASSWORD_LENGTH` letters and digits carrying one of each class the complexity rule counts, drawn from `crypto.getRandomValues` with rejection sampling and a string-expressed Fisher-Yates, living beside the rule it satisfies so a rule that ever grows breaks the generator in the same file — fills the field and opens its controlled eye at once, because the value is meant to be handed to the new account's owner and a masked one cannot be handed over. It is also the answer to the browser offer being only a heuristic: absent in some browsers, and it may file the value into the administrator's own vault instead of saying it out loud. `probe:render` calls the generator directly (no render reaches it) and asserts the label carries the same constant the function obeys.
- `src/pages/admin/UserGroupsPage.tsx` is the admin's group table, the accounts table's twin by design and its own page in every other respect. Reached from `nav.items.userGroups` in the admin-only `users` group; headed by `userGroups.listTitle` ("User groups"/"Группы пользователей") rather than by `sectionKey`, so the card does not echo the menu item's own name ("Groups"/"Группы") back at the visitor. **Six columns, sortable on four**: `id`, `name`, `role`, `status`, `permissionsCount`, `actions`, with `name`/`role`/`status`/`permissionsCount` carrying a sorter and `id`/`actions` deliberately not — the server's `UserGroupSortField` has no member for either, and a header that offered one would answer with `validation_failed`. `DEFAULT_COLUMN_WIDTHS` is 110/420/180/200/140/140 = **1190px**, and the selection column takes it to the same **1230** total as the accounts table on purpose: the two sit under one sidebar, and a visitor who can see one whole should be able to see the other. The name column is 420 — the widest thing here — because a group name is the one thing on this page nobody truncates into a tooltip, and the identifier gives the room back by staying at 110; the actions column is the exception to "a number in the list", being exactly as wide as the four buttons a row draws (`actionsColumnWidth`), with the room that frees going to the name. Storage key `fluxy.userGroups.columnWidths`. The row actions are icons with tooltips: edit, **show accounts**, block/unblock, delete. "Show accounts" is the one that reads rather than writes, so it sits with the row actions and not in the toolbar — which group's members to look at is a decision made *about this row*, and a toolbar button would have to be told which one by a selection the table does not have. It navigates to `${area}/users?groupId=...` and that is the whole of the interaction: no state to hand over, and the page that comes out can be reloaded or sent to somebody else and still show the same list. Block and unblock go through `PATCH {status}` — there is no dedicated endpoint — and deletion is confirmed with `modal.confirm`, the one irreversible move. Base groups get disabled block/unblock/delete buttons with the `baseImmutable`/`baseUndeletable` tooltips, but **"show accounts" is never disabled**: it is a question about the rows that belong here, and a base group holds as many of them as any other.
- `src/pages/admin/UserGroupFormPage.tsx` is the add **and** edit form, one component behind `user-groups/add` and `user-groups/{id}` — **both `extra` routes with no menu item**, unlike the accounts form whose add address is a menu entry of its own. The rail offers the table alone and both forms are reached from buttons on it, so a third entry saying "add a group" would be a page whose only content is the button that brought you here. The heading comes from whether there is an `id`, not from `sectionKey`, exactly as on the accounts form. Three rules the server owns, none of them this form's to invent: **a base group accepts `name` and nothing else** — the role, status and permission controls are drawn (a control that vanishes teaches nothing about why it was there) and disabled, with one sentence at the top naming the whole row rather than any one field, and the submit body carries only `{ name }` rather than three values the server would answer `409 user_group_immutable` for; **a permission the role does not own cannot be granted**, so `permissionsForRole` decides which checkboxes appear before anything is sent and a Client group is offered a note instead of ten boxes that would all be thrown away, with the set pruned when the level changes *and* filtered again at submit for the case the effect cannot see; and **`permissions: []` clears where an absent `permissions` does not**, so the form always sends the set it holds rather than omitting it when nothing is ticked — otherwise unticking the last box would answer with a request that changed nothing while looking like it had worked. Under the checkboxes sit **"Select all" and "Clear"**, both acting on `offered` and never on the whole catalog (a grant the level does not own would be dropped by the prune a frame later, and a button whose effect is partly undone is a button that lies), both disabled on a base group, and both gone in the branch that draws the note — "select all" over nothing is a control that cannot be obeyed. The level starts at `Client` and status at `Registered`, the same least-privilege reasoning as the accounts form's default group.
- `src/features/user-groups/permissions.ts` holds `ALL_PERMISSIONS`, `OWNER` and `permissionsForRole` — the frontend's copy of which permissions each role owns, mirroring `UserPermissionCatalog` on the backend. It is what makes "a Client group has no boxes" a decision taken *before* a request rather than a refusal explained after one. All twenty-eight permissions are owned by `Admin` today, so `permissionsForRole` answers `[]` for Client and Reseller; a permission added on the server must be added here and to the two locale `permissions.*` blocks, or its checkbox label degrades to the raw key. `probe:render` calls it directly — no render reaches it, since the add form opens at `Client` — and asserts Admin gets all of them while the other two get none, which is the precondition that keeps the bulk buttons from being dead code everywhere. **The last five pairs are the content resources' grants** — `viewStreams`/`editStreams`, `viewAudioStreams`/`editAudioStreams`, `viewVideoOnDemand`/`editVideoOnDemand`, `viewSeries`/`editSeries` and `viewEpgSources`/`editEpgSources` — and they are deliberately **not** the same pair: a group that may read the video streams may not read the audio ones, and a group that may read the catalogue may change neither.
- `src/features/users/userStatus.ts` holds `combineStatus` — the frontend's copy of `UserStatusComposition.Combine`. An account's **effective** status is the most restrictive of its own and its group's (`Blocked` > `Unregistered` > `Registered`), and it is what the accounts list shows. The local `RESTRICTIVENESS` map exists because the `UserStatus` enum's *numbers* are in the wrong order for this question (`Unregistered=0, Registered=1, Blocked=2`) — comparing them directly would rank an unregistered account above a registered one. The map is written out rather than derived for exactly that reason: a numeric comparison here would compile, pass a glance, and be wrong.
- `src/features/profile/loginGuardForm.ts` holds `GuardFieldValues`, `guardToFormValues` and `formValuesToGuard` — extracted out of `LoginGuardFields.tsx` because both flows (the profile card and this form) share them, and `react-refresh/only-export-components` flags non-component exports in a component's file. One conversion point so the two call sites cannot drift; the component file now exports only its component.

- **The credit balance lives on three surfaces, and each states one of its rules.** The
  reseller's own header chip (`AccountHeader`, `.layout-shell__credits`) draws the value from
  the shared `['profile']` query and only for `session.role === 'Reseller'` - the two other
  roles draw nothing, not a zero - and it is a `span`, not a control: the balance is a
  statement. Its own class is what keeps it out of the `≤768px` rule that hides the username,
  so the number survives the narrow bar. The accounts table draws it as a **second line inside
  the group cell** (`features/users/components/UserGroupCell.tsx`) - one fact with the group it
  belongs to, not a ninth column, which is what keeps the pinned 1190 sum - and only when the
  row's role is `Reseller`; `0` is drawn and any other role draws nothing, not a dash. The form
  (`UserFormPage`) has one `InputNumber` (`min={0}`, `precision={0}`, 200 px wide) directly
  after the group select: enabled only while the watched group's role is `Reseller`, disabled
  with `users.creditsHint` otherwise, keeping the typed value in the store while leaving it out
  of the body, and its validator is `isCreditAmount` in `features/users/creditsField.ts`
  (`validation.creditsInvalid`). The server keys its own refusal `credits`, which is the field's
  name.

- **`features/credit-logs/` is the balance's audit trail** (`GET`/`DELETE /admin/credit-logs`,
  read behind `viewResellers`, wiped behind `editResellers`). `layout.ts` holds the five column
  keys and widths (170/110/170/540/200 = **1190**), the storage key
  `fluxy.creditLogs.columnWidths`, and the one key-to-field mapping the table needs: the
  "Credits" header is keyed `credits` while the request says `sortBy=amount`. `creditLogActor.ts`
  is the "Issued by" rule (an issuer on the row wins, so an admin-panel decrease names the admin;
  a negative row with no issuer names the reseller, which is the future reseller-spent row; a
  zero-or-positive row with no issuer is an em dash, the deleted-issuer case) and the tone
  (`amount > 0` green, zero and negatives red), both unit-tested. The page is
  `pages/admin/CreditLogsPage.tsx`: one `page-card` with a search / reseller picker / width reset
  / danger clear in the head, the `RangePicker` on its own row in the body (`dateFrom`/`dateTo`,
  inclusive, account-zone days via the shared `utils/dateRange.ts`), a closable range tag and a
  closable reseller tag, and the reseller cell navigating to that reseller's edit form
  (`${area}/users/${resellerId}`, the accounts table's own edit target) rather than filtering
  again. Clear-all is gated on `editResellers` and never on data state, behind one
  `modal.confirm` that names the whole table. `features/connection-logs/startRange.ts` is now a
  thin wrapper over `utils/dateRange.ts` - the account-zone arithmetic the two tables share.

- **`features/user-logs/` is the account audit trail** (`GET`/`DELETE /admin/user-logs`, both
  behind the single `viewUserLogs` grant - there is no `editUserLogs`, because an operator never
  writes a row: a row is written by the flow it records, and the wipe destroys the same
  evidence the read shows). `layout.ts` holds the five column keys and widths
  (210/170/400/220/190 = **1190**), the storage key `fluxy.userLogs.columnWidths`, and
  `sortFieldOf`, which maps only `recordType` to itself and every other key to `createdAt`
  (the endpoint's own two sort fields). `recordTone.ts` is the tag colour - `isSuccess` green
  (`'success'`), a refusal red (`'error'`) - typed to those two `Tag` status names, because
  `'danger'` is a `Typography.Text` type and on a `Tag` it is an unknown string with no colour
  class at all (the credit log's `creditLogTone` is the opposite case: it feeds
  `Typography.Text type`). `recordTypes.ts` is the ten-wire vocabulary as a runtime list,
  because `types/` is type-only and both the filter picker and the address read-back build
  from it. `types/` carries `UserLogRow` (note: **no user-agent field** - the server stores one
  and does not return it) and the page. The page is `pages/admin/UserLogsPage.tsx`: one
  `page-card user-logs-card` (the second class is the >1200px head rule - see
  [shell-and-layout.md](shell-and-layout.md)) with auto-refresh (OFF by default, a 30s
  `setInterval` through a ref, never `refetchInterval`) /
  search / three `mode="multiple"` pickers / width reset / danger clear in the head, the
  `RangePicker` on its own row in the body, then the tag row and the table. The three repeated
  filters are written with `withFilterList` and read back with `listParam` (a uuid test for the
  two account pickers, the record-type whitelist for the third), because a bad element is a 400
  under that parameter's name. `networkFilters.ts` holds the three network filter names
  (`ip`/`country`/`isp`) and their read-back; note the parameter is `country` while the response
  field is `countryCode`. The username cell links to `${area}/users/${accountId}` only when
  the row names an account; otherwise it is plain text carrying the typed identifier. The
  network cell is the connection log's `ConnectionNetworkCell` with **`onFilter={choose}`**: the
  endpoint now takes the connection log's three network parameters, so each fact is a click that
  writes its own filter and drops `page` in the same write. The refusal
  (`profile answered and the grant is absent`) draws the card, its title and one `Alert` as the
  only body - no toolbar, no filters, no table - and the logs query is `enabled: false` there;
  an unanswered profile draws the ordinary shell, which is the state every `probe:render`
  assertion lands in.
