## Structure

> Moved from AGENTS.md — the core bullets stay in the index.

- `src/features/subscriptions/` is the subscriptions domain, and its root modules are the shape the review forced them into. `api.ts` holds the endpoints (`getSubscriptions`, `getSubscription`, `createSubscription`, `updateSubscription`, `deleteSubscription`, `generatePlaylistId`, `bulkSubscriptions` and **`patchSubscription`** — the single-field write the service strips use, because the list deliberately omits whitelists, lock flags and bouquets and a strip that reconstructed a whole row would clear them). `subscriptionBody.ts` is the pure `SubscriptionValues`/`toCreateBody`/`toUpdateBody` mapping, unit-tested in `tests/features/subscriptions/subscriptionBody.test.ts`: the update body derives `clearTariffPlan`/`clearMaxConnections` **from the values** (`values.tariffPlanId == null`) rather than from flags a form could forget, and writes `?? null`, because a cleared single `Select` puts `undefined` — a key with an undefined value that `JSON.stringify` drops — into the form store, and the coercion at the form boundary (`currentValues()`) plus the loose check here is what makes "cleared" and "kept" two different requests again. `prolongPreview.ts` is the confirmation dialog's preview of the prolongation — a **UTC-mode** mirror of the server's `ProlongedExpiry` (`dayjs.utc` for the stored expiry and the floor `now`, calendar adds clamping in UTC exactly like `DateTimeOffset.AddMonths`), unit-tested under pinned non-UTC zones because local-mode dayjs arithmetic diverges on month-end clamps and DST; the data comes from the list row's `tariffPlanDurationValue`/`tariffPlanDurationUnit`, so no second request opens the dialog. `subscriptionRules.ts` mirrors the server's limits (`PLAYLIST_ID_LENGTH`, `WHITELIST_MAX_ENTRIES`, `isPlaylistId`, `isMac`, `hasService`, `hasOutputFormat`), `subscriptionOptions.ts` holds the status and output-format arrays — runtime values at the feature root because `types/` and its barrel are type-only — and `types/` carries the six response contracts. `components/SubscriptionSubrows.tsx` and `components/SubscriptionsListContext.ts` draw the strips under each row.
- `src/pages/admin/SubscriptionsPage.tsx` is the subscriptions table — the fifth of the tables with a bulk toolbar, headed by `subscriptions.listTitle` like the other admin tables. Five columns (`name`, `expiry`, `activeConnections`, `connections`, `creator`, `actions`) - six, after the owner added the live count - summing to **1190** with the selection column taking them to the same **1230** every table here reaches. **`activeConnections` and `connections` are the same width** (one `CONNECTIONS_COLUMN_WIDTH` feeding both): the owner reads them as one sentence, "3 of 5", and two columns that differ by fourteen pixels make a sentence out of two numbers meant to be one. `activeConnections` is the **count of open sessions**, added to the list row by one grouped `IN` query per page (`SubscriptionListItem.ActiveConnectionCount`; `ended_at IS NULL` is the predicate the connection log's `state=live` and its partial index share) - drawn at zero as a dimmed plain "0" with an accessible name, and at any other value as a `Typography.Link` into **`/admin/live-connections?subscriptionId=...`**, the live page being exactly the rows that count sums. It is a read, so it is not gated on `editSubscriptions`. The name cell is the wide one because it carries the owner, the tariff plan name (or "no tariff plan"), the creation date and **one** status tag — trial / blocked / expired, the computed status the server reports, never more than one — and wraps to two lines when it must; the expiry cell says "never" for null, red when expired, green otherwise. Paging, search (playlist id and both MACs), the three filters (owner, creator, computed status) and sorting are server side and live in the address; the two date columns are the sort keys and both toggle both directions — the name column (which shows the creation date) carries `key: 'createdAt'` and the expiry column `key: 'expireAt'`, because antd sends `columnKey` as `sortBy` and a key the server's `sortFields` does not name is silently dropped (that is why one column once sorted one way only); the auto-refresh toggle leads the toolbar exactly as on the streams tables. Row actions are edit, prolong (behind a confirmation dialog that names the concrete outcome — «Срок действия подписки пользователя client будет продлён до 23 окт. 2028, 17:00 в соответствии с тарифным планом Default», the date computed by `prolongPreview` and formatted with `formatTimestamp`; disabled without a plan), **kill active connections drawn disabled with its reason** (no endpoint exists — the stub does not lie), block owner (the bulk action with one id, so `editSubscriptions` is the gate and the account block is the write) and delete behind `modal.confirm`. **The service subrows are forced-open expandable rows**: `ServerTable` gained optional `expandable` and `rowClassName` pass-throughs and the page passes `expandedRowKeys` = all ids with `showExpandColumn: false` — no empty chevron column, which was both the big left gap and the extra width pushing the table past the card — so each row's strips — playlist with copy/regenerate/delete, MAG and Enigma2 with copy/change-in-a-modal/delete (an antd `Form`/`Input` with the `isMac` validator, `onOk` submitting the form so the validator speaks — a raw input that silently no-oped shipped once), then one add-services strip offering "generate playlist"/"add MAG"/"add Enigma2" only where the service is absent *and* the effective plan allows it — render attached below the row with no chevron. The strips indent to line up with the «Подписка» column and are visually part of the row — no background of their own, no border between a row and its own strip (the border between different subscriptions stays), 4px vertical padding under the row's 8px — every rule scoped under the card's `subscriptions-table` class alongside the highlight rules; and a selected row highlights its strips through `rowClassName` plus an adjacent-sibling rule painted from `data-theme`-scoped tokens — both themes, because a hardcoded light blue made the strips unreadable in dark mode while rc-table's own selected-row rule never reaches an expanded row. The name cell links the username to `users/:id` and the plan name to `tariff-plans/:id` — the plan link carries a dark-theme-readable color (`#b7d4ff` on dark; antd's dark link measured only 2.8:1 on a selected row, and the line's receding opacity multiplied it further, so the opacity moved onto the plain spans), a probe computing the contrast against every background this table paints. Every write button on the strips is gated on `editSubscriptions` through `hinted` (copy stays live for a viewer), which `probe:render` asserts. A single-row strip write answers single-row: the last-service refusal is one plain message (`subscriptions.lastServiceBody`), never the bulk selection summary. The bulk menu is labeled `subscriptions.bulk.menu` — "Actions"/"Действия", the other tables' convention — every item carries an icon, and the eight actions each open one dialog; the menu is gated on `editSubscriptions`; storage key `fluxy.subscriptions.columnWidths`. The sidebar is `subscriptionsAdd` (`subscriptions/add`) plus `subscriptionsManage` at `subscriptions` — "Управление" — the three placeholder device/playlist items having been merged into it.
- `src/pages/admin/SubscriptionFormPage.tsx` is the add **and** edit form behind `subscriptions/add` and `subscriptions/:id`, with the fetch-by-URL spinner, `useUnsavedChangesWarning` and `fieldErrors` wiring of the other forms. The owner select exists only on create (any user; the server never changes it afterwards), the plan select defaults to "no tariff plan" and offers only the plans available to the owner, and while a plan is chosen the dependent inputs (connections, restreamer, output formats, STB/country lock, trial), the bouquet multi-select and the MAC inputs the plan does not support are **disabled and not saved** — the server owns that rule and ignores them anyway. Clearing the plan select is the one path that bit twice: rc-select's clear stores `undefined`, not `null`, so `currentValues()` coerces after the spread and the body mapping derives the clear flag from the value (see the feature bullet above). Without a plan the bouquet list is required and preselects every bouquet when empty (and again when the plan is cleared), and at least one service (playlist / MAG / Enigma2) is always required; the generate-playlist button fills the id field with the answer of `POST /admin/subscriptions/playlist-id` and auto-runs on create when the selected plan supports playlists and nothing else. **Replacing an existing id asks first**: the button, and the strip's regenerate action, open a danger `modal.confirm` naming the id that will stop working, while a row with no playlist (the strip's add line, the create form) mints without a question — the branch is `replacesPlaylistId` in `subscriptionRules.ts`, unit-tested so the "first generation is silent, a replacement is not" rule cannot drift. The expiry input is `SubscriptionExpiryField` — an antd `DatePicker` with `showTime` behind `getValueProps: expireAtPickerProps`, because the form store holds the ISO string and the picker demands a Dayjs (feeding it the string crashes with `isValid is not a function`; the VOD form's `getValueProps` pattern is the fix, and the conversion lives in `subscriptionBody.ts` so a unit test can pin it) — beside a «Бессрочно» checkbox that is the *only* clear path, the picker carrying no clear affordance. The wire contract is the sentinel trap named: `''` clears the expiry on PATCH, `null` keeps it, create folds `''` to `null`. The create form starts max connections at 1.
- `src/pages/admin/ConnectionLogsPage.tsx` is the connection log — **one module behind two menu entries**, `/admin/live-connections` (`nav.items.liveConnections`) and `/admin/connection-logs` (`nav.items.subscriptionActivity`), reached from the subscriptions group after the tariff plans. The mode arrives through `sectionKey`, because the router renders every menu item as `<Page sectionKey={item.labelKey} />` and offers no other prop; an unknown key **throws** rather than falling back, so a key renamed on the menu side only fails the render probe and the browser's error fallback instead of drawing one list under the other's heading. The two modes differ in exactly four things, three of which live in `src/features/connection-logs/layout.ts` as data with a unit test (`tests/features/connection-logs/layout.test.ts`) because a width table that stops summing to 1190 is perfectly valid TypeScript (the fourth, the start-time range, is the page's own `MODE_SPECS` flag `showsStartRange`): the **column set** (live has `actions` and no `endedAt`; activity is the reverse — a finished session has nothing to end, so it draws no actions column at all rather than an empty one; both draw **seven** columns — subscription, user, stream, network, user agent, started, and then the mode's own end or actions, because the owner replaced the log's own identifier with the two links it stood in for and added the user agent as its own clickable column), its **starting widths** (each mode sums to **1190**; `startedAt` and `endedAt` are **equal at 200** and `startedAt` is the same 200 in both modes; the address starts at **160** and the user agent at **170** - the owner's round-4 correction, which took 40 px from the agent and gave it to the address, leaving the pair at 330 and both totals unchanged; the actions column is `actionsColumnWidth(1) + 45` = 101 on the owner's round-3 correction, and the stream column gave it those 45 px; and the two screens agree on subscription, user, network and agent, with only `stream` differing because the activity view spends 200 on its end column where the live one spends 101 on its actions), and the **storage key** (`fluxy.connectionLogs.live.columnWidths.v2` / `…activity.columnWidths.v2` — the `.v2` is the round-3 column set, because an arrangement stored for the old table describes a column that no longer exists). Both headings come from `connectionLogs.titles.<mode>` — live says "Live connections"/"Активные подключения" and activity says **"Connection logs"/"Журнал подключений"** — and those are keys of their own, deliberately separate from `nav.items.*`, because the owner renamed both the page heading and the menu item to "Connection logs"/"Журнал подключений" — the rail and the card now name one resource with one set of words, and the keys stay separate so either can still be worded alone. The toolbar order is auto-refresh, search, owner picker, stream picker, medium switch, width reset, clear-all; every parameter (the seven filters - including the exact `userAgent` one - the two range bounds `startedFrom`/`startedTo`, the medium, the state, the shared five) lives in the address, so the drill-down from a subscription row arrives filtered. **The start-time range is the activity view's alone and sits on a row of its own**: the live page is "every session still open" and draws no range control, no range tag, and sends neither bound - a `startedFrom`/`startedTo` in a live address is **ignored** rather than stripped (`startRangeForMode` in `startRange.ts`, pinned by `tests/features/connection-logs/startRange.test.ts`), because the visitor's address stays theirs and the live query stays the same whatever it holds. On the activity view the control is one `DatePicker.RangePicker` over two GET parameters, converted by the shared `src/utils/dateRange.ts` (unit-tested under pinned non-UTC zones in `tests/utils/dateRange.test.ts`; `features/connection-logs/startRange.ts` keeps only this table's `STARTED_FROM_KEY`/`STARTED_TO_KEY`/`startRangeForMode` and its re-exports, and the credit log passes `dateFrom`/`dateTo` to the same arithmetic): each bound is the first/last millisecond of the picked calendar day **in the account's time zone** - the zone the rows' `formatTimestamp` prints - so the picker's day and the visible day agree, both ends are inclusive on the server, and a single-sided range leaves the other side absent. The picker is drawn in the card body above the tag row and the table, **not in the card head's toolbar**: 250 px of range control pushed the owner picker, the stream picker and the medium switch onto a second line inside the heading, which is why the owner asked for a separate row. The range is drawn as one closable tag that clears both keys in one write, and the tag likewise exists only where the picker does. **The page is two components, and that is a bug fix rather than tidiness**: both entries render this one module, so react-router changes the props of a *mounted* component instead of remounting it, and every `useState` inside survived the switch — the paused auto-refresh travelled from live to activity and, worse, so did the widths, which were then written under the activity key and made the table keep the live arrangement after a reload. `ConnectionLogsPage` now resolves the key and renders `<ConnectionLogScreen key={mode} mode={mode} />`, so the state that must not survive ends with the instance that owns it; `useColumnWidths` was hardened the same way (its state is paired with the storage key it was read for, and a changed key re-reads **during render** rather than in an effect, so no frame paints the old arrangement). The **network cell** (`features/connection-logs/components/ConnectionNetworkCell.tsx`) is shared by the connection log **and the two visit histories**, and is two lines — flag and address on the first, the provider on the second — with the provider the **only** text set below the cell size; the flag and the address inherit the row's own 14px, and the address is **plain text with no `<code>` and no size of its own** on the owner's round-3 correction (antd's `code` decoration carried `font-size: 85%`, which made the address the one field in the row printed under the row's size), still clickable where the table can filter. The flag falls back to the letter code and stops being clickable when the image fails, its URL is `https://www.iptrackeronline.com/flags/{code}.png` (lower case only; the previous host answered a Cloudflare challenge for every image), and each of the three facts writes its own filter **when the table has one**: `onFilter` is optional, and the visit histories pass none because their endpoint resolves the geo fields while a page is built and takes no `ip`/`country`/`isp` parameter, so their cell draws the same facts as plain text rather than as controls that write nothing. The provider line comes from `networkLabel` in `src/utils/networkLabel.ts`, which reads the connection log's stored `isp` or the visit's `organization` + `autonomousSystemNumber`. The clear-all is behind `editSubscriptions` and one confirmation; the kill action is drawn disabled with its reason on the live mode and not drawn at all on activity, because no streaming subsystem exists to obey one.
- `src/features/epg/` is the programme guide sources: `api.ts` (`getEpgSources`, `getEpgSource`, `getEpgSourceChannels`, the two writes and the delete), its four `types/`, and its `hooks/`. Three pages use it: `EpgSourcesPage` (the `epgManage` menu item — server-paged table with no selection column, no bulk menu and no auto-refresh, whose toolbar carries the search, the width reset, the add button and a **disabled "Reload EPG" stub** with its reason, because the guide updater is a later pass), `EpgSourceFormPage` (one component behind `epg-sources/add` and `epg-sources/:id`, with the name, the absolute http(s) address and the 1..365 retention that starts at 7) and `EpgSourceChannelsPage` (read-only, at `epg-sources/:id/channels`, reached only from the row's "Channels" action — the streams that name the source, with their guide key). The raw guide and the parsed programmes have no screen: both belong to the updater. The video stream form's guide field is a `Select` over `useAllEpgSources` now, because a source is a row of this installation and the server refuses one that does not exist.
