## Structure

> Moved from AGENTS.md — the core bullets stay in the index.

- `src/pages/admin/ContentCategoriesPage.tsx` is the content categories table — one component behind **four** menu entries (`/admin/video-streams/categories`, `/admin/audio-streams/categories`, `/admin/video-on-demand/categories`, `/admin/series/categories`), one per content section. What separates the four instances is the kind of content they list, and it arrives through the only prop the router gives a section page: `sectionKey` is mapped to a `ContentType` by `SECTION_TYPES`, a map written beside the table that generates the keys (`CONTENT_SECTIONS` in `src/utils/navigation.ts`), and `probe:render` renders a *second* key to assert the mapping rather than trusting it — a key renamed on the menu side only would fall back to the video-stream kind silently. The card heading is `contentCategories.titles.<Type>` ("Категории видеотрансляций"…), because a heading that said only "Categories" on all four would leave four identical screens. **The order is arranged by dragging and saved by a button**: rows arrive in the order the server last confirmed, a drag moves them on screen only (`pendingIds`, kept apart from the query cache — the cache is what the server confirmed, an unsaved arrangement has no business in it), and the toolbar pair "Save order"/"Discard changes" is drawn while disabled and enables the moment the screen order differs from the server's (the same drawn-even-when-disabled convention the bulk menu follows). Saving sends **one** `PUT /admin/content-categories/order` with the whole list — one arrangement, one request, however many rows moved; the owner asked for exactly this to keep the write count down. A create while an arrangement is unsaved appends the new row to it, a delete drops its id out, and neither discards the visitor's moves. Dragging is `@dnd-kit/core`+`@dnd-kit/sortable` (antd 6 has none of its own; antd's own docs use `react-dnd`): the listeners live on a handle cell reached through a row context (there is no prop path from a row component into one cell of it, so the `useSortable` values travel through `RowDragContext`), and `PointerSensor` carries `activationConstraint: { distance: 5 }` — without it a click on a handle begins a drag on the way down. The two row actions are the ones the domain has today: "show content" disabled with the `membersSoon` reason (no content tables exist yet — the base-groups pattern of telling the truth before the click), and delete behind `modal.confirm`, which until the content tables arrive is the whole of the guard. `src/utils/http.ts` grew a `PUT` branch for the reorder, the way it grew `DELETE` for the active sessions.
- `src/pages/admin/VideoStreamsPage.tsx` is the streams table, the third of the four tables with a **bulk toolbar**. It is headed by `videoStreams.listTitle` rather than by `sectionKey` (the menu item says "Manage video streams", the card says "Video streams"; the prop is accepted and unread, like the other admin tables). Its eight columns are `id`, `icon`, `name`, `category`, `activeSource`, `status`, `epg`, `actions`, with widths summing to **1190** and the selection column taking them to the same **1230** as the accounts and groups tables; `name` gets the widest share of that room and truncates into a tooltip like the other text columns, while `status` carries the stream kind under the state. Only `name`, `category` and `status` sort: `type` and `sortOrder` are fields the endpoint honours but no header offers, and `activeSource`/`epg` are derived. **Paging, search, sorting and the three filters are server side**, and the table's five parameters plus the three filters all live in the address (`categoryId`, `status`, `type` through `withFilter`), so a reload or a shared link keeps the view. The **auto-refresh** re-reads every 30 seconds, on by default, through an icon-only button whose accessible name carries both the action and the interval; it deliberately **leads the toolbar**, because it describes the whole table while the bulk menu beside it acts on a selection that is empty on first paint. `probe:render` pins that order as well as the welcome state: the menu is drawn disabled with nothing selected, and with no profile answer it also carries the `editStreams` reason, which is exactly what an operator who may read but not change streams sees. Row actions are start/stop (one slot, chosen by the current state), restart, edit, delete behind `modal.confirm`, and play drawn disabled with the reason because the relaying process does not exist yet. **The bulk menu is gated on `editStreams`** and carries nine operations in three groups — start/stop/restart, the five edits (category, type, delay, archive, restream) and delete; the five edits open one dialog each, the delete asks once for the whole selection with the count, and the type dialog offers only the three kinds a bulk change can keep whole. The selection and the run are `useBulkAction`'s (`features/video-streams/hooks/mutations.ts` supplies `useBulkVideoStreams`), and every run re-reads the list, clears the selection and sends its per-row refusals or cleared-setting warnings to the shared summary — warnings are not failures. The feature's `api.ts` holds `VIDEO_STREAMS_PAGE_SIZE`, the bulk payload/action/type unions, and the restart and bulk calls beside the single-row ones.
- `src/pages/admin/VideoStreamImportPage.tsx` is the playlist import, the other way to add streams: one M3U file in, a category's worth of rows out. It is reached from `nav.items.videoStreamsImport` — the menu says "Import video streams"/"Импорт", the card says "Import streams"/"Импорт потоков" — which `CONTENT_SECTIONS` adds immediately after the add item and for the two stream sections; the other two never grow an import entry. The page is the create form with the playlist where the name and sources were, and the playlist sits **first**: the file is what the page is for, and every control below describes what to do with the entries it names. There is no name field, no "What it plays" divider, no source-list editor, no logo/EPG/identity field; the kind offers only `Permanent`, `OnDemand` and `Redirect`, status starts at `Stopped` (the endpoint's own default, and the safe state for a batch of thousands), and delay/archive/restream reuse the create form's capability rules — archive is greyed out and zeroed for a non-Permanent kind. The browser checks the 10 MiB file ceiling before the wire; the entry ceiling is the server's to count, because counting `#EXTINF` lines here would be a second parser. `importVideoStreams` sends `FormData`, which `src/utils/http.ts` recognises: it omits the JSON `Content-Type` (the browser writes the multipart boundary) and does not `JSON.stringify` the body. The result is an `Alert` whose type reports failures over skips, carrying `total`/`imported`/`skipped`/`failed`, followed by a paginated table of the per-line problems; success clears the chosen file — a second click would import the same names and report every one as skipped — and invalidates `['videoStreams']`. `useUnsavedChangesWarning` guards a chosen file or edited settings, and the `videoStreamsImport.*` keys are translated in both bundles.
- `src/components/SourceListEditor.tsx` is the **shared** ordered-list editor — the control that edits a list of addresses in relay order, with the move-up, move-down and remove buttons on every entry and the "add another" button underneath. It lives in `src/components/` rather than in the video feature because **the audio form draws the same control**: both stream forms collect an ordered list of sources, and a feature may not import another feature. It was moved there when the audio feature arrived; the video form's import changed and nothing else about it did. Its labels arrive as a prop (`{ up, down, remove, add, required }`) rather than as translation keys, because the same component draws the video form's source list and the audio form's, and the two call sites word their own buttons — a source in one, a source in the other, but a *file* in the video form's second list.
- `src/pages/admin/AudioStreamsPage.tsx` is the admin's **audio** streams table, the video table's twin by construction and its own page in every other respect. It is headed by `audioStreams.listTitle` rather than by `sectionKey`, for the same reason the video one is. Its **seven** columns are `id`, `icon`, `name`, `category`, `activeSource`, `status`, `actions` — the video table's eight minus the `epg` one, because an audio stream has no programme guide. The widths sum to **1190** and the selection column takes them to the same **1230** the accounts, the groups and the video streams tables reach; `name` is **352** rather than the video table's 262, because the room the EPG column gave up went to the one column nothing truncates a second time. Only `name`, `category` and `status` sort, `type` is a field the endpoint honours but no header offers, and `activeSource` is derived. **Paging, search, sorting and the three filters are server side**, and the table's five parameters plus the three filters all live in the address (`categoryId`, `status`, `type` through `withFilter`), so a reload or a shared link keeps the view. The **auto-refresh** re-reads every 30 seconds, on by default, through an icon-only button whose accessible name carries both the action and the interval, and it **leads the toolbar** — it describes the whole table while the bulk menu beside it acts on a selection that is empty on first paint. Row actions are start/stop (one slot, chosen by the current state), restart, edit, delete behind `modal.confirm`, and play drawn disabled with the reason because the relaying process does not exist yet. **The bulk menu is gated on `editAudioStreams`** — a *separate* grant from the video table's `editStreams`, and deliberately so: a group that may change the video streams may not change the audio ones. It carries **seven** operations in three groups — start/stop/restart, the three edits (category, type, restream) and delete — where the video menu carries nine, because an audio stream has no delay, no archive and no payload a kind of it can switch off. **There is no warnings column**: a video bulk run may report a cleared delay or archive beside its refusals, and an audio run never does, so `useBulkAction` is given only a `partialTitleKey`. The feature's `api.ts` holds `AUDIO_STREAMS_PAGE_SIZE`, the bulk payload/action/type unions, and the restart and bulk calls beside the single-row ones.
- `src/pages/admin/AudioStreamFormPage.tsx` is the add **and** edit form for one audio stream — one component behind `audio-streams/add` (a menu item) and `audio-streams/{id}` (an `extra` route with no menu item, reached only by choosing a row; a second `lazy()` over the same module makes a move between the two remount rather than carry a half-filled form across). The heading comes from whether there is an `id` (`audioStreams.addTitle`/`audioStreams.editTitle`), not from `sectionKey` — the prop is accepted and deliberately unread. The fields are the name, the category, the state, the kind, the **ordered source list**, the icon address, the Enigma2 service id and the four restreaming settings — and **nothing else**. There is no delay, no archive, no programme guide, no series reference and no VOD reference, because an audio stream has no such fields; a form that drew any of them would be asking the operator for something the server refuses. **There is no capabilities module for the audio feature** — the video one has `features/video-streams/capabilities.ts` because a video kind's payload differs from another's, and the audio feature has **no conditional field at all**: both kinds relay from the same list and carry the same restreaming settings, so there is nothing for such a module to describe. That is the whole difference between the two media, and it is why the audio form is shorter than the video one and the audio bulk menu is shorter than the video one. Edit mode **fetches by URL and draws a spinner until the answer arrives** — `probe:render` lands in exactly that state and asserts it, because a form painted from whatever the previous screen happened to hold would edit the wrong row after a reload. Success navigates to `${area}/audio-streams` — `area` from `areaForRole(session.role)`, since `navigate('..')` from a child of the area pops to `/admin`, not to the list.
- `src/pages/admin/AudioStreamImportPage.tsx` is the audio playlist import, the other way to add streams: one M3U file in, a category's worth of rows out. It is reached from `nav.items.audioStreamsImport`, which `CONTENT_SECTIONS` adds immediately after the add item — the same place the video import sits, because reading a playlist is the other way to add streams for either medium. The page is the create form with the playlist where the name and sources were, and the playlist sits **first**: the file is what the page is for, and every control below describes what to do with the entries it names. There is no name field, no "What it plays" divider, no source-list editor, no logo/identity field; the kind offers only `OnDemand` and `Redirect` (both relay from a list of addresses, which is exactly what a playlist supplies), and status starts at `Stopped` (the endpoint's own default, and the safe state for a batch of thousands). The browser checks the 10 MiB file ceiling before the wire; the entry ceiling is the server's to count, because counting `#EXTINF` lines here would be a second parser. `importAudioStreams` sends `FormData`, which `src/utils/http.ts` recognises: it omits the JSON `Content-Type` (the browser writes the multipart boundary) and does not `JSON.stringify` the body. The result is an `Alert` whose type reports failures over skips, carrying `total`/`imported`/`updated`/`skipped`/`failed`, followed by a paginated table of the per-line problems; success clears the chosen file — a second click would import the same names and report every one as skipped — and invalidates `['audioStreams']`. `useUnsavedChangesWarning` guards a chosen file or edited settings, and the `audioStreamsImport.*` keys are translated in both bundles.
- `src/pages/admin/VideoOnDemandPage.tsx` is the admin's **on-demand catalogue**, the streams table's sibling and its own page in every respect. It is headed by `videoOnDemand.listTitle`, its eight columns are `id`, `poster`, `name`, `category`, `status` (the type rides under the state), `releaseDate`, `rating` and `actions`, and the widths sum to **1190** with the selection column taking them to the same **1230** the other tables reach. Paging, search, the three filters (`categoryId`, `status`, `type`) and sorting are server side and live in the address; only `name`, `category`, `status`, `releaseDate` and `rating` offer a sorter (the endpoint also honours `type`). The row actions are **play**, which opens a modal whose `<video>` points at `GET /admin/video-on-demand/{id}/play` (the server decides whether a relay is proxied or a redirect answered with 302), **transcode**, drawn disabled with `videoOnDemand.actions.transcodeUnavailable` while `GET /admin/video-on-demand/transcode-formats` says `available: false`, edit and delete. The bulk menu carries `change-status`, `move-category`, `change-type` and `delete`, one dialog each, and is gated on `editVideoOnDemand`. The optional subtitle address becomes a `<track>` in the player; the `<video>` carries a targeted `jsx-a11y/media-has-caption` disable because captions are a per-row fact rather than a property of the page. Storage key `fluxy.videoOnDemand.columnWidths`.
- `src/pages/admin/VideoOnDemandFormPage.tsx` is the add **and** edit form for one on-demand video — one component behind `video-on-demand/add` and `video-on-demand/{id}` — with the same fetch-by-URL spinner, unsaved-changes guard and `fieldErrors` wiring as the stream form. The fields are the name, the category, the state and the kind, the source and the optional subtitles, and the metadata: IMDb id, poster, backdrop, synopsis, cast and genres (`Select mode="tags"`), director, release date (`yyyy-MM-dd`), rating (0–10, one decimal) and a two-letter country. The date, rating and country shapes are the only rules the form enforces itself; the name's uniqueness, the category's kind, the list limits and the rating's database precision are the server's, and their refusals land under the fields.
- `src/pages/admin/VideoOnDemandImportPage.tsx` is the on-demand playlist import: the playlist first, then the category, state and kind, and the same counts-and-problems report as the stream import. Both delivery kinds are offered because both take one address per entry; the file ceiling is checked in the browser, the entry ceiling is the server's.
