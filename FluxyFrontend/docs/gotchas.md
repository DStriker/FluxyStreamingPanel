## Gotchas

- **The i18n keys are deliberately untyped; the locale files are not.** `t('profile.typo')` compiles and falls back at runtime, which is accepted because the keys are written twice and the two copies must agree: `en.ts` exports `type Translation = typeof en` and `ru.ts` declares itself `: Translation`, so a key present in one file and missing from the other is `TS2353` on the line it happened. Adding a translation means both files, and that type is what makes it an error rather than a missing string.
- **`AuthForm` and `ConfirmCodeForm` are generic in the values their page collects, and neither has a default.** A page that writes `<AuthForm>` alone infers `unknown`, and its first field read fails to compile — that is the design: the alternative is a `values` typed as whatever the component guessed, which compiles happily and is `undefined` at the first submit. Name the shape at the call site: `SignInValues` or `RegistrationValues` from the auth feature's `api.ts` for `AuthForm`, and `RegistrationConfirmValues` or `ResetConfirmValues` from the component for `ConfirmCodeForm`. The token half of the contract is fixed the same way: neither form mints an antiforgery token — it passes only the captcha token it minted for its action, beside the values — so the endpoint call a page wires in is always its feature's `mutations.ts` hook's `mutateAsync`, never the endpoint function itself.
- **`useSession()` answers `SessionContextValue | null` and never throws without a provider.** `npm run probe:render` renders `ProfilePage` with no provider at all, so a hook that threw would take the probe down instead of describing the page. Consumers narrow instead: `AccountHeader` and `AccountSidebar` write `if (!session) return null` — only `RequireAuth` renders them, so `null` there means the guard was bypassed rather than that nobody is signed in, and the comment above each says so — while everything else reaches through `session?.`.
- **`src/config/index.ts` reads `import.meta.env ?? {}`.** The probes bundle `src/` for Node, where `import.meta.env` does not exist at all: the fallback is what keeps those bundles running, and typing it as `Record<string, unknown>` behind two narrow helpers (`pick`, `raw`) is what keeps `tsc` honest about a value that genuinely is not always there. Vite inlines the real values at build time, so the type is a description of a build step rather than of the object at hand.
- **The route table is annotated `RouteObject[]`, not inferred.** `index: true` widens to `boolean` the moment nothing says otherwise, and an entry carrying both a `path` and an `index` is a contradiction the union only reports once a union is being asked for — which, unannotated, would be the first consumer of the table rather than the line the entry sits on. Every top-level entry is built through `withFallback`, which attaches the shared `ErrorFallback`: the crash screen used to be nine repeated lines, and a route added later would have been the one to drop it.
- **Every request to the API must go through `apiUrl`.** There are exactly two `fetch` calls in the app — one in `csrf.ts`, one in `http.ts` — and both build the URL with `apiUrl(path)`. Nothing may fetch a bare `/auth/...`. This is not a style rule. A relative path resolves against whatever serves the page, which in development is the Vite server; it answers an unknown path with the SPA shell and a **200**, so `res.ok` is true, the JSON parse fails, and the token silently comes back `null`. Every later POST is then refused with `csrf_invalid` and the UI shows no cause. It happened once already.
- **`apiUrl` lives in `src/utils/url.ts` and must stay there.** `http.ts` imports `csrfHeader` from `csrf.ts`, and `csrf.ts` needs `apiUrl` too — so defining `apiUrl` in either of them closes an import cycle. A cycle does not necessarily throw here; it can resolve in an order that yields a stale binding, which surfaces as a wrong URL rather than a crash. The module exists to break that, and it imports nothing but `config`.
- **`VITE_API_BASE_URL` must stay empty in development.** `vite.config.js` proxies `/auth` to the backend (`VITE_API_PROXY_TARGET`, default `http://localhost:5159`), and `preview` proxies it too, so the page and the API share one origin. That is not a convenience — see [api-same-origin.md](api-same-origin.md). `credentials: 'include'` is still set on both fetches; it is a no-op same-origin and load-bearing if a deployment ever splits the origins.
- **Either launch profile works, and that is deliberate — do not "fix" it back to one.** The proxy sets `X-Forwarded-Proto: https`, which is how the backend recognises a proxied request and skips `UseHttpsRedirection` for it (the branch is Development-only; outside it the header is attacker-controlled). Without that header the `https` launch profile answers the http port with a **307** to `https://localhost:7221`, and the proxy relays the redirect verbatim. The browser follows it to a different **scheme**, the call becomes cross-origin, needs a preflight, and the antiforgery cookies come back `secure` over a plain http connection and get discarded — which reads as `csrf_invalid` with nothing wrong in the response body. Measured on the `https` profile: proxied `/auth/csrf` was `307`, then after this change `200` with `XSRF-TOKEN` and **no** `secure` flag, and the POST advanced to `captcha_invalid`, which is the point past CSRF. Visual Studio launches the `https` profile by default, so a rule that only works under the `http` profile would be a rule that breaks again on the next F5. The header value must state the scheme the **browser** used, not the one the proxy used to reach the backend. The backend reads it only as a marker that a terminator already decided, so `http` there would be a marker stating the wrong scheme — worse than no header at all, because it would suppress the redirect while misreporting what happened.
- **`strictPort: true` is set on `server` and `preview` on purpose.** Vite's default is to take the next free port, and a silent move from 5173 to 5174 changes the page origin — hence a different CORS decision and a different rate-limit bucket — while the console still prints "ready". This is not hypothetical: a stray second dev server on 5173 pushed the real one to 5174, and that port drift was half of what made the CORS failure above look like an unfixable mystery. The port has to be a fact, not a suggestion.
- **API paths carry no `api/` segment.** The backend serves nothing but the API, so the prefix was dropped there (`[Route("auth")]` in `FluxyBackend/Fluxy.API/Controllers/Auth/AuthenticationController.cs`, and the same route on `RegistrationController.cs` beside it). Both halves hardcode their own copy — `/auth/${action}` in `src/features/auth/api.ts` and `TOKEN_URL` in `src/utils/csrf.ts` — so a rename has to be made in two repositories at once or registration silently 404s. `npm run probe:paths` checks the local half of that drift: every prefix a request is made with must be one the dev proxy knows.
- **The three login endpoints exist and are per-role.** `submitAuth` posts to `/auth/client-login`, `/auth/reseller-login` and `/auth/admin-login`; each refuses an account of a different role with the same `invalid_credentials` a wrong password gets, and each entrance has its own window (5 attempts per 15 minutes per IP and role, keyed without the username). An earlier version of this note said all three 404 — they were filled in when the JWT + refresh-token session was built, and `npm run probe:session` exercises them against a live backend.
- **The profile page has a login guard card next to the time zone card.** `LoginGuardCard` edits the two switches and the three allow lists (`changeLoginGuard` sends them as the `loginGuard` field of the single `PATCH /auth/profile`, `lookupGeo` reads `/auth/geo/lookup` for the "use my current network" button) and joins the same confirmation step as the other changes — a `profile_change_submitted` answer swaps the page to `ConfirmCodeForm` with `kind: 'guard'`, no rename afterwards. The form item names are the server's camelCase field names (`allowedIps`, `allowedCountry`, `allowedAutonomousSystemNumber`), so `fieldErrors()` lands rejections under their inputs with no translation step. Limits mirror the server (`LOGIN_GUARD_MAX_IPS` in `src/features/profile/loginGuardPolicy.ts`); the server stays the authority.
- **The guest pages are guarded in the router, not inside the pages.** `GuestOnly` asks `/auth/me` once per navigation and leaves through `homeForRole(session.role)` — by role, never by entrance: an admin at `/login` belongs on the admin area, a client at `/admin/login` on the client one, because that is where signing that account in would land it. Two properties are easy to break without anything failing loudly. The fallback for an unknown role must be a **non-guest** route — a session that demonstrably exists sent back to login would pass through the guard that just asked and come straight back, which is a loop and not a fallback. And the destination must come from this app's own route table rather than a path the server sent, so a path the two sides disagreed about cannot bounce a signed-in visitor between the catch-all and the guard. The two copies of the landing rule agreeing is asserted by `npm run probe:session`: `homeForRole(role)` must equal the `redirect` the sign-in itself was answered with.
- **`homeForRole` and `areaForRole` answer different questions, and building a section URL from the wrong one is how `/admin/dashboard/profile` happened.** The landing path the server names is a *page* — `admin/dashboard` — while the area every section hangs from is only its prefix — `admin`. So the router's area path, the sidebar's menu keys and the header's profile shortcut all take `areaForRole`; `homeForRole` is where a sign-in opens and nothing else. Both are cut from the same `config.*_HOME_ROUTE` by `areaOf` / `insideArea` in `src/config/index.ts`, so neither can move without the other, and neither the server's `Auth:LandingPath*` nor the landing paths themselves changed when the nesting did. `npm run probe:render` asserts the result twice: every menu key must match a declared child route, and `matchRoutes` must resolve each of them to that role's own area rather than to the catch-all — a nested path still resolves, just to the 404, so string comparison alone would have passed it.
- **Page `action` is the reCAPTCHA action and comes from a `*CaptchaAction` constant; the submit path is kebab-case.** `ClientLoginPage` passes `action={ClientLoginCaptchaAction}` (`'client_login'`, the string the server expects to find in the token) and submits to `action: 'client-login'`. The two spellings still have to agree when a flow is added — the captcha half is now a constant in `src/features/auth/api.ts` rather than a literal copied into five pages, but the endpoint is still written where it is used.
- **reCAPTCHA is disabled in dev** (`getCaptchaToken` returns `null` when `import.meta.env.DEV`) and skipped entirely when the site key is empty. Captures in prod only.
- **`getCsrfToken` always mints a fresh token — never a cached one, never the cookie read back.** It is best-effort only in the failure direction: it silently returns `null` when the backend is absent, and that silence is load-bearing for the login pages. It is also what hid the wrong-URL bug above, which is why the probe asserts the URL `getCsrfToken` actually requests. **The callers are exactly four modules** — `http.ts` for its refresh retry, `features/auth/api.ts` for `signOut` (which must mint under the session it is about to end), `hooks/useWrite.ts` for every write built on it and `features/sessions/hooks/mutations.ts` for the one write with no argument of its own — and a page or a component naming it directly is a sign the write belongs in its feature's `hooks/mutations.ts`. The freshness is a correctness rule, not a preference. The antiforgery service binds a token to the identity that was current when it was minted: a token obtained on the sign-in page is refused after sign-in, with `csrf_invalid` and `"The provided antiforgery token was meant for a different claims-based user than the current user"` in the server log. That is exactly what killed the placeholder's sign-out button — it read the `XSRF-TOKEN` cookie written before the session existed, the POST came back 400, and `handleSignOut` had no `catch`, so nothing appeared to happen at all. Two fixes close it from both sides: every submit now mints immediately before sending, and the backend drops the readable `XSRF-TOKEN` copy whenever the session changes (`AuthCookies.Write`/`Clear`), so a cookie cannot outlive the identity it was minted under either. Both halves — and the refusal of the stale token, which is the rule itself — are asserted by `npm run probe:session`.
- **The header logo is sized through `rootClassName`, not `className`, because antd's `Image` puts those two on different elements.** In antd 6 `className` lands on the `<img>` itself and `rootClassName` on the `.ant-image` wrapper; the wrapper is the flex item whose width is the logo's width. Giving the class to the `<img>` looks right in the markup and loses the cascade twice over: antd's `.ant-image .ant-image-img { width: 100% }` is two classes to the logo's one, and the wrapper is left shrink-to-fit, so at 1440px the image measured 914×291 inside a 64px header and pushed the page's scroll width past the viewport. `AccountHeader` therefore carries `rootClassName="layout-shell__logo"`, `index.css` sets the width on that wrapper, and `.layout-shell__logo .ant-image-img` lets the image fill it. The width is CSS rather than the `width` prop so the 96px and hidden breakpoints can change it without an inline style winning.
- **The app renders two assets: `public/logo.jpg` (both `AuthCard` and `AccountHeader`) and `public/logo.svg` (the favicon generator).** All of `public/` is tracked, so a fresh clone renders both. Two files sit in the *repository root* — `logo.jpg` and `reflux_logo.png` — and nothing in `src/` or `scripts/` references them; `public/logo.png` is likewise referenced by nothing. Do not "wire up" any of the three, and do not assume a root `logo.jpg` is what `/logo.jpg` serves.
- `index.html` carries a static `lang="en"` for the moment before the bundle runs; from then on `src/i18n.ts` keeps `document.documentElement.lang` in step — on init and on every `languageChanged` — from `i18n.resolvedLanguage ?? i18n.language`. The language itself comes from i18next (`localStorage` key `fluxy-lang`, then `navigator.language`, default `en`).
- `.env` is gitignored; `.env.example` is the committed template (it documents `VITE_API_BASE_URL`, the route vars and the reCAPTCHA key). Env vars are inlined at build time, so changing them requires a rebuild, not just a dev-server restart.
- `dist/` is committed/present locally and ignored by eslint. Don't edit build output.
- Comment language in this repo is mixed Russian/English; `csrf.ts` and `launch.json` contain Russian comments. Keep the surrounding style when editing existing lines. **Commit messages are English-only and short** — one line for the subject, a body of a few lines at most.
