## The user groups API: `admin/user-groups`

Groups are what a role turned into: a row carrying **one** of the three roles plus the permissions its members inherit. `users.role` was **dropped** by `AddUserGroups` — the role a caller holds is read through `Include(Group)` from the group the account names, and the permission gates below are the second, independent check on top of it. A group is what the admin area manages; the account merely points at it.

| Endpoint | Auth | Answer |
| --- | --- | --- |
| `GET /admin/user-groups` | `Permission.ViewUserGroups` | page: `page`, `pageSize`, `search`, `role`, `status`, `sortBy`, `sortOrder` |
| `GET /admin/user-groups/{id}` | `Permission.ViewUserGroups` | one group with `permissions` and `members`; `404 user_group_not_found` |
| `POST /admin/user-groups` | `Permission.EditUserGroups` | `201 user_group_created` + relative `Location` |
| `PATCH /admin/user-groups/{id}` | `Permission.EditUserGroups` | `200 user_group_updated` |
| `DELETE /admin/user-groups/{id}` | `Permission.EditUserGroups` | `200 user_group_deleted` |

The class still carries `[Authorize(Policy = AdminPolicy)]`. **Role and permission are two separate requirements, not one**: the four policies (`Permission.ViewUsers`, `.EditUsers`, `.ViewUserGroups`, `.EditUserGroups`, the constants on `AuthenticationExtensions`) each demand *both* `RoleRequirement(Admin)` and their `PermissionRequirement`. Deliberate — a permission key alone would be checkable by any signed-in account that somehow held it, and a role alone is what the API already had. **Reads demand the view permission, writes the edit one**, so an operator who may see the group list still gets `403 permission_denied` from a `PATCH`.

- **Three base groups, always.** Their identifiers are constants in `BaseUserGroups` (`…0001` Clients, `…0002` Resellers, `…0003` Administrators) rather than database-invented values, because three different places must name the same rows without having seen each other: the migration that backfills accounts, the startup seeder, and the service that refuses to delete them. **Base-ness is the identifier** — `BaseUserGroups.IsBase(id)` — which is why renaming a base group cannot un-base it.
- **A base group accepts `name` and nothing else.** `UserGroupService` refuses a `PATCH` carrying `Role`, `Status` *or* `Permissions` on one with `409 user_group_immutable`, and refuses to delete one the same way. Rename is the whole of what the form offers, and controls are drawn disabled rather than hidden so the visitor is told before the click.
- **`409 user_group_in_use`** for any group that still has a member (`users.group_id` is `RESTRICT`, so the database would refuse it anyway — the service checks first to answer with a code instead of a `DbUpdateException`). Delete on an empty group of one's own is the only group that goes.
- **The permission catalog is role-scoped, and the two failure modes differ on purpose.** A name that does not exist (`viewEverything`) is **refused** with `validation_failed` and the list that does — a client wrong about the contract is told so. A *valid* permission the chosen role does not own (`viewClients` on a Client group) is **dropped** — that is a client describing a group, and the server already knows what a Client group may hold. The catalog is `[Flags]` powers of two stored as `integer` in `user_group_permissions`, with **twenty-two** members in six groups: the two **group-management** keys (`ViewUserGroups=4`, `EditUserGroups=8`), the six **account** keys split by the role of the account they act on (`ViewClients=16, ViewResellers=32, ViewAdmins=64, EditClients=128, EditResellers=256, EditAdmins=512`), the four **stream** keys — the video pair (`ViewStreams=1024`, `EditStreams=2048`) and the audio pair (`ViewAudioStreams=4096`, `EditAudioStreams=8192`), deliberately **not** the same pair: a group that may watch the video streams may not watch the audio ones — the **on-demand** pair (`ViewVideoOnDemand=16384`, `EditVideoOnDemand=32768`), the **series** pair (`ViewSeries=65536`, `EditSeries=131072`), the **guide** pair (`ViewEpgSources=262144`, `EditEpgSources=524288`), the **bouquet** pair (`ViewBouquets=1048576`, `EditBouquets=2097152`) and the **tariff plan** pair (`ViewTariffPlans=4194304`, `EditTariffPlans=8388608`). All twenty-two are owned by `Admin`, so `permissionsForRole` on the frontend answers an empty set for Client and Reseller and their form shows a note instead of boxes.
  - **A permission added in code reaches the base groups two ways.** The startup seeder (`DefaultUserSeeder.ReconcilePermissionsAsync`) reconciles the three base groups against `UserPermissionCatalog` on every start, so adding a member needs no migration. The tariff plan pair also got a data-only migration (`20261028140626_GrantTariffPlanPermissions`) for the installation migrated but not yet restarted: it inserts the two grants for the Administrators base group with a `WHERE NOT EXISTS` guard, because the seeder may already have written them and the unique index over (user_group_id, permission) would refuse a second copy and fail the migration.
  - **The column is `integer`, not `smallint`.** The on-demand write key is `32768`, one more than a `smallint` can hold; the first scaffold therefore wrapped it and the base group stored a negative grant. `WidenUserGroupPermission` widens the column, lossless for every value already there. The enum's values are still the schema, and a new member is still a value nobody has used yet.
  - **The account keys start at 16, not at 1.** Values `1` and `2` were the retired `viewUsers`/`editUsers` of the first version — one pair for accounts in general, replaced by the per-target split — and the numbers are schema, so renumbering the live ones would reinterpret every stored grant as a grant of something else without a single query being made. `1` and `2` are therefore empty and must not be handed a new meaning.
  - **The stream keys are not split by role, because a stream is not an account.** One `ViewStreams` and one `EditStreams`, nothing narrower, for the same reason content categories carry no permission at all: one installation-wide list of streams, one screen that draws it, no second axis. They are a pair rather than one key so a group that may watch streams and a group that may run them stay two grants. The audio pair is a **second** such pair rather than a widening of the first: the two media are two resources with two tables and two routes, and a grant naming both would be a grant to a thing nobody can administer — the group form would offer one box for two screens and neither could be locked away on its own.
  - **Adding a permission needs no migration.** The catalog is code; base groups are reconciled at startup, so a new member appears on the Administrators row on the next boot. It does need a line in `UserPermissionCatalog.Owner` — an unowned member is a grant nothing ever answers — and the frontend's `ALL_PERMISSIONS`/`OWNER` (`src/features/user-groups/permissions.ts`) plus the two locale `permissions.*` blocks, or its checkbox label degrades to the raw key.
- **The seeder reconciles the base groups at startup**: role and permissions are restored to what the catalog says, `name` is left alone (an installation may have renamed them, and that is allowed), and permissions are reconciled in both directions so a grant removed from the catalog does not linger on the Administrators row.
- **Effective status is the most restrictive of the account's and its group's** (`UserStatusComposition.Combine`: `Blocked` > `Unregistered` > `Registered`). The accounts list draws that effective value; the detail shows the row's own `Status` beside a read-only `EffectiveStatus`. The same composition is copied to `src/features/users/userStatus.ts` on the frontend, with its `RESTRICTIVENESS` map written out because the `UserStatus` enum's *numbers* are in the wrong order for this question.
- **No captcha, no attempt window** — the same recorded departure as `admin/users`: every write is behind an `AdminOnly` session plus a fresh antiforgery token, and reCAPTCHA cannot be minted outside a page. `RejectsCsrfAsync()` runs first, before any body is read.

**Codes:** `user_group_created|updated|deleted|not_found|already_exists|immutable|in_use`, plus `validation_failed` and `permission_denied` — all translated in both locale bundles (the probe imports `en.ts`/`ru.ts` and looks each one up).

**Migration `20261009130702_AddUserGroups` is hand-written**, and its order is the point: create `user_groups` → insert the three base groups → insert the four admin permission rows → add `users.group_id` nullable → three `UPDATE … WHERE role = n` backfilling every existing account onto its matching base group → `SET NOT NULL` → drop `users.role` → index and FK. No `CASE` fallback for an account that matches no base group: on this installation every account did, and a fallback would have hidden a row the backfill had missed instead of surfacing it.

Layering follows the usual split: `UserGroup` in `Fluxy.Core/Users/Models/`, `UserGroupListItem` / `UserGroupPage` / `UserGroupDetail` in `Fluxy.Core/Users/ReadModels/`, `NewUserGroup` / `UserGroupPatch` in `Fluxy.Core/Users/Commands/`, `UserGroupOutcome` / `UserGroupAction` / `UserGroupSortField` / `UserGroupSortOrder` / `UserPermission` in `Fluxy.Core/Users/Enums/`, `UserGroupListLimits` / `UserPermissionCatalog` / `BaseUserGroups` / `UserStatusComposition` in `Fluxy.Core/Users/Utils/`, `IUserGroupService` in `Fluxy.Core/Users/Interfaces/`, `UserGroupService` in `Fluxy.Application/Users/Services/` (Scoped), the entities and their two configurations in `Fluxy.DataAccess/`, and the contracts in `Fluxy.API/Contracts/UserGroups/` (`AdminUserGroup*`, `CreateUserGroupRequest` / `UpdateUserGroupRequest`, `BulkUserGroupsRequest`, `UserGroupResponses`).

Verified against a running instance by `npm run probe:groups` in the frontend (**28/28**, driving the app's own modules rather than `curl`), the load-bearing rows being: the three base groups present and only those flagged; the Admin base group granting four and the Client one granting **zero**; a duplicate name → `409 user_group_already_exists`; the unknown-vs-wrong-role asymmetry above, with the row re-read to prove nothing was stored; rename → `200` while role, permissions and deletion of a base group each → `409 user_group_immutable`; a populated group → `409 user_group_in_use`; an unused id → `404 user_group_not_found`; a write with no antiforgery token → `400 csrf_invalid` (so CSRF runs *before* the rules — it must not come back as a 409 wearing a different hat); `GET /admin/users?groupId=` returning only that group's accounts; and a second account holding only `viewUsers`+`editUsers` still reading accounts while every group endpoint answers `403 permission_denied`.
