## The connection logs API: `admin/connection-logs`

The record of what was watched under which subscription, from where, and for how long. Two endpoints, because nothing here captures a connection: the process that relays a stream will own the write path, and a `POST`, a `PATCH` or a `DELETE {id}` declared now would be a route with no rule behind it.

| Endpoint | Auth | Answer |
| --- | --- | --- |
| `GET /admin/connection-logs` | `Permission.ViewSubscriptions` | page: `page`, `pageSize`, `search`, `kind`, `state`, `subscriptionId`, `ownerId`, `streamId`, `ip`, `country`, `isp`, `userAgent`, `startedFrom`, `startedTo`, `sortBy`, `sortOrder` |
| `DELETE /admin/connection-logs` | CSRF + `Permission.EditSubscriptions` | `200 connection_logs_cleared`; wipes the whole table |

- **Country and provider are stored columns, and that is the deliberate divergence from the visit history.** `refresh_tokens` resolves GeoIP while a page is built because it stores no second copy of a fact the database could later answer differently — and that is exactly why it cannot filter by country or provider. This table is filtered and counted by both, so the snapshot is taken when the session opens and kept as it was. **Nothing on the read path calls `IGeoIpResolver`**: a lookup there would answer a different value from the one the filter just ran against.
- **`ip`, `isp` and `userAgent` are exact filters and `country` is canonicalised.** An absent or blank value means "no filter"; a present one is compared against the stored column as it reads. The user agent is **case sensitive** (`CURL/8.5.0` and `curl/8.5.0` are two clients), because it is a client's own string and folding its case would answer rows for a client that never sent it. `country` is the exception only because its column is upper-case by construction — a typed `de` is folded to `DE` rather than dropping the filter. `total` is counted under the same predicate as the page, so a filtered list's pages sum to it.
- **`startedFrom` / `startedTo` are one range over `started_at`, both ends inclusive and each optional.** Absent or blank means no bound on that side; a present value is an ISO 8601 date or date-time (`2026-05-01`, `2026-05-01T10:00`, `2026-05-01t10:00:00z`, `2026-05-01T10:00:00+03:00`), parsed with the invariant culture and **an absent offset read as UTC** - the same wire convention as the subscription expiry. A present offset is honoured and normalized to UTC, so the query means the same instant wherever the API runs. A value that parses as no instant is `400 validation_failed` naming `startedFrom` or `startedTo` - never read as "no bound", because that would widen the list silently. Both bounds are inclusive because the screen's picker names whole days: an end the operator picked as "the 1st" that dropped everything started during the 1st would answer a list narrower than the control shows, so the page sends that day's last millisecond. `total` is counted under the same predicate, and no new index is needed: the default `(started_at DESC, id DESC)` index answers the range scan. An inverted range (`startedFrom` after `startedTo`) is not refused as a conflict - it is simply a predicate nothing satisfies, and the answer is an empty page with `total: 0`, the same answer any other filter that matches nothing gives.
- **`ix_connection_logs_user_agent` (`AddConnectionLogUserAgentIndex`) is what keeps the exact user-agent filter one index read.** The column has always been stored and read; the filter that compares it arrived with the screen's click-through, and a table that grows forever should not be scanned for a value that is already indexed. The scaffolded index is a plain b-tree, so unlike the partial live index there is nothing hand-written in that migration.
- **The subscription is an `ON DELETE CASCADE` foreign key; the stream is opaque.** Deleting a subscription deletes the connections it carried — the log is evidence about a subscription, and removing the subject is what the operator asked for. `stream_id` has **no** FK, because the relaying process may report a stream row this installation never recorded (the same rule `VideoStream.SeriesId` follows); the read path resolves the title from `video_streams` or `audio_streams` by the kind, and answers null when the row is gone.
- **The subscriptions list carries `activeConnectionCount`.** Each `SubscriptionListItem` reports how many of its `connection_logs` rows have `ended_at IS NULL` — the same predicate the log's `state=live` filter and the partial `IX_connection_logs_live_started_at` index are built on. `SubscriptionRepository.GetPageAsync` fills it with **one grouped `IN` query over the identifiers the page actually holds**, never a count per row: a correlated subquery in the projection would be an N+1 over a page of a hundred subscriptions, and a join would multiply the page's rows by their connections and force a `Distinct` the pager could not trust. `total` is deliberately untouched — this is a per-row fact, not a filter, so the pager still counts the subscriptions the same predicate admits. The admin table draws the number beside the ceiling ("3 of 5") and links a non-zero value into the live log filtered to that subscription.
- **The join rule.** The page is cut from the log alone — every filter and the order are columns of that table — and only then joined to `subscriptions` and `users` for the owner's name and identifier. The title cannot join the same way (two tables, one kind at a time), so it is read as a keyed set for the identifiers the page actually carries. That is also why only `startedAt` and `endedAt` are sortable: an order on the owner or the title would order a page already cut.
- **`kind` is required and defaults to `video`; `state` is `live` or `all` and defaults to `all`.** `live` is exactly `ended_at IS NULL` — one predicate, and the one the hand-written partial index `IX_connection_logs_live_started_at` is built on, because "live" is a small tail of a table that grows forever. A value that names nothing is `400 validation_failed`, never "no filter": the screen draws one medium and one state at a time.
- **The bounds are refused, not clamped**: `page < 1` and `pageSize` outside `1..1000` are `validation_failed`, and a search above 200 characters is refused under `errors.search`. `total` is counted under the same predicate as the page, so pages sum to it and every page reports the same one.
- **The permission pair is reused, not multiplied.** Reading the log is reading the subscription surface (`viewSubscriptions`); wiping it destroys the evidence that surface is about (`editSubscriptions` plus a fresh antiforgery pair). A third pair would split one screen's access into two grants an operator has to reason about, and the owner ratified the reuse explicitly.
- **The clear ignores the screen's filters on purpose.** The button says "clear all logs", so the whole table goes — both media, live and finished alike — whatever the reader had narrowed the table to; a delete that obeyed a filter the caller happened not to send would wipe a different set from the one it named. An empty table answers 200 with a count of zero: the second press of a button that already did its job is not an error. `ExecuteDelete` is immediate and outside the unit of work, which the interface's remarks say.
- **There is no kill endpoint.** The row's "kill active connections" action stays the disabled stub it has always been, and the new page draws it disabled with the same reason. The streaming subsystem that would obey one does not exist.
- **The migration `20261102162452_AddConnectionLogs`** creates the table, **six** model indexes and one index written by hand — the partial `(started_at DESC, id DESC) WHERE ended_at IS NULL` — because EF Core's model index has no filter; it is created in `Up` and dropped in `Down`, the same treatment the subscriptions' partial unique indexes get. The six model indexes are the default order, the subscription drill-down, the stream lookup and the three exact filters the table stored at the time (`ip`, `country_code`, `isp`). `20261103190533_AddConnectionLogUserAgentIndex` adds the **fourth exact filter** and with it the seventh published index: the plain b-tree behind `?userAgent=`, scaffolded rather than hand-written because a plain index is something the model can describe. That makes **eight** indexes on the table in total — seven EF `HasIndex` entries in the snapshot plus the hand-written partial one.
- **The Development trial seeder** (`DevelopmentConnectionLogSeeder`, behind `IConnectionLogSeeder`, run from `SeedDatabaseAsync()` after `DefaultUserSeeder`) fills an empty log so the two screens have something to draw. It is Development-only through `IHostEnvironment`, idempotent through a `CountAsync` probe, and writes nothing without at least one subscription, one video stream and one audio stream — logging one line either way. Its rows name **real** records, because the subscription FK refuses a fabricated identifier and the title is resolved from a real stream row; it covers both media, at least one open session with a process id, at least one finished session, and three distinct countries and providers, so the filters and the click-through have data. **The insert intent on `IConnectionLogRepository` exists for this caller alone** — storage plumbing, not capture: the integration host's `TestUserSeeder` does not run it, and the Testing environment makes it a no-op.
- **`ConnectionLogEntity.ToModel`/`FromModel` are unused on purpose.** This pass has no production write path, so no endpoint reaches either; they stay beside each other (with remarks saying so) because the capture that arrives with the relaying process will need the same pair every other entity carries rather than a second, divergent mapping.

Layering follows the usual split: `ConnectionLog` in `Fluxy.Core/Subscriptions/Models/`, `NewConnectionLog` in `Commands/`, `ConnectionLogListItem` / `ConnectionLogPage` in `ReadModels/`, `ConnectionStreamKind` / `ConnectionLogSortField` / `ConnectionLogSortOrder` in `Enums/`, `ConnectionLogListLimits` / `ConnectionLogQuery` / `ConnectionLogQueryText` in `Utils/`, `IConnectionLogService` / `IConnectionLogSeeder` in `Interfaces/` and `IConnectionLogRepository` in `Repositories/`; `ConnectionLogService` and `DevelopmentConnectionLogSeeder` in `Fluxy.Application/Subscriptions/Services/`; the entity, configuration and repository in `Fluxy.DataAccess`; the contracts in `Fluxy.API/Contracts/Subscriptions/`; the query parser in `Controllers/Support/`; and `ConnectionLogsController` in `Fluxy.API/Controllers/Subscriptions/`.

The integration suite (`ConnectionLogTests`) pins the untouched page and its fields, the state and kind filters, every filter narrowing the total (the user agent exactly, and its case included), the bounds, the page turn, the end-time order with live sessions last, the start-time range with each side optional and both ends inclusive, a range combined with another filter, the range refusals naming their parameter, the clear with a deliberately filtered query string, the cascade on subscription delete, and the role and permission gates.
