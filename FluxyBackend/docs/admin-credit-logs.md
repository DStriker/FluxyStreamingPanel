## The reseller credit log API: `admin/credit-logs`

The audit trail of how a reseller's credit balance got to where it is. **Phase 1 is the balance and its history only** — purchasing and spending beyond an administrator editing the balance are out of scope, and the write path they will need arrives with them.

| Endpoint | Auth | Answer |
| --- | --- | --- |
| `GET /admin/credit-logs` | `Permission.ViewResellers` | page: `page`, `pageSize`, `search`, `resellerId`, `dateFrom`, `dateTo`, `sortBy`, `sortOrder` |
| `DELETE /admin/credit-logs` | CSRF + `Permission.EditResellers` | `200 credit_logs_cleared`; wipes the whole table |

- **The balance is a stored column, not a sum of the log.** `users.credits` is `integer NOT NULL`, and the migration writes the `0` existing rows need and then drops that column default, so a later insert that forgot the column is refused rather than answered with a `0` the application never chose. The model deliberately carries **no `HasDefaultValue`** — the same rule every other column of `users` follows. `credit_logs` is the trail of how the balance got here; the column is the value itself.
- **The gate is reused, not multiplied.** Reading a reseller's balance history is reading the reseller surface (`viewResellers`); wiping that history destroys evidence about it (`editResellers` plus a fresh antiforgery pair). Those two grants already exist, so `ViewResellersPolicy` / `EditResellersPolicy` are two new policy *names* over the existing bits — no `UserPermission` member, no catalog change, no migration, no frontend permission mirror.
- **The amount is a signed delta.** Positive is credit issued, negative is credit spent, zero is the entry an account created with no initial credit carries. The running total is never stored per row: a table an operator reads to find what moved would then hold a second copy of the balance, and the two could disagree.
- **`issued_by_id` is set on every row the admin panel writes — create and update, whatever the sign of the delta; it is null on a reseller-spent row and after the issuing administrator is deleted.** A create records the acting administrator even when the initial balance is `0`, because the row says who opened the account and with what balance. An update that adds credit names the administrator, and so does one that takes credit away: a decrease made from the admin panel is still an administrative edit, and naming the reseller there would misattribute it. A null issuer is reserved for the future reseller-initiated spend — a write path that does not exist yet — and for history whose issuer has been deleted. **The issuer's foreign key is `ON DELETE SET NULL`**: deleting the administrator who wrote a row must not erase the reseller's history, it only makes the issuer unknown. The reseller's key is `ON DELETE CASCADE`, because a ledger line whose subject is gone is a line nobody can be told about.
- **Descriptions are English and generated by one helper.** `Core/Users/Utils/CreditLogDescriptions.cs` builds exactly two sentences: `Reseller created with initial credits: {n}` and `Credits changed: {before} → {after}` (U+2192). The row is written once and read by every screen, so a sentence stored in one operator's language would read as noise to the next; the frontend renders its own translation from the amount where it wants one, and treats this sentence as the auditable record. Because the search box matches the description, the wording is also what the ledger is searchable by.
- **Create writes exactly one row when the target group's role is reseller** (`UserRole.Reseller`, resolved through the group — never a base-group identifier), with `amount` = the initial balance, zero included, and `issued_by_id` = the acting administrator. It is staged before the single `TrySaveAsync`, so the account and the record of the balance it started with commit together.
- **Update writes one row only when `credits` was named and differs from the stored value.** `amount` is the delta and `issued_by_id` is the acting administrator whatever the sign of the delta. An unchanged value writes nothing — a line saying `5 → 5` is noise — and the balance write and the row are staged before the **same** `TrySaveAsync`, which is what makes them atomic (pinned by a test that installs a trigger refusing the insert and then checks that neither half survived).
- **A reseller→client move keeps the balance and writes no row.** Nothing about the value changed in that request; the role changed. A later request that names `credits` on the now-client account is refused.
- **`credits` on a non-reseller is `400 validation_failed` keyed `credits`**: `Credits apply only to reseller accounts.` A negative value is the same status and key with `Credits cannot be negative.` Both rules live in the service, where the target's post-patch role is known; the sign is checked in the action too so the cheapest refusal is the one a form hears first.
- **`search` is a case-insensitive substring of the description or the reseller's username**, evaluated through the single required join, and `total` is counted under that same predicate. The issuer's name is a separate `IN` read for the page's identifiers, so the nullable issuer join never multiplies rows or reaches the count.
- **`sortBy` is `createdAt` or `amount` only** (camelCase, case-insensitive), default `createdAt desc`, tie-broken by `id desc`. Both are columns of `credit_logs`; the usernames are joined for the page, and an order built on them would order a page the server had already cut.
- **`dateFrom` / `dateTo` are one range over `created_at`, both ends inclusive and each optional.** Absent or blank means no bound on that side; a present value is an ISO 8601 date or date-time (`2026-05-01`, `2026-05-01T10:00`, `2026-05-01t10:00:00z`, `2026-05-01T10:00:00+03:00`), parsed with the invariant culture and an absent offset read as UTC. A value that parses as no instant is `400 validation_failed` naming `dateFrom` or `dateTo` — never read as "no bound", because that would widen the list silently.
- **The page bounds are refused, not clamped**: `page < 1` and `pageSize` outside `1..1000` are `validation_failed`, and a search above 200 characters is refused under `errors.search`. A page past the end answers the true `total` with an empty `items` list.
- **The clear ignores the screen's filters on purpose.** The button says "clear the credit log", so the whole table goes whatever the reader had narrowed it to; a delete that obeyed a filter the caller happened not to send would wipe a different set from the one it named. An empty table answers `200` with `0`, because the second press of a button that already did its job is not an error. `ExecuteDelete` is immediate and outside the unit of work, which the interface's remarks say.
- **`GET /auth/profile` carries `credits`; `GET /auth/me` deliberately does not.** `me` is the cheap session identity the guest guard polls on every navigation and answers from the token's claims, which is why it never gained the field; `profile` reads the row and is where the balance belongs. `GET /admin/users` and `GET /admin/users/{id}` carry it too, so the admin screens draw it without a second call.
- **The migration `20261106115256_AddUserCreditsAndCreditLogs`** adds `users.credits` with the `0` default the existing rows need (dropped immediately, see above), creates `credit_logs`, both foreign keys (`CASCADE` for the reseller, `SET NULL` for the issuer) and **three** indexes: `(created_at DESC, id DESC)` for the default order and its tie-break, `(reseller_id, created_at)` for one reseller's history, and the issuer index EF adds for the second foreign key. `Down` drops both the table and the column.

Layering follows the usual split: `CreditLog` in `Fluxy.Core/Users/Models/`, `NewCreditLog` in `Commands/`, `CreditLogListItem` / `CreditLogPage` in `ReadModels/`, `CreditLogSortField` / `CreditLogSortOrder` in `Enums/`, `CreditLogListLimits` / `CreditLogQuery` / `CreditLogQueryText` / `CreditLogDescriptions` in `Utils/`, `ICreditLogService` in `Interfaces/` and `ICreditLogRepository` in `Repositories/`; `CreditLogService` in `Fluxy.Application/Users/Services/`; the entity, configuration and repository in `Fluxy.DataAccess`; the contracts in `Fluxy.API/Contracts/Users/`; and `CreditLogsController` in `Fluxy.API/Controllers/Admin/`. The write path stayed where it belongs — `UserAdminService.CreateAsync` / `UpdateAsync` — because the log row is part of the balance change, not an operation of its own.
