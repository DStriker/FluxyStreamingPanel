## The video streams API: `admin/video-streams`

The first piece of the relaying domain. A stream is a named, typed entry the relay process plays; the playing itself is not in this API. A stream has no position of its own.

| Endpoint | Auth | Answer |
| --- | --- | --- |
| `GET /admin/video-streams` | `Permission.ViewStreams` | page: `page`, `pageSize`, `search`, `categoryId`, `status`, `type`, `sortBy`, `sortOrder` |
| `GET /admin/video-streams/{id}` | `Permission.ViewStreams` | one stream with `sources` and `files`; `404 video_stream_not_found` |
| `POST /admin/video-streams` | CSRF + `Permission.EditStreams` | `201 video_stream_created` + relative `Location` |
| `PATCH /admin/video-streams/{id}` | CSRF + `Permission.EditStreams` | `200 video_stream_updated` |
| `POST /admin/video-streams/{id}/start` / `…/stop` / `…/restart` | CSRF + `Permission.EditStreams` | `video_stream_started` / `video_stream_stopped` / `video_stream_restarted` |
| `POST /admin/video-streams/bulk` | CSRF + `Permission.EditStreams` | `200 video_streams_bulk_completed`, one entry per identifier |
| `POST /admin/video-streams/import` | CSRF + `Permission.EditStreams` | `200 video_streams_import_completed`, counts and per-line problems |
| `DELETE /admin/video-streams/{id}` | CSRF + `Permission.EditStreams` | `200 video_stream_deleted`, `404` on a second |

- **The type owns the fields only it can use, and the two halves are asymmetric on purpose.** A `Permanent`/`OnDemand`/`Redirect` stream takes `sources`; `OnlineSeries` takes `seriesId`; `VodPlaylist` takes `vodId`; `FilePlaylist` takes `files`. A payload the chosen kind cannot use is **dropped**, not refused — a form whose operator just changed the type is still carrying the previous kind's values, and refusing them would answer a request nobody meant. The one exception is `archiveDays`: only a `Permanent` stream may keep an archive, and a non-zero value on any other kind is **refused** (`400` naming `archiveDays`), because an archive length is a promise about retention rather than a leftover field. The form mirrors that by greying the field out and zeroing it in `toBody`, so it never builds a body the server would refuse.
- **A programme guide is two facts or none.** Exactly one of `epgSourceId`/`epgChannelKey` is refused with `validation_failed` naming **both** fields; both set or both empty are the only accepted answers. `hasEpg` on the read side is derived from the pair, never stored.
- **`status` is a field of both writes.** An operator chooses it on the add form (which starts at `Running`) and can enable or disable an existing stream on the edit form; the create endpoint keeps `Stopped` only as the answer for a body that names no status, and `PATCH` treats an absent value as "keep", which is what lets the bulk service patch other fields without reviving or halting a stream. `start`/`stop`/`restart` remain the three table transitions that write the same row fact. `activeSource` is never written by the service at all: the relaying process reports it and nothing else.
- **A name is unique within its category** (`UNIQUE(category_id, name)`), compared exactly and case sensitively like username and email. A lost race is caught and mapped to `409 video_stream_already_exists` naming `name`.
- **Both lists are replaced wholesale, never patched.** Absent keeps, empty clears, a list replaces in the order sent — which is what makes the order on the operator's screen the order the relay plays in, with no position arithmetic to get wrong. An empty `sources` is still refused for a URL kind ("add at least one source address"), matching the form's own whole-list rule.
- **No captcha, no attempt window** — the recorded admin-area departure: every write is behind an `AdminOnly` session plus the `EditStreams` permission and a fresh antiforgery pair, and `RejectsCsrfAsync()` runs before any body is read.
- **There is no stream position, in the schema or in a write.** `video_streams.sort_order` was dropped by `20261023121109_DropVideoStreamSortOrder`; the order a stream is shown in belongs to the list that shows it, and when bouquets arrive it belongs to the membership rather than to the stream row. A create therefore appends nothing, a category change moves nothing, and a playlist's order is not a display order — the list is ordered by the query. The migration drops `IX_video_streams_category_id_sort_order` with the column; the unique `IX_video_streams_category_id_name` already answers the category filter, so no replacement index is needed. `Down` recreates the column at `0` and the index, but cannot restore the positions that were there.
- **The list is paged** (`total` counted before paging, the same "the pager must not lie" rule the accounts and session histories follow), `search` is a case-insensitive substring of the name, and the sort fields are the column keys — `name`, `category`, `status` and `type` — parsed from plain text case-insensitively. `pageSize` defaults to 20 and is refused above **1000**, the same ceiling as every other paged table; that ceiling is also what lets the table's "select everything" checkbox hand one whole page to the bulk endpoint.

### Bulk operations over the streams

`POST /admin/video-streams/bulk` applies one of nine operations to the streams one page holds: `start`, `stop`, `restart`, `delete`, `move-category`, `change-type`, `change-delay`, `change-archive` and `change-restream`. It has a controller of its own (`VideoStreamsBulkController`) because the request names a set the table assembled rather than one addressed row and the answer is a per-identifier report; the policy is the same `EditStreamsPolicy` the single-row writes carry.

- **A well-formed run answers `200 video_streams_bulk_completed`**, with `succeeded`, `failed` and one `items` entry per identifier. Each entry carries the very code the single-row endpoint would answer (`video_stream_started`, `video_stream_not_found`, …), `ok` read off the status that code maps to, and `errors` keyed by camelCase field name. A category move that collides with a name already used there refuses **that row alone** with `video_stream_already_exists`; the others still move. Partial success is the shape.
- **The body is validated before any row is read.** The action is matched case-insensitively and with hyphens (`Start`, `change-type`); identifiers must be 1..1000 uuids and duplicates collapse; the value an action needs must be present and usable. A body that breaks any of those answers `400 validation_failed` naming every broken field at once. `RejectsCsrfAsync()` runs **before** the body is parsed, so a stale pair is `csrf_invalid` rather than a validation answer.
- **Every operation delegates to the single-row service.** Start, stop, restart and delete are the same writes the row buttons make; a move is `UpdateAsync` with only a `categoryId`. That is why the category-scoped name collision, an unusable category and a missing stream are all answered per row rather than aborting the run.
- **Three collective rules live in the bulk service.** A delay or an archive may only be written to `Permanent` streams, restream settings only to `Permanent`/`OnDemand`, and a bulk type change may only choose `Permanent`, `OnDemand` or `Redirect`. Any other kind answers `validation_failed` on that row (`delayMinutes`, `archiveDays`, `restreamUserAgent`) while the rest of the selection continues.
- **A bulk type change clears what the destination cannot carry instead of refusing the row.** Moving to `OnDemand`/`Redirect` clears a non-zero delay and archive; moving to `Redirect` also clears all four restream settings. The row still lands as `video_stream_updated`, and each clearance is a warning: `video_stream_delay_cleared`, `video_stream_archive_cleared`, `video_stream_restream_cleared`, each `{ code, message }`. A successful change that cleared nothing answers `warnings: null`; a refused row never carries a warning, because nothing was written.
- **Restream is a whole-value replacement, not a patch of one field.** All four settings are written on every run and a blank field clears its setting. Zero is a value for delay and archive, not an absence.
- **Restart is also a single-row action** (`POST /admin/video-streams/{id}/restart`): it writes `Running` and answers `video_stream_restarted`. It is not a separate status and deliberately leaves `activeSource` alone, because that is the relaying process's report.
- **No schema change.** A bulk operation is the existing writes applied in a loop — no table, no queue, no background worker, no migration.

### The playlist import: `POST /admin/video-streams/import`

The other way to add streams: one M3U file in, a category's worth of rows out. It has a controller of its own (`VideoStreamsImportController`) because the request is a file rather than a JSON row and the answer counts a batch rather than describing one stream — the same seam that gave the bulk endpoint its own controller.

- **The form is the add form without the two fields the file supplies.** `multipart/form-data` carries `playlist`, `type`, `status`, `categoryId`, `delayMinutes`, `archiveDays` and the four restream fields; there is no `name` and no `sources`, because each entry's title names its stream and each entry's address is its one source. `type` is limited to `Permanent`, `OnDemand` and `Redirect` (the three kinds that relay from a list of addresses); an absent `status` means `Stopped`, so a batch cannot start relaying by omission. `archiveDays` above zero is still refused on a non-`Permanent` kind, the same rule the add form follows.
- **`RejectsCsrfAsync()` runs before the form is read**, and the content type is checked before the form reader can throw its own exception. A `Content-Length` greater than the file limit plus a megabyte of multipart overhead is `413 video_stream_import_too_large` before anything is buffered; the file length itself is checked again after the form is parsed. A body that is not a form at all is `415 unsupported_media_type`; a URL-encoded body carries no file and is refused as a validation error.
- **The parser reads one `#EXTINF` and the absolute URL after it as one entry.** The name is the title after the first unquoted comma, then `tvg-name`, then `Stream N`; a URL with no directive still becomes an entry under the fallback name. BOM and CRLF are tolerated, unknown directives are ignored, and quoted attributes may contain commas. What it refuses, it refuses one line at a time: a dangling directive or an address that is not absolute becomes a problem on its line and the rest of the file is still read. An HLS playlist is refused whole — its `#EXT-X-` tags name variants of one stream, not separate channels.
- **The batch is partial success by design.** `imported + skipped + failed == total`, and every entry that did not land is in `problems` with its line, name, code and field errors. A name already used in the category or repeated within the file is **skipped** (`video_stream_already_exists`); an unusable title, source or parser line is **failed** (`validation_failed`). Existing streams are never updated: the only names the service reads are the ones it must refuse, and every surviving entry becomes a new row.
- **One save writes the batch.** The service stages every row through `AddRangeAsync` and calls `TrySaveAsync` once. A name another request took between the check and the save is `409 video_stream_import_conflict` and **nothing** from the batch is written; the check matches `IX_video_streams_category_id_name` by name, so any other unique violation is rethrown rather than announced as a taken name. No migration: the import writes the same three tables the single create writes.
- **Refusals are one code each**: `video_stream_import_empty`, `..._hls`, `..._too_many_entries` and `..._unreadable` are `400`, the size refusal is `413`, and a save-time name race is `409`; every other field problem is `400 validation_failed` with the field named. The file limit is 10 MiB and one import accepts 5000 entries.

The parser is covered by twelve unit tests; the endpoint by four integration tests — a mixed playlist (one imported, two skipped, one failed) with its counts and stored rows, an empty playlist and an HLS one refused whole, a missing file and a type the import cannot use, and a request without the antiforgery pair refused before the file is read.

Layering follows the usual split: `VideoStream` in `Fluxy.Core/Streams/Models/`, `VideoStreamPage` / `VideoStreamListItem` in `Fluxy.Core/Streams/ReadModels/`, `NewVideoStream` / `VideoStreamPatch` / `VideoStreamWrite` / `BulkVideoStreamOperation` / `M3uPlaylistEntry` / `NewVideoStreamImport` in `Fluxy.Core/Streams/Commands/`, `VideoStreamOutcome` / `BulkVideoStreamOutcome` / `BulkVideoStreamItemResult` / `M3uPlaylistOutcome` / `M3uPlaylistProblem` / `VideoStreamImportOutcome` / `VideoStreamImportProblem` in `Fluxy.Core/Streams/Outcomes/`, `VideoStreamAction` / `BulkVideoStreamAction` / `VideoStreamBulkWarning` / `VideoStreamSortField` / `VideoStreamSortOrder` / `VideoStreamStatus` / `VideoStreamType` / `M3uPlaylistStatus` / `VideoStreamImportStatus` in `Fluxy.Core/Streams/Enums/`, `VideoStreamLimits` / `VideoStreamListLimits` / `VideoStreamBulkLimits` / `VideoStreamEpg` / `M3uPlaylistParser` / `VideoStreamImportLimits` in `Fluxy.Core/Streams/Utils/`, plus `IVideoStreamService` / `IVideoStreamBulkService` / `IVideoStreamImportService` in `Fluxy.Core/Streams/Interfaces/`, `VideoStreamService` / `VideoStreamBulkService` / `VideoStreamImportService` in `Fluxy.Application/Streams/Services/` and the `VideoStreamRules` helper in `Fluxy.Application/Streams/Utils/`, the three entities and their configurations in `Fluxy.DataAccess/` (migrations `20261014125324_AddVideoStreams` and `20261023121109_DropVideoStreamSortOrder`), the contracts in `Fluxy.API/Contracts/Streams/` plus `BulkItemWarningResponse` in `Fluxy.API/Contracts/Common/`, `VideoStreamsController`, `VideoStreamsBulkController` and `VideoStreamsImportController` in `Fluxy.API/Controllers/Content/`.

### What running caught: a PATCH that failed on any stream with a list

`dotnet build` was clean and every rule above read correctly. Against a running instance, a `PATCH` that renamed a stream — or changed anything at all — answered `409 video_stream_already_exists` on a table holding exactly one row, under a name nobody else held. Two separate mistakes were stacked, and each one hid the other:

- **`UpdateAsync` loaded the stream without the two collections.** `ReplaceSources`/`ReplaceFiles` decide what to delete by comparing the wanted list against what the row already holds — and an unloaded `ICollection` navigation reads as **empty**, never as null. So the comparison always differed, `RemoveRange` removed nothing, and the fresh rows were inserted straight over the ones still in the table, colliding on `IX_video_stream_sources_stream_id_position` (SQLSTATE 23505). Fixed with `.Include(entry => entry.StreamSources).Include(entry => entry.StreamFiles)` on that load. **The read path deliberately does not do this** — `GetAsync` and the page read the two lists as separate `AsNoTracking` queries, because a page of twenty streams would otherwise be two more collections per row for data the table never draws.
- **Every unique violation was reported as a name conflict.** `SaveAsync` returns the `DbUpdateException` for *any* 23505, and both `CreateAsync` and `UpdateAsync` answered it with `AlreadyExists(Name)`. Three unique indexes exist here and only one is about the name — the other two are the position columns of the two lists — so a bug in the list writer was announced as "that stream name is already taken", which sent the search to the uniqueness rule instead of to the write. Both now ask `IsNameIndexViolation`, which matches the constraint name `IX_video_streams_category_id_name` inside the message; anything else is **rethrown** rather than dressed up, so a future bug surfaces as the 500 it is instead of a plausible 409.

Both are worth remembering as one rule: a `DbUpdateException` carries *which* constraint refused, and mapping all of them to the one outcome the code knows how to explain turns every future bug into a confidently wrong answer.

Verified against a running instance: create → `201` with an honest `Location` and both lists stored in the order sent; a reorder → `200` and the next read answers the new order; a shorter list → wholesale replacement with no orphans; an empty list → `400` with the stored list intact; a same-name `PATCH` → `200` (the exclusion that lets a rename keep its own name); a rename to a free name → `200`; `start` twice → `200` both times; `archiveDays` on a non-Permanent kind → `400` naming it; a half guide → `400` naming both fields; `delete` → `200`, `delete` again → `404`.
